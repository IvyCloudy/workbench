## F1. 案例文件 + 非案例文件推送时，案例编辑器页内出现两层浮层堆叠

### 用户场景
用户在资源管理器选中一个案例文件和一个非案例文件（不含 `testcase_id`，如台账、配置导出），右键「推送」。

用户反馈的问题：
- 推送过程中案例编辑器页内先弹出一个「已跳过非案例文件」浮层（底层）。
- 推送完成后，在汇总里点案例行查看结果时，案例编辑器页内又叠出一个「推送结果」浮层（上层）。
- 关掉上层后，底层的跳过提示仍然留在页面上，看起来像两个结果叠在一起。

### 需求
1. 批量推送流程（含仅 1 个案例文件的情形）中，非案例文件的去向**不应**在案例编辑器页内单独弹浮层说明，而是统一由「门控/汇总面板」里的灰色「已跳过」行承载，并注明"不含 testcase_id，已跳过"。
2. 仅在"全部所选文件都是非案例文件（没有任何批量面板可以承载跳过信息）"时，才在案例编辑器页内弹一次「已跳过」浮层兜底。
3. 上述兜底浮层所在路径没有后续的推送结果层，因此不会出现两层堆叠。

### 使用预期
- 选案例 + 非案例一起推送 → 门控/汇总面板里出现灰色「已跳过」行；点案例行才在其案例编辑器页内弹出推送结果浮层。两层不再叠在同一页。
- 全是非案例文件（单选）推送 → 只弹一次「已跳过」页内浮层，无结果层，不堆叠。

### 补充说明（已确认方案与约束）
- 根因：旧逻辑对"案例文件数 ≤ 1"的推送，会在案例编辑器页内提前弹出跳过提示浮层；而推送结束后查看结果又在该页内叠加结果浮层，造成两层堆叠。
- 口径一致性：非案例文件在"门控视图"和"汇总视图"两处都以同一灰色「已跳过」行呈现，用户在校验阶段即能看到文件完整去向，无需再额外弹窗。
- 与不推送的语义一致：非案例文件本身不参与推送、不会出现在推送成功/失败统计里，仅在汇总中以中性灰状态标记"已跳过"。

## F2. 选中文件数 > 1 时，无论是否案例文件，都应弹汇总界面

### 用户场景
用户在资源管理器用多选（Ctrl/Shift 选中 2 个及以上文件）进行推送，所选可能包含：
- 多个案例文件；
- 案例 + 非案例混合；
- 全部是非案例文件（如多个台账/配置导出）。

用户期望：无论哪种组合，都能看到一个统一的「汇总界面」回显每文件的推送结果。

### 需求
1. 选中文件数 > 1（多选）时，一律走批量汇总流程，**不区分**是否案例、是否混合、是否全是非案例。
2. 全是非案例文件的多选推送，直接弹汇总界面：以灰色「已跳过」行呈现每个非案例文件，并附顶部说明"所选文件均不含 testcase_id，已全部跳过，未推送任何案例"，不再弹页内浮层。
3. 单选（仅 1 个选择条目）的案例文件推送，保持原有的"编辑器内结果弹窗"行为不变（不在本需求范围内强制改为汇总）。

### 使用预期
- 多选任意组合 → 进入汇总界面；非案例以灰色「已跳过」行出现，案例以成功/失败行出现。
- 全是非案例多选 → 汇总界面只有灰色「已跳过」行 + 顶部说明，不出现空的进度面板闪现。
- 单个案例文件单选推送 → 仍为编辑器内结果弹窗（与既有行为一致）。

### 补充说明（已确认方案与约束）
- 触发口径：以"选择条目数 > 1"作为是否进入汇总的判定，而非"案例文件数"。这样即便多选里只含 1 个案例文件（其余为非案例），也会进入汇总，避免"有汇总、有无汇总"的体验分裂。
- 全跳过状态呈现：当汇总结果全部为「已跳过」、无成功/失败时，汇总头部的状态使用中性灰标识（而非绿色"成功"），避免误导用户以为推送成功。

## F3. 案例 + 非案例（仅 1 个案例文件）推送后无汇总界面，只有编辑器内结果弹窗

### 用户场景
用户选中"1 个案例文件 + 1 个非案例文件"（即总共只有 1 个案例文件）右键推送。

用户反馈的问题：
- 推送后只看到了案例文件内的「推送结果」弹窗，没有看到汇总面板，非案例文件的去向也不清楚。
- 不符合"多选应弹汇总"的预期（这里虽然案例文件只有 1 个，但选择条目是 2 个）。

### 需求
1. "单文件编辑器内推送"路径（结果直接弹在案例编辑器页内）的判定条件应收紧为**真正的单选**：仅当"选择条目数为 1 且非文件夹、且为案例文件"时才走该路径。
2. 多选（选择条目数 > 1）即便只含 1 个案例文件，也应走批量汇总流程，汇总界面中呈现"案例结果行 + 灰色已跳过行"。

### 使用预期
- 选 1 案例 + 1 非案例 → 汇总界面（案例结果行 + 灰色「已跳过」行），点案例行可查看其推送结果。
- 选 1 个案例文件（单选）→ 编辑器内结果弹窗，保持原行为。

### 补充说明（已确认方案与约束）
- 与 F2 的触发口径对齐：统一以"选择条目数"与"是否含文件夹"作为是否进入汇总的分流依据，而非"案例文件数"，避免"案例数==1 走编辑器内、案例数>=2 走汇总"这种割裂。
- 单文件路径保留的合理性：真正单选一个案例文件时，用户更习惯在原案例编辑器页内直接看到结果弹窗，故维持既有行为，不做强制汇总。

## F4. 文件夹作为一个选择条目，应统一走汇总界面

### 用户场景
用户在资源管理器选中一个文件夹（例如 `测试任务/<任务>/测试案例/` 下的某个子目录），右键「推送」。文件夹内部可能包含：
- 多个案例文件；
- 案例 + 非案例混合；
- 仅非案例文件。

用户反馈的问题：
- 文件夹只占 1 个"选择条目"，若内部恰好只有 1 个案例文件，当前会被当成"单文件"走编辑器内推送路径，与"多选/文件夹应走汇总"的预期不一致，且非案例文件去向也不清楚。

### 需求
1. 任一选择条目为文件夹时，强制走批量汇总流程，**不受文件夹内部文件数量、是否案例的影响**。
2. 文件夹内的非案例文件以灰色「已跳过」行并入汇总；案例文件以成功/失败行呈现。
3. 文件夹内全部为非案例文件时，同样进入汇总界面（灰色「已跳过」行 + 顶部说明），不弹页内浮层。

### 使用预期
- 选文件夹（任意内部构成）→ 直接进入汇总界面。
- 文件夹内混合案例/非案例 → 汇总中案例结果行 + 灰色「已跳过」行齐备。
- 文件夹内全是非案例 → 汇总只有灰色「已跳过」行 + 顶部说明。

### 补充说明（已确认方案与约束）
- 触发口径统一：把"是否含文件夹"与"选择条目数 > 1"并列作为强制进入汇总的依据。只要满足其一，即走批量汇总；仅"单选一个案例文件（非文件夹）"才走编辑器内结果弹窗。
- 与 F1~F3 一致：文件夹场景下非案例文件同样以灰色「已跳过」行呈现，不单独弹页内浮层，杜绝多层堆叠。

## F5. 推送前校验案例路径合法性，命中非法路径时拦截并提示原因

### 用户场景
用户在资源管理器选中案例文件（单选 / 多选 / 文件夹均可）右键「推送」，将案例推送到线上 TMS 的指定案例路径下。

用户期望：推送之前，系统能先确认"这个目标路径在线上到底能不能挂案例"。常见的不可推送情形包括：
- 目标路径其实是一个**功能条目**（不是测试要点），按规则不允许直接挂案例；
- 目标路径是一个**非末级测试要点**（下面还有更细的测试要点），案例只能挂在末级测试要点上；
- 目标路径上对应的**测试要点根本不存在**，路径无效。

如果直接推，要么在远端失败、要么产生挂错位置的脏数据。用户希望推送前就被拦下，并清楚知道是哪一类原因。

### 需求
1. 本项校验**合并进已有的「案例合法性校验」功能**，与其共用同一套失败呈现与阻断逻辑（不是独立弹窗）：
   - **案例文件打开时**：编辑期主动校验（打开弹窗 / 单元格红黄高亮）即包含本项；
   - **案例推送前**：批量前置校验与单文件前置校验均包含本项。
2. 推送前，调用接口查询每个案例文件的目标路径在线上是否存在及其类型（接口入参为当前测试任务信息与一组案例路径，返回每个路径的类型信息）。查询前先复用推送映射层 `pushDataMapper.normalizePath` 对非空路径做标准化（去开头 `/`、补结尾 `/`、`\` 转 `/`），与真正推送时 `testCasePath` 的取值口径一致；接口回显路径同样标准化后匹配。标准化后无效的路径（如 `/`、`\`）本地即判定为非法，产出 `pathInvalid` 失败项（"路径格式无效，请核对路径"）并剔除该行，不等到推送映射阶段才报错。
3. 在调用接口之前，**本地先拦截「路径为空」**：案例文件中未填写任何有效案例路径（如「路径」列缺失或全空 / `path` 字段缺失）即视为非法、阻碍项，提示"案例路径未填写"，无需依赖接口。
4. 依据接口返回，对以下三类非法路径**判定为路径不合法**（弹窗展示时统一加「路径问题：」类别前缀，下列为前缀后的具体原因；文案与「打开文件 / 推送前」通路无关，见补充说明「提示词通用化」）：
   - **① 功能条目**：路径类型为功能条目（`tcoType = 1`）→ 提示"路径为功能条目，无测试要点，请核对路径"。
   - **② 非末级测试要点**：路径类型为测试要点（`tcoType = 2`）且末级测试要点数量大于 1（`pointTotal > 1`）→ 提示"路径为非末级测试要点，请核对路径"。
   - **③ 测试要点不存在**：路径类型为测试要点（`tcoType = 2`）且末级测试要点数量为 0（`pointTotal = 0`）且类型为 3（`type = 3`）→ 提示"路径上的测试要点不存在，请核对路径"。
5. 合法路径（如末级测试要点且测试要点存在）正常进入推送流程，不受本校验影响。
6. 校验结果统一并入「案例合法性校验」的失败集合：非法路径按**行级通用格式**呈现（问题行 / 问题列 / 问题原因），与该行其它校验问题融合到同一张 05g 卡片；任一 error 即阻断本次推送。

### 使用预期
- 打开一个案例文件（其路径命中上述非法情形或路径为空）→ 编辑期校验弹窗显示「第 N 行」+ 原因文案，编辑器里 path 列对应单元格染红、hover 可看原因；此时展示的原因文案与推送前完全一致，不出现"不允许推送"这类与打开场景无关的表述。
- 选中的案例文件里，只要有一个目标路径命中上述非法情形 → 推送被拦截，汇总/门控界面出现对应失败行与原因（如"路径问题：路径为非末级测试要点，请核对路径"）。
- 所有目标路径均合法 → 正常推送，本校验不出现任何提示。
- 即便单文件推送，命中非法路径（含空路径）也会在推送前被拦截并提示，不会真正发出。

### 补充说明（已确认方案与约束）
- **合并方式 / 通用格式**：本项不是独立弹窗，而是「案例合法性校验」的**行级**失败项（`severity=error`）。`collectPathFailuresForFile` 先还原「路径 → 行」引用，接口判定非法后按引用行逐行产出：
  - 问题行 → `tsId` 用该行真实 `testcase_id`、`rowIndex` 为 1-based 行号（05g 组头「第 N 行」，可点击跳转）；
  - 问题列 → `field='testCasePath'`（编辑器 path 列红底 + hover 原因）、`columnName='案例路径'`；
  - 问题是什么 → `reason`，带「路径问题：」类别前缀 + 具体原因。前缀与问题列解耦：`columnName` 仍用列名做定位/高亮，reason 前缀改为标明问题类别、不再复用列名；前缀常量为 `CASE_PATH_REASON_PREFIX`（`caseRowFields.ts`）。
  - **合法路径结构**：`功能条目/{测试点路径}/末级测试要点`，案例必须挂在末级测试要点上，故「路径为功能条目（无测试要点）」「路径为非末级测试要点」「路径上的测试要点不存在」均不合法。
  - **提示词通用化**：同一份 `reason` 由「打开文件」与「推送前」两条通路共用，因此只描述路径本身的问题 + 修复建议（"路径为功能条目，无测试要点，请核对路径" / "路径为非末级测试要点，请核对路径" / "路径上的测试要点不存在，请核对路径"），不使用"不允许推送"等推送动作措辞。空路径必填文案 `CASE_PATH_EMPTY_REASON` 本就是中性的"案例路径未填写"，保持不变（`classifyFailure` 依赖 reason 归类）。
  - 同一路径被多行引用 → 每行各一条；同 `rowIndex` 的其它字段问题由 05g 自动聚合到同一张卡片，实现与缺列 / 枚举非法 / 待补充等校验的融合。
  - 接口异常 / 未回显路径不产出「接口不可用」提醒，统一按「无法判定即跳过」处理（见下方降级策略）。
- 判定依据：接口对每个路径返回的类型字段（`tcoType` / `pointTotal` / `type`）；不关注返回中具体案例列表（`data`）内容。
- **空路径**：由 `preValidate/validators.ts` 的行级 `PATH_EMPTY_VALIDATOR`（`error`、`field='testCasePath'`）逐行拦截并高亮；`collectPathFailuresForFile` 不再产出文件级空路径项，避免与通用行级格式不一致。该必填校验不依赖任务绑定、不查接口。
- 失败级别：命中规则属于阻断性错误（error），与门控界面中其他错误同级，触发统一阻断。
- 前置闸门：案例文件**未绑定测试任务**时，路径合法性校验（接口判定）整项跳过（不拦截、不查接口）——与推送自身要求绑定任务的约束一致；空路径必填校验不受此闸门影响。
- 样例行：`isSampleTsId` 命中的模板示例行（`案例唯一标识，不可修改` / `案例唯一标识`）**不参与路径合法性校验**，与 `runValidators` 主循环、重复案例名称校验、`extractSampleRows` 同口径；还原行引用时跳过该行但仍用原始下标作 `rowIndex`，其余行号不变。英文占位 `TESTCASE_ID` 不属于中文样例行，仍参与占位校验与路径校验。
- 代码复用：`src/utils/caseRowFields.ts` 是行字段读取的公共层（规范键别名 / 表头大小写兼容 / null 口径 / 样例行判定 / 路径列展示常量），`validators.ts` 与 `casePathValidator.ts` 共用。路径校验与 `runValidators` 使用同一份 `rows` / `resolveRowIndex`，结果以 `pathInvalid` kind 并入 `PRE_VALIDATE_KIND_ORDER`，由 `flattenFailuresByKind` 统一排序，命中行并入 `droppedIndex`。**字段取值以 `pushDataMapper` 为准：YAML/JSON 只用英文键，CSV 只用规范中文列名；中文变体表头由缺列校验在文件层拦下**。
- 检视后收敛（复用 / 类型安全 / 文案通用化）：
  - `PushFailCategory` 正式纳入 `'casePath'` 分类码，`casePathValidator.ts` 去掉 `as` 强转（分类值不变，埋点不受影响）；
  - `validators.ts` 的 `testcase_id` 占位 / 空值 reason 去掉「后再推送」；05g 打开通路 hint 去掉「阻断」，纯 warn 底部提示改为「将保留上述提醒并继续推送」，避免纯 warn 场景误称包含「待补充」案例；
  - 新增 `src/preValidate/validationSource.ts`：`resolveTargetType` / `loadValidationSource` / `FILE_LEVEL_TSID` 由 `editValidationHandler`、`batchPreValidate`、`stepPreValidate` 共用，消除两份文件类型判定与 parse→sourceRows 组装、`__FILE_LEVEL__` 字面量重复；
  - 新增 `src/utils/pushFailure/severity.ts` 的 `normalizeSeverity`，统一各模块 `severity || 'error'` 兜底口径；
  - 归类 / 字段相关符号统一从 `utils/pushFailure` barrel 引入，deprecated `utils/pushFailureCategory` 不再被引用（文件保留兼容）。
  - **P0 修复（路径列口径）**：新增 `findCaseColumnIndex` 统一 CSV 表头定位（规范键 + 大小写 / 空白变体），`CASE_PATH_COLUMN_ALIASES` 与 `missingColumns` 路径 spec 统一为规范键（`path`/`路径`）。此前表头写「案例路径」时三层校验口径不一致；现由缺列校验在文件层拦下中文变体，规范表头下缺列、行级必填、路径合法性三层均能正常命中，并补了回归用例。
  - **P2 / P3 收尾**：路径列别名按要求去掉 `testCasePath`（`CASE_PATH_FIELD` 接口字段码保留），`missingColumns` 与前端高亮清单同步；新增 `src/test/preValidateShared.test.ts` 直接覆盖 `validationSource`（合规目录判定、CSV / YAML / JSON 三种 `sourceData` 组装、parse 异常上抛）与 `normalizeSeverity`；文件级伪 tsId 收敛到 `src/utils/failureTsIds.ts` 单一来源，前后端同值由契约测试守护。另清理 `loadValidationSource` 补可选链、`testcase_id` 空值提示统一为「案例ID」、未知 `tcoType` 增加诊断日志但仍按合法放行。
  - **字段口径对齐推送映射层**：`caseRowFields` 与 `missingColumns` 的名称 / 路径别名收窄为规范键（YAML 英文 `name`/`path` + CSV 中文「名称」/「路径」），与 `pushDataMapper` / `enumTypeValidators` 一致；中文变体表头由缺列校验在文件层拦下，避免放行后 mapper 读出空字段。明确 **YAML/JSON 中文只是 `headerLabels` 的显示映射，不是数据键**。`src/test/caseFieldContract.test.ts` 按 CSV / YAML 断言「缺列判定」与「行级校验」一致。
  - **测试基线修复（P1）**：全局 `vscode` mock 补 `env` / `commands`，7 个 `pushFailureStore` mock 补 `collectFailureColumns` 等导出；`pushCoreEditorFlow.repro.test.ts` 给非法 tsId 行补 `type` 以隔离枚举校验噪声。全量单测由 `11 failed / 54 failed` 收敛为 0 失败，主链路集成回归恢复。
- 降级策略（接口异常 / 超时 / 未回显路径，A）：无法判定即**跳过**，不拦截、不产出提示；仅当接口正常返回且明确命中非法规则时才是 `error` 级硬阻断。未能判定的路径不写结论缓存，下次校验仍会重试。
- 触发覆盖与按需查询：批量 / 文件夹 / 混合选择走 `validateFileForPush`，单文件推送走 `runPush` 内的 `stepPreValidate`，打开 / 工具栏「格式校验」走 `editValidationHandler`；三处共用 `collectPathFailuresForFile`，均**全量查询线上最新状态**。表格单元格编辑保存 / 文本编辑防抖复用同一条 `requestEditValidation → _doValidate → runValidators + pathInvalid → persistPushFailures → postEditValidationRefresh` 闭环，但走**增量**：`collectPathFailuresForFile` 按文件缓存「路径 → 判定结论」，只向接口查询本次新增 / 改动过的非空 `path`；路径未变时复用结论重新产出 `pathInvalid` 失败项。因此改路径单元格会立即重新判定，改其它列不重复打接口，也不会因编辑期覆盖式写盘清掉已有的 path 红格。缓存仅对编辑期生效，换绑测试任务或路径集合清空时自动失效；推送前 / 打开时强制全量，不受缓存影响。空路径始终由 `PATH_EMPTY_VALIDATOR` 逐行拦截，不查接口。
- 后端契约（B）：`query-tco-path` 应回显全部查询路径并以字段标记状态（`pointTotal=0/type=3` 表示测试要点不存在）；未回显的路径不判定。
- 绑定信息（C）：绑定缺少 `subTestTaskId` 时查询结果可能失真，需绑定流程保证带出该字段。
- 埋点：本校验不新增专用埋点；接口成败由 `http.queryTcoPath` 的 `api.queryTcoPath.ok/fail` 覆盖，失败项走编辑期 / 推送期既有的通用埋点。

## F6. 步骤明细弹窗内删除步骤的确认框异常偏长

### 用户场景
用户在案例编辑器的「步骤明细」弹窗（双栏布局：左侧步骤列表 + 右侧字段卡片）中，选中某一步骤并点击删除。

用户反馈的问题：
- 点击删除后弹出的确认框（"确定删除该步骤？"）宽度异常地长，几乎铺满整个步骤明细弹窗的宽度，而框内只有一句简短的确认文字，视觉上很不协调。
- 该确认框本应是居中、紧凑的小弹窗，却被撑成了接近全屏宽的大框。

### 需求
1. 通用确认 / 提示弹窗（`xsPromptModal`）宽度应回归紧凑的默认宽度（约 380px），短文字确认框（如"确定删除该步骤？"）不应被页面级通用弹窗的宽规则（`88vw` 等）撑满。
2. 调用方按需加宽的情形（如承载富文本表格的确认框）维持可自定义宽度的能力，不受默认宽度限制。
3. 纯文字确认 / 提示内容较长时，应限制弹窗高度上限，并让内容区可滚动，避免内容被裁切或弹窗超出视口、按钮不可达。

### 使用预期
- 步骤明细里删除步骤 → 弹出的「确定删除该步骤？」为居中紧凑小框，宽度与文字量匹配，不再横向铺满。
- 其它短文字确认 / 提示（如各类"确定？"）同样保持紧凑宽度。
- 承载表格等宽内容的确认框仍按调用方指定宽度正常展示。
- 文字较多的确认 / 提示内容出现滚动条，弹窗不超出屏幕、按钮始终可点。

### 补充说明（已确认方案与约束）
- 根因：通用确认 / 提示弹窗的对话框在 HTML 中带内联默认宽度 `380px`，但每次打开时旧逻辑在未传自定义宽度时会把该内联宽度清空，随后被页面级通用规则 `.xs-modal-dialog{width:88vw}` 覆盖，导致确认框被撑成全屏宽。修复为"缺省显式恢复 380px 默认宽度"，并在关闭时重置，彻底避免被通用宽规则接管。
- 高度保护仅作用于纯文字（`message`）内容；富文本表格（`html`）确认框保持原生高度不约束，避免破坏宽表格展示。
- 涉及文件：`media/pages/table-editor/editor/05b-prompt-confirm.js`（`_applyXsPromptConfig`、`closeXsPrompt`）。

## F7. CMBT_AITEST 平台案例（MBT 前缀 ID）的推送与删除适配

### 用户场景
用户文件中存在来自 CMBT_AITEST 平台的案例，其 `testcase_id` 形如 `MBT58a41215a4be69bb3ca921687afa02f6`（严格大写 `MBT` 前缀 + 32 位小写字母数字）。这类案例原先按现有 `testcase_id` 格式规范会被判为非法，推送前就被拦截；即便放行，推送到线上的 `sourceId` 也会带着 `MBT` 前缀，与该平台线上的既有数据对不上。

### 需求
1. **校验放行**：严格大写 `MBT` + 32 位小写字母数字的 `testcase_id` 视为合法，推送前不再因 ID 格式被拦截；前缀大小写、后缀大小写、长度或字符不符合的一律不放行。
2. **平台标识**：这类案例以 `sourcePlatform = CMBT_AITEST` 推送，与其它来源（testAgent / testAgentMA）分开批次，不影响原有案例。
3. **推送去前缀**：请求里的 `sourceId` 去掉 `MBT` 前缀，只发送后面的 32 位；本地文件中的 `testcase_id` 与编辑器界面显示保持完整 `MBT...` 值不变，大小写与字符均不改写。
4. **删除去前缀**：删除线上案例（含删除确认、实际删除两步）时同样使用去前缀的 `sourceId`，与线上存储口径一致；本地文件与界面仍保留完整 `MBT...` 值，删除后的本地快照按显式删除结果清理（不再生成自动追踪的已删除行）。
5. **埋点去前缀**：发往线上埋点网关的事件属性中，凡携带 testcase_id 明细（删除行 ID 列表等）也去掉 MBT 前缀，与线上按 sourceId 审计的口径一致；计数仍按原始条数统计。
6. **结果回写不串位**：推送成功回写的案例编号、失败标记与高亮、错误行号定位，一律按本地原始完整 `MBT...` ID 匹配，不因线上 `sourceId` 去前缀而丢失或串到其它行。
7. **MBT 打标**：案例表格中 MBT 案例的 `testcase_id` 单元格前显示红色 `MBT` 标识，与其它来源案例（含 TA 掩码标识）一眼可区分；该标识只作展示，不改变数据、不影响复制 / 搜索 / 筛选。
8. **只读冻结**：MBT 案例在表格中仅「案例路径」列可编辑，其它所有字段只读；步骤明细弹窗内容与添加/删除/复制/移动按钮全部冻结，展开步骤子表格中的编辑与操作按钮同样冻结。整行删除仍保留可用（走既有线上删除链路）。任何被冻结的编辑入口统一提示「MBT业务关键案例，不允许在端到端流程中修改。」。
9. **历史标记清理**：此前因格式校验被标红的 MBT 案例失败标记，在读取时自动过滤清除，升级后不再显示过时的红格。

### 使用预期
- 含 MBT 案例的文件，打开与推送前校验不再报「testcase_id 的值不符合案例唯一标识规范」；表格中该案例的 ID 前带红色 `MBT` 标识。
- 推送成功后，MBT 案例与其它案例一样正常回写案例编号，失败时对应行正常标红、行号准确。
- 删除 MBT 案例与删除其它案例体验一致；线上按去前缀 ID 命中（确认与删除两步均是），本地快照按显式删除结果同步清理。
- MBT 案例在编辑器中只有案例路径可以修改，其它字段双击 / 粘贴 / 批量填充 / 查找替换均被拦截并提示业务文案；步骤明细弹窗与展开子表只读，整行删除不受影响。
- 升级前遗留的 MBT 格式错误红格，再次打开文件后自动消失。

### 补充说明（已确认方案与约束）
- MBT ID 规则为严格大写前缀 + 32 位小写字母数字，不加大小写 insensitive 匹配；前缀或后缀大小写不符、长度不是 32 位、含非法字符的一律不放行。
- 去前缀只作用于「发往线上的 sourceId / testcase_id」（推送、删除确认、删除动作、埋点事件属性），属于输出层规范化，本地文件与内存行对象始终是原始完整值，重复推送不会产生不同 sourceId；埋点计数仍按原始条数统计。
- 接口回显的 `sourceId` 为去前缀值，解析时按请求顺序反查映射回本地完整 ID，保证失败盘、前端高亮、案例编号回写、行号定位等所有以本地 ID 为键的链路一致。
- 平台分流在读原始 ID 阶段完成（MBT 前缀仍可见），先判平台再去前缀；三批来源互不混批。
- 不再维护 MBT 相关的专用伪 tsId 或独立校验机制，复用既有格式校验、拆批、响应解析与失败盘链路。
- 表格打标复用既有 `testcase_id` 单元格徽标机制（与 TA 掩码标识同一套样式，MBT 用红色变体），仅在展示层按 ID 值判断，不写入数据、不进入失败盘；与「校验失败」红格语义区分，二者可独立出现。
- 只读冻结复用既有样例行冻结框架：扩展冻结判定按单元格区分（MBT 行仅路径列例外），主表双击/粘贴/清空/批量填充/列操作/查找替换、展开子表、明细弹窗写入入口全部经同一判定；整行删除不走单元格冻结，保持既有线上删除能力。冻结提示文案统一为「MBT业务关键案例，不允许在端到端流程中修改。」。

## F8. 移除「已删除行」自动追踪与展示，避免 `testcase_id` 变化被误判为删除

### 用户场景
用户在案例编辑器中修改某行的 `testcase_id`（例如修正 ID、重新生成 ID，或 MBT 案例相关 ID 调整）后，表格下方出现「已删除 N 行」区域，并把变化前的旧 ID 当作被删除行展示成灰色/删除线占位行，但用户实际上并未删除任何行。同时，工具栏的「仅看已删除行」筛选和命令面板的「同步已删除行」入口也不再使用。

### 需求
1. **移除自动追踪**：不再根据快照差异自动推断「已删除行」；`testcase_id` 变化不再生成已删除行记录，也不再在表格下方显示旧 ID / 旧行内容。
2. **移除展示与筛选**：表格底部不再渲染幽灵行与「已删除 N 行」分隔区；工具栏不再提供「仅看已删除行」按钮，查找替换、推送结果定位、筛选计数等逻辑一并移除该筛选维度。
3. **移除命令入口**：命令面板不再提供「同步已删除行」命令，对应处理器与入口移除；不再允许用户手动触发一次全量已删除行同步。
4. **保留显式删除能力**：右键删除行、F7 删除案例文件（含 MBT 案例整行删除）仍调用线上删除接口，确认提示、删除结果反馈与本地快照清理保持原行为，不因移除自动追踪而退化。
5. **埋点口径兼容**：保存 / 推送结果中的删除行数统计字段保留，但因不再自动检测删除，恒为 0；显式删除行为与结果埋点保持不变；命令式 `syncDeletedRows.*` 事件随入口下线，删除同步统计改由 `editor.deleteRows.synced` 与 `caseFileDelete.intercept.done` 承载。
6. **历史数据兼容**：`deleted-rows.json` 与推送快照中的历史已删除记录不再用于前端展示；孤儿记录清理与显式删除成功后的清理逻辑保留，避免升级后残留脏数据。

### 使用预期
- 修改任意行的 `testcase_id` → 表格下方不再出现「已删除行」区域，旧 ID 不再以幽灵行形式出现。
- 编辑器工具栏不再显示「仅看已删除行」按钮；命令面板不再出现「同步已删除行」。
- 右键删除行 / F7 删除案例文件 → 线上删除与确认提示保持原行为，删除结果反馈不受影响。
- 保存 / 推送统计里删除行数为 0；删除相关用户行为埋点仍正常记录实际删除动作。
- 命令式同步删除埋点不再产生；删除同步频次 / 成功数 / 失败数在编辑器删行与文件删除结果事件中统计。

### 补充说明（已确认方案与约束）
- 根因：旧逻辑按 `testcase_id` 集合差集判断删除，ID 变化会让旧 ID 从快照键集合中消失，被误判为删除并渲染成幽灵行。
- 采用方案 B：只移除自动追踪及展示 / 筛选 / 命令入口，不改动显式删除执行原语；线上删除链路继续复用既有删除接口。
- 前端不再维护已删除行状态与幽灵行渲染，后端差异计算不再产出或下发 `deletedInfos`；二者一一对应，避免一端移除另一端残留导致旧索引错位。
- 本地显示值与线上 `sourceId` 口径互不影响：本地文件与界面仍保留原始完整 ID，去前缀只作用于发往线上的推送 / 删除 / 埋点字段。

## 附：统一约束小结

- **非案例文件永不参与推送**，仅在门控视图与汇总视图中以灰色「已跳过」行呈现，标注"不含 testcase_id"；点击该行仅打开文件供查看，不弹推送结果。
- **进入汇总的判定**：选择条目数 > 1，或任一选择条目为文件夹。满足其一即走批量汇总；仅"单选一个案例文件（非文件夹）"走编辑器内结果弹窗。
- **不堆叠**：批量流程中的非案例去向一律由汇总/门控的灰色行承载，仅在"全是非案例且无批量面板承载"的极窄场景才用一次性页内浮层兜底，该场景无后续结果层、不会堆叠。
- **全跳过中性呈现**：汇总结果全部为「已跳过」时使用中性灰状态，避免误导为推送成功。
- **案例路径合法性前置校验（F5）**：推送前查询每个案例路径在线上是否存在及其类型，命中「功能条目 / 非末级测试要点 / 测试要点不存在」三类非法路径时，以失败行拦截并提示具体原因，阻断本次推送；未绑定测试任务或接口异常时降级跳过，不阻断正常推送。
- **MBT 案例（F7）**：严格大写 MBT + 32 位小写字母数字的 ID 校验放行并按 `CMBT_AITEST` 平台推送；推送、删除、埋点发往线上的 `sourceId` / testcase_id 均去掉 MBT 前缀，本地文件与界面保留完整 ID 并显示红色 MBT 打标；接口结果回写按本地完整 ID 定位；编辑器中仅案例路径可改、其余字段冻结（整行删除不受限），历史格式错误标记读盘时自动清理。
- **已删除行功能（F8）**：移除自动追踪、幽灵行展示、「仅看已删除行」筛选与命令入口；`testcase_id` 变化不再误判为删除；线上删除仅保留右键删行 / F7 文件删除等显式入口，删除行数统计恒为 0；命令式同步埋点下线，删除同步统计改由编辑器删行 / 文件删除结果事件承载。
