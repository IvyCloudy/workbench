# 案例编辑器「校验」技术设计（非需求）

> **功能定位（新增）**：本文档覆盖的「案例编辑器校验」能力，是测试案例体系（含「新增测试案例」「推送 TMS」「要点-案例关联」「删除案例」等能力）上**全新新增**的"编辑器内案例合法性校验"能力，补齐"编辑期自查 → 推送前拦截"的本地质量防线，将高频推送失败前移到编辑期。校验能力自 `v1.0` 基线起生效，为独立新增模块，非对既有 YAML 修复的替代。

> **文档范围与需求对应**：本文档为「案例编辑器校验」的**技术设计**，对应需求文档 `案例编辑器校验功能需求.md`；「单元格级一键修复」为独立功能（当前未实现），其设计另行成册，不在本文档范围。

> 文中涉及的函数名（如 `collectRowIssues` / `handleValidate` / `validateRow`）均指**目标形态**，不代表当前代码已存在。需求约束以需求文档第 3 章为准。
> 状态约定：`待实现` = 尚未编码；`已实现` = 已在代码中落地（见需求文档 §7 对照）。

## 0. 功能设计总览（做什么 / 功能清单）

> 本章节为"功能层设计"，回答"本次新增要做哪些功能、每个功能如何设计与流转"；其后的 §1~§5 为"技术实现层"（基础设施 / 数据结构 / 实现骨架 / 实施顺序），两者上下呼应。所有功能均为 `v1.0` 基线新增，非对既有 YAML 修复的替代。

### 0.1 设计目标
1. **编辑期自查**：打开 / 编辑防抖 / 手动触发即可发现行级字段错误，将高频推送失败前移到编辑期。
2. **精确定位**：每个问题精确到 `[row, col]` 单元格，展示中文列名 + 原因，一键定位。
3. **与推送预校验一致**：编辑期校验与推送前本地预校验共用同一份字段约束（以推送预校验为唯一权威源），"校验通过"即代表"推送不会因行级字段错失败"。
4. **不阻断**：任何异常降级继续，绝不阻断编辑 / 删除 / 文件操作。
5. **只定位不修复**：确定性可修复问题由独立的「一键修复」功能承接（当前未实现），本文档校验部分只做定位、展示与引导。

### 0.3 各功能详细设计

#### F1 工具栏「校验」按钮（手动校验）
- **触发**：点击工具栏「校验」按钮（`id="validateBtn"`，置于「推送」旁）/ 命令面板格式校验命令。
- **输入**：当前已加载表格数据（`ctx.session.cachedTableData.rows`），无需重新解析。
- **处理**：`handleValidate` → 遍历非样例行 → `collectRowIssues` 收集 `CellIssue`（跳过样例行）→ 回推 `validateResult`。
- **输出**：结果面板列出问题（`行号·中文列名·原因·级别`）；无问题提示"校验通过，可推送"；空表 / 仅样例行提示"无可校验数据行"。
- **范围**：默认全表，不受前端过滤视图影响；与推送预校验共用同一份字段约束。
- **异常**：解析失败 / 竞态不阻断；同一文件重复打开有序列 / 抑制保护，避免重复弹窗。
- **埋点**：编辑期 `manualValidation.*`（见埋点需求 §4.11）。

#### F2 单元格级问题定位
- **触发**：校验结果回推后前端处理 `validateResult`。
- **处理**：每条 `CellIssue.field` 经 `headerLabels` 映射 `col`；找不到列降级**整行高亮 + 面板标注"列缺失"**；构造 `highlightedCells.cells:[row,col]` 红底；结果面板每条带「定位」按钮滚动聚焦。
- **输出**：精确红底 + 中文列名原因 + 定位跳转；同格多条问题聚合为一条展示。
- **异常 / 降级**：列映射失败不静默丢弃问题（对策见需求文档 §5.2）。

#### F3 不可修复项（C 类）引导
- **触发**：结果面板渲染 C 类问题（语义不符 / 需业务判断）。
- **处理**：仅显示「定位」+ 原因 + **建议值文案**，不显示「修复」按钮、不写盘。建议值来自静态话术（枚举非法列白名单、步骤/预期缺失给通用提示），由系统枚举白名单生成。
- **输出**：建议值仅展示，不触发任何写盘。

#### F4 编辑期自动校验
- **触发**：文件打开（`triggerEditValidationOnWebviewOpen`）/ 编辑防抖（`postEditValidationRefresh`，CSV 800ms、YAML·JSON 500ms、>512KB 大文件 1500ms）。
- **处理**：打开即跑文件级缺列 + 行级失败弹窗（代号 05g）；编辑后防抖重跑刷新高亮与状态，**不重复弹窗**。
- **输出**：写入 `push-failures.json` 供渲染；打开弹窗经 `postFileLevelPreValidateGate`。
- **降级 / 抑制**：解析失败 / 竞态不阻断；重复打开有抑制 / 序列保护。

#### F5 推送前预校验与门控
- **触发**：点击「推送」进入 `runPush` 前 `stepPreValidate`。
- **预校验类型（9 类）**：缺失必填列、占位 `TESTCASE_ID`、空 `testcase_id`、格式非法、枚举非法、计划执行次数非法、名称空、同文件重名、内容含「待补充」软拦截。
- **拦截语义**：error 级（占位/空/格式/枚举/计划执行次数/名称空/重名）→ 对应行从 payload 剔除；warn 级（「待补充」）→ 不剔除、仅高亮；结构性缺列 → 所有行剔除、推送短路。
- **门控**：error 级 → `preValidateGateBlocked` 阻断（仅「关闭」）；warn 级 → 弹确认，「取消」=`preValidateGateCancelled` / 「忽略并继续」放行。
- **一致性**：与编辑期校验共用同一份字段约束（推送预校验为权威源）。

#### F6 单元格高亮持久化
- **触发**：校验结果产出后。
- **着色**：error 红底 / warn 黄底，按 `field`/`[row,col]` 精确染色。
- **持久化**：写入 `globalStorageUri/push-failures.json`（文件绝对路径为 key）；编辑 / 推送 / 重开时重新加载覆盖旧标记。
- **输出**：关闭 / 重开 / 重启 VSCode 后高亮不丢失。

> 埋点：校验全流程 `editValidation.*`、推送前 `${telemetryPrefix}.*`、门控 `.aborted` 按埋点需求文档 §4.11 上报，且含 `columns`（有问题列名）维度。

## 2. 核心数据结构

```ts
// 后端校验产出（handleValidate 回推给前端）
interface CellIssue {
  row: number;          // 0-based 数据行下标
  field: string;        // 英文 key，如 'testCaseName'（前端据此映射 col，后端不持有列序）
  category: string;     // 错误分类，对齐 pushFailureCategory 的 category
  reason: string;       // 短标签，如 'empty' / 'invalidEnum' / 'format' / 'missing'
  message: string;      // 用户友好文案
  suggestion?: string;  // C 类给出的建议值文案（不自动写入，见需求 §3.3）
}
// 注：col 不在结构中；前端用 headerLabels 将 field 映射为 col 后再构造 highlightedCells.cells。
```

## 3. 校验项与字段约束详细设计

> 编辑期校验与推送前预校验（F5 / 需求 §3.5）共用同一份 `collectRowIssues()` 行级字段约束（以推送预校验为唯一权威源）。本节列出各校验项的判定规则、错误分类（`category`/`reason`）与拦截语义（`error` 剔除 vs `warn` 不剔除）。字段约束来源：推送侧 `pushDataMapper.mapRowToCaseItem` 的必填/长度/枚举/格式约束 + `pushCore.stages.ts` 的 `DEFAULT_VALIDATORS` / `FIELD_LEVEL`（见 §1）。

### 3.1 校验项总览（含样例行跳过）

| 类别 | 校验项 | 判定规则 | 级别 | 拦截语义 |
|---|---|---|---|---|
| 范围 | 样例行跳过 | `testcase_id` 为占位（如 `TESTCASE_ID`）整行跳过 | — | 不计入问题 |
| 文件级 | 缺必填列 | 必填列（标识、名称、案例类型、执行方式、优先级、关键案例等）任一缺失 | error | 所有行剔除、推送短路 |
| 必填 | 标识为空 | `testcase_id` 为空 | error | 该行剔除、不推送 |
| 必填 | 名称空 | `testCaseName` 为空 | error | 该行剔除、不推送 |
| 格式 | 标识格式非法 | `testcase_id` 不符合格式规则（正则/前缀等） | error | 该行剔除、不推送 |
| 枚举 | 案例类型非法 | `type` 不在白名单（13 项，见需求枚举白名单） | error | 该行剔除、不推送 |
| 枚举 | 执行方式非法 | `test_type` 不在白名单；支持简写 `接口`→接口自动化、`界面`→UI自动化（大小写不敏感归一） | error | 该行剔除、不推送 |
| 枚举 | 优先级/关键案例非法 | `priority` ∉ {高/中/低}；`key_flag` ∉ {是/否} | error | 该行剔除、不推送 |
| 数值 | 计划执行次数非法 | `planExecCount` 非非负整数（负数/小数/非数字） | error | 该行剔除、不推送 |
| 唯一 | 标识重复 | 同文件内 `testcase_id` 重复 | error | 重复各行列均剔除、不推送 |
| 软拦截 | 待补充占位 | 内容含 `待补充`/`TODO` 等占位 | warn | 不剔除、仅黄底高亮，可忽略继续 |

### 3.2 空校验（必填项）
- `testcase_id`（标识）、`testCaseName`（名称）为强必填；任一为空 → `category='required'` / `reason='empty'`，error 级，对应行从推送 payload 剔除。
- 判定复用 `mapRowToCaseItem` 内部 `fieldOrDefault` 的空值判断，与推送预校验一致，不另立规则。

### 3.3 枚举校验
- **案例类型**：`type` 须 ∈ 白名单（13 项，见需求 §3 枚举白名单）；非法 → `reason='invalidEnum'`。
- **执行方式（test_type）**：须 ∈ 白名单；支持同义词/简写归一：`接口`→`接口自动化`、`界面`→`UI自动化`，归一在 `resolveTestType` 层完成（大小写不敏感）；归一后仍不在白名单 → error。
- **优先级/关键案例**：`priority` ∈ {高/中/低}、`key_flag` ∈ {是/否}；非法 → error。
- 枚举白名单以系统级定义为唯一来源（推送预校验同款），校验侧只读复用，不自行硬编码，保证双入口一致。

### 3.4 缺列校验（文件级）
- **判定**：文件表头缺失任一必填列 → 文件级 error。
- **双入口一致影响**：
  - 编辑期（F4）：打开文件即跑文件级校验，触发弹窗（代号 05g）提示缺列；缺失列所在相关单元格以整行/标注方式高亮，面板标注「列缺失」（见 §2 `CellIssue` 缺列降级）。
  - 推送前（F5）：结构性缺列 → 所有行剔除、推送短路，不发出任何后端请求（`stepPreValidate` 短路，reason 含缺失列名）。
- 列缺失时单元格级 `field→col` 映射必然失败，故该文件所有行降级为整行高亮（F2 降级策略）。

### 3.5 其他校验项
- **格式（标识）**：`testcase_id` 不符合格式规则（前缀/长度/字符集）→ `reason='format'`，error。
- **数值（计划执行次数）**：`planExecCount` 须为非负整数；负数、小数、非数字均 → error。
- **唯一性（重名）**：同文件内 `testcase_id` 重复 → 重复各行列均标 `reason='duplicate'`，error；修正为互不相同后通过。

### 3.6 软拦截 / 警告（不阻断）
- 内容含 `待补充`/`TODO` 等占位 → `category='warn'` / `reason='placeholder'`，**warn 级**：不剔除、仅黄底高亮；推送门控（F5）弹确认，可「取消」或「忽略并继续」。
- C 类（语义类，需业务判断）仅定位 + 建议值文案，不自动修复（见 F3）；建议值按来源细分：
  - **枚举非法但非别名**（如 `testType` 拼错）：建议值 = 枚举白名单列表（如「建议改为：手工 / UI自动化 / 接口自动化 / 自动化」），**静态话术由系统枚举白名单生成**；
  - **步骤 / 预期缺失**：建议值 = 通用补全提示（如「建议至少补充一个步骤」），**静态话术**；
  - **语义数量不一致**（预期数 ≠ 步骤数）：**仅给提示文案，不计算具体建议值**（见需求 §3.3）。

### 3.7 与推送预校验的一致性
- 编辑期 `collectRowIssues` 与推送前 `stepPreValidate` 调用**同一份**行级字段约束函数，避免「校验通过但推送仍失败/驳回」。
- 任一侧新增/修改字段约束，须同步另一侧（需求 §3.7 一致性要求）；新增校验项须在 `DEFAULT_VALIDATORS` / `FIELD_LEVEL` 中登记，校验与推送自动继承。

### 3.8 字段级校验要求矩阵（不同字段要求不一致）

> 各字段的校验严格度并不一致：标识 / 名称 / 枚举 / 数值属**硬约束**（error，推送必失败，须修）；部分字段属**软约束**（warn，可忽略继续）；接口级字段本地**无法校验**（边界，需推送后才发现）。下表逐字段列出差异，供实现与评审核查（字段码以 `headerLabels` 为准）。

| 字段 | 必填 | 校验类型 | 级别 | 本地可校验 | 特殊约束 |
|---|---|---|---|---|---|
| `testcase_id`（标识） | 是 | 空 / 格式 / 唯一 | error | 是 | 冻结列只读；样例行占位（`TESTCASE_ID`）跳过；推送 payload 主键 |
| `testCaseName`（名称） | 是 | 空 | error | 是 | — |
| `type`（案例类型） | 是 | 枚举（13 项白名单） | error | 是 | 非法 → `invalidEnum` |
| `test_type`（执行方式） | 是 | 枚举（含简写 `接口`→接口自动化、`界面`→UI自动化 归一） | error | 是 | 归一在 `resolveTestType` 层，大小写不敏感 |
| `priority`（优先级） | 是 | 枚举（高 / 中 / 低） | error | 是 | — |
| `key_flag`（关键案例） | 是 | 枚举（是 / 否） | error | 是 | — |
| `planExecCount`（计划执行次数） | 是 | 数值（非负整数） | error | 是 | 负数 / 小数 / 非数字 → error |
| `description` / `expected` / `testCaseDes` 等 | 否 | 软校验（待补充占位） | warn | 是 | 含 `待补充` / `TODO` → 黄底，可忽略继续；步骤 / 预期缺失属 C 类仅提示不修 |
| `designer` / `artifactId` / `sourcePlatform`（接口级） | 是（后端） | 本地不可校验 | —（仅提示边界） | **否** | 仅后端可判定，须在面板提示「校验通过 ≠ 一定推送成功」 |

> 说明：硬约束字段由 `collectRowIssues` / `stepPreValidate` 统一收集；软约束字段不阻断推送但参与高亮；接口级字段的缺失 / 错误只能由推送后置发现，属已知边界（需求 §5.1）。

### 3.9 触发场景设计（文件打开 / 推送 / 批量推送）

#### 3.9.1 文件打开（编辑期自动校验入口）
- **触发**：文件在编辑器打开（`triggerEditValidationOnWebviewOpen`）。
- **流程**：① 文件级缺列检测（`detectMissingColumns`）→ 若缺失必填列，整文件标记文件级 error 并在面板标注缺列；② 行级失败收集（`collectRowIssues` 全表，跳过样例行）构造 `CellIssue`；③ 写入 `push-failures.json` 供渲染红 / 黄底；④ 弹窗（`postFileLevelPreValidateGate`，代号 05g）展示，**不阻断打开**。
- **特点**：仅弹一次（序列 / 抑制保护，重复打开不重复弹）；解析失败 / 竞态不阻断；编辑后仅刷新高亮而非重复弹窗（见 §0 F4 与操作指引 Q1）。

#### 3.9.2 单文件推送前预校验（`stepPreValidate` 入口）
- **触发**：点击「推送」进入 `runPush` 前 `stepPreValidate`。
- **流程**：① 复用与 3.9.1 同一份 `collectRowIssues` / `detectMissingColumns`；② 逐行判定 error / warn；③ error 级行从 payload 剔除、warn 级保留；结构性缺列 → 全部行剔除 + 推送**短路**；④ 门控：error → `preValidateGateBlocked` 阻断（仅「关闭」）；warn → 弹确认（「取消」=`preValidateGateCancelled` / 「忽略并继续」）。
- **一致性**：与 3.9.1 共用约束，确保「校验通过即推送不因此失败」（需求 §3.7）。

#### 3.9.3 批量推送多文件
- **触发**：批量推送（多选文件 / 多案例推送）时，对每个目标文件逐一执行预校验。
- **逐文件流程**：对每个文件重复 3.9.2 的 `stepPreValidate`；单文件内 error 级行剔除、缺列短路。
- **聚合与隔离策略**：
  - **文件级隔离**：某文件存在 error 级失败 → 该文件整体不参与推送（门控阻断），但**不自动阻断其他无错文件**（隔离粒度以推送侧批量逻辑为准），最终聚合成「成功文件 / 失败文件」清单。
  - **缺列文件短路**：结构性缺列文件直接整文件剔除，不发出后端请求。
  - **部分失败呈现**：结果清单标注失败文件原因（缺列 / error 级行数）；仅含 warn 的文件弹确认可整体「忽略并继续」。
- **埋点**：批量场景 `${telemetryPrefix}.missingColumnsDetected` 及 `.xxxSkipped` 按文件聚合上报（需求 §3.7）。

#### 3.9.4 边界与特殊场景
- **过滤视图叠加**：校验基于**全量数据行**（不受前端「仅看失败行」等过滤视图影响）；结果面板可与过滤视图叠加显示，但定位 / 高亮仍作用于全量中命中单元格，不限于可见行（避免隐藏行漏判，见需求 §5.1）。
- **空表 / 仅样例行**：文件为空或所有数据行均为样例行（`testcase_id` 占位）时，点「校验」应提示「无可校验的数据行（均为样例行或文件为空）」，而非空面板或报错（见需求 §5.1、§6 验收）。
- **编辑防抖档位**：编辑后防抖触发重跑的延迟为 CSV 800ms / YAML·JSON 500ms / 大文件（>512KB）1500ms（见 §0 F4）；防抖期间仅刷新高亮与状态，不重复弹窗。

### 3.10 风险与对策（对应需求 §5.2）

| 风险 | 对策（设计落点） |
|------|----------|
| 列映射失败导致问题丢失 | 前端 `field→col` 反查失败时降级为整行高亮 + 面板标注「列缺失」，不静默丢弃（§3.4 / §4.2） |
| 校验规则与推送不一致 | 校验与推送预校验共用同一份 `collectRowIssues` 字段约束（以推送预校验为权威源），单方改动需同步（§3.7） |
| 隐藏行 / 过滤视图下误判 | 基于全量数据行校验与高亮，不区分可见性（§3.9.4） |
| 冻结行 / 列被误标 | 校验定位沿用既有冻结行 / 列约束，冻结列（如 `testcase_id`）不参与编辑校验写回（§3.8） |
| 编辑防抖重复弹窗 | 打开弹窗有序列 / 抑制保护，编辑后刷新经 `postEditValidationRefresh` 重绘而非重复弹窗（§3.9.1） |

## 4. 关键实现骨架

### 4.1 后端 handler

```ts
// editorMessageHandlers.ts —— buildHandlers() 新增一项
validate: handleValidate,

async function handleValidate(_msg, ctx) {
  // 1. 取缓存的当前文件表格数据（无需重新解析）
  const rows = ctx.session.cachedTableData?.rows ?? [];
  // 2. 复用 collectRowIssues 跑全量校验（跳过样例行）
  const issues: CellIssue[] = [];
  rows.forEach((row, i) => {
    const tsId = row[TS_ID_COLUMN];
    if (tsId && isSampleTsId(tsId)) return;   // 样例行跳过
    issues.push(...collectRowIssues(row, i));
  });
  // 3. 下发结果：问题清单（col 由前端映射）
  ctx.webviewPanel.webview.postMessage({
    type: 'validateResult',
    issues,
  });
}
```

### 4.2 前端改动点

1. **`index.html` 工具栏**：新增「校验」按钮 `id="validateBtn"`（置于「推送」旁）。

3. **结果面板**：复用编辑器现有结果弹窗结构（代号 05g），每条问题带「定位」按钮 + 「重新校验」入口（「重新校验」复用同一 `validate` 消息通道，即全表校验）。
