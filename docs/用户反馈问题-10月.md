| F6 | 案例编辑器与推送链路上的遥测事件多以 `fileFormat` 维度为主，缺少"文件名"维度，线上难以按文件定位高频出错的具体文件（如某 csv 反复解析失败、某 yaml 推送频繁超时），只能靠用户手动反馈截图 | 在所有关键遥测事件中统一补充 `filePath`（仅文件名 basename，按脱敏约定不上报绝对路径）维度，使研发能在遥测后台按"文件"聚合定位问题；纯字段扩充，不改变任何业务功能与用户行为 |

## F1. 案例文件删除时，只有样例文件会删除失败

### 用户场景
用户通过命令在 `测试任务/<任务>/测试案例/` 下新建了一个案例文件。新建出的文件里按约定带了一行示例数据（样例行），样例行的「案例标识」列是一段占位文案（如"案例唯一标识，不可修改""TESTCASE_ID"），并不是真实推送后拿到的 `testcase_id`。

用户还没往里填真实用例、也没推送过，就直接想把这个刚建好的空壳文件删掉（资源管理器右键删除、或选中整目录删除）。

用户反馈的问题：
- 删除时提示失败 / 被卡住，文件删不掉。
- 明明文件里没有一条"真正的线上案例"，却要走删除确认、预检或线上同步，最后因为样例占位的标识不是合法线上 id 而失败。
- 用户预期：一个只有样例、从没推送到过 TMS 的文件，删它就该像删普通本地文件一样直接成功，不应该失败。

### 需求
1. 案例文件的「案例标识」列只含样例占位（非空但非真实线上标识）、没有任何真实推送案例时，应被判定为"无需线上操作"，走与"全部本地未推送行"一致的**仅本地删除**路径（即 `hardDeleteOnly` 语义），直接物理删除成功。
2. 仅含样例占位行的文件删除时：
   - 不触发删除确认接口的预检；
   - 不弹"同步删除 TMS 平台案例"类的确认（或按全 `type=3` / 仅本地口径跳过确认）；
   - 不因样例占位的标识无法在 TMS 校验而判定为删除失败或预检失败；
   - 批量删除中整批"仅样例 / 仅本地"时，不弹确认窗、直接放行删除。
3. 该判定口径与编辑器内删除、案例文件删除拦截、批量 / 文件夹删除三条路径统一：都以「案例标识列是否"存在且非空且非样例占位"」为是否已推送的判断标准。

### 使用预期
- 新建的、只含样例行的案例文件，在资源管理器右键删除 → 直接本地删除成功，不弹任何确认、不报失败。
- 删除前已用编辑器打开该文件时，删除后不残留"删除中"灰色态，不卡住。
- 批量删除里混有"仅样例文件"与"有真实线上案例的文件"时：仅样例文件按本地删除直接放行（批量确认弹窗里标记为"仅本地删除"），需要同步 TMS 的文件照常走确认 + 预检 + 同步流程；整批仅由样例 / 本地文件构成时，不弹确认窗直接删除。
- 注意：判定依据的是"案例标识列是样例占位文案"，而不是"文件名里带样例二字"。一个确实推送过、案例标识是真实 `testcase_id` 的文件，即便文件名叫 `样例.csv`，仍按正常已推送案例走同步删除，不会误删。

### 补充说明（已确认方案与约束）
- 方案对齐：该需求复用 `docs/requirements/删除案例功能需求.md` 中已定义的"样例占位不触发线上删除"与 `hardDeleteOnly` 分档规则——"仅含样例占位"与"无案例标识列 / 空文件 / 全部行标识为空"同属"无需线上操作"，应直接放行物理删除而非失败。
- 关键修复点：当前删除逻辑在文件级预检 / 是否已推送判断上，可能把样例占位行当成"待同步的待删案例"带入预检或执行接口，导致样例标识在 TMS 校验阶段失败、整文件被判定为预检失败而保留不删。须确保"样例占位 = 非已推送"这一判断在**备份前的首次解析阶段**就生效：非空标识列表为空（仅样例占位或全空）即判定为无需线上操作、直接放行，不再进入预检 / 同步链路。
- 口径一致性：编辑器内删除（`skipConfirm` / 基础确认）、案例文件删除拦截（单文件 / 批量 / 文件夹）、要点删除关联清理，三路径共用同一"样例占位判定"函数与同一 `hardDeleteOnly` 计算口径，避免"编辑器内能删、文件级删不了"或反之的口径分裂。
- 验收可参考 `docs/requirements/删除案例功能需求.md` §4 第 8 条（本地未推送行不调接口）、第 37 条（批量整批无 TMS 交互跳过确认窗）的既有判定，并将其扩展到"仅含样例占位"这一等价情形。

## F2. 批量删除未绑定测试任务的案例文件时，只需一条"谨慎操作"提示，无需逐个文件确认

### 用户场景
用户在工作区里新建了一批案例文件，但其中很多还没"绑定测试任务"（比如通过命令新建后还没关联任务、或放在不属任何任务的目录下）。用户想一次性批量删掉这批未绑定任务的文件。

用户反馈的问题：
- 批量删除 (N≥2) 时，每个未绑定任务的文件在聚合确认弹窗里**各占一个 Tab**，且弹窗要求"所有 Tab 都要被查看过"才能点确定——等于要**逐个文件查看 / 确认**一遍，文件一多非常繁琐。
- 这些文件本来就是"仅本地删除、不同步 TMS"，风险比"同步删除线上案例"低得多，却要为每个文件走一遍确认流程，体验割裂、效率低。
- 用户预期：删一批未绑定任务文件，弹**一条**"谨慎操作"提示说清楚"以下文件均未绑定测试任务，仅删除本地、不同步 TMS 平台，确认吗？"即可，不用一个文件一个文件地点。

### 需求
1. 批量删除（N≥2）中，所有"未绑定测试任务"的文件应**聚合为一条整体提示**，而非每个文件一个独立 Tab / 逐个确认：
   - 弹窗顶部风险卡片统一提示"N 个文件未绑定测试任务，仅本地删除、不同步 TMS"；
   - 把这批未绑定文件归为一个分组（单个可勾选/确认的整体项），用户确认一次即对该批全部未绑定文件生效，**不要求逐个 Tab 强制查看**。
2. 确认该整体提示后，这批未绑定文件统一按"仅本地删除"直接物理删除（不调预检 / 不调 TMS 删除接口），删除结果与其它文件一起并入批量汇总面板。
3. 单文件（N=1）删除未绑定文件的既有"谨慎操作"简单确认（导语"仅本地删除、不会同步 TMS"，按钮"继续删除"）保持不变。

### 使用预期
- 批量删 10 个未绑定任务的文件（通常就是删一个未绑定任务的文件夹）→ 弹窗里这 10 个文件合并为一条"仅本地删除"整体提示（含文件清单），用户点一次"继续删除"即全部本地删除，无需逐个 Tab 查看。
- 删除结果在批量汇总面板统一回显（未绑定文件计入"仅本地删除"分档）。
- 注意：本需求只改变"未绑定文件"的批量确认聚合方式（从逐 Tab 改为整体一条提示），不改变其"仅本地删除、不同步 TMS"的业务语义，也不影响真正"已绑定任务且需同步"文件的逐条 / 关联案例确认强度。

### 补充说明（已确认方案与约束）
- 方案对齐：本需求复用 `docs/requirements/删除案例功能需求.md` §3.2 中"未绑定任务（unbound）→ 仅本地删除、不调线上接口"的既有语义，仅把**批量场景下的呈现粒度**从"每个文件一个 Tab、强制逐个查看"收敛为"整批未绑定文件一条整体提示"。
- 与 `hardDeleteOnly`（无 testcase_id / 仅本地）、`type=3`（从未推送 TMS）的关系：三者都属于"无需线上操作"的本地删除分档，在批量弹窗里本就已是风险较低的一类；本需求进一步为其中的"unbound"分档补足"整批聚合、一次确认"的体验，使未绑定文件不再因逐 Tab 强制查看而显得与更高风险的 TMS 同步文件一样繁琐。
- 强制查看约束的取舍：既有弹窗的"三重防误删"中"强制查看所有 Tab"是为防用户漏看"同步 TMS 的关联案例"而设；未绑定文件无关联案例、无线上同步风险，对其放宽强制查看、改为整体提示，不会削弱对真正高风险文件的防护。
- 验收可参考 `docs/requirements/删除案例功能需求.md` §4 第 35 条（文件删除-测试任务未绑定仅本地删除）、第 37 条（批量整批无 TMS 交互跳过确认窗）的既有判定，并将其扩展到"批量未绑定文件聚合为一条整体提示"这一体验要求。

## F3. 测试要点文件删除：无测试要点的文件不应被整体拦截，应按"仅本地删除"处理

### 用户场景
测试要点文件（位于 `测试任务/<任务>/测试大纲/` 下的 `.md` / `.xmind`）内部由"功能条目"节点组织，功能条目下挂"测试要点节点"（如带五角星图标的测试点）。用户删除这类文件（资源管理器右键删除，或选中整个测试大纲目录批量删除）时，有些文件其实是"空壳"——里面只有功能条目、但功能条目下没有任何测试要点节点（或整文件根本没解析出任何测试要点）；还有一类文件既不包含任何任务功能条目、也不包含任何测试要点（完全空壳），这些文件同样没有可同步的测试要点。

用户反馈的问题：
- 文件里只要存在"无测试要点节点的功能条目"，当前就会**拦截整个测试要点文件**、不让删除，用户只能先改文件、补齐测试要点节点才能删，体验很卡。
- 用户预期：一个没检测到任何测试要点的文件，删它就该像删普通本地文件一样，本地删掉即可，没必要因为"没有可同步的测试要点"而被整体拦住。

### 需求
1. **单个测试要点文件删除时**：先解析文件、识别其中是否包含测试要点节点；若**文件中无测试要点**（未解析出任何测试要点节点，包括"只有功能条目但无测试要点节点"以及"既无功能条目也无任何测试要点"两类空壳），则在删除确认处提示"未检测到测试要点，仅本地删除，不同步 TMS"，确认后按**仅本地删除**直接物理删除成功，不调线上同步接口、不拦截。
2. **批量删除测试要点文件时**：只有**包含测试要点**的文件才进入聚合确认弹窗的对应 tab、参与"同步删除"相关的确认；**无测试要点的文件不生成确认 tab**，直接按本地删除处理（其存在仅作为"仅本地删除"一类在弹窗/汇总中说明，不要求逐文件确认）。在批量确认弹窗的"谨慎操作"整体提示中，需**明确标明这批无测试要点、将仅本地删除的文件总数**（如"本次共 N 个测试要点文件未检测到测试要点，将仅本地删除、不同步 TMS"），让用户清楚知晓影响范围，不要求逐文件展开。
3. 无测试要点 = 仅本地删除、不同步 TMS，不影响"包含测试要点的文件"正常走同步删除与关联案例确认。

### 使用预期
- 单个测试要点文件、删除时未解析出任何测试要点 → 弹"未检测到测试要点，仅本地删除，不同步 TMS"提示，点确认即本地删除成功，不再整体拦截。
- 含"无测试要点节点的功能条目"的文件 → 同按"无测试要点"处理，本地删除成功，不再因结构上有空功能条目而被拦。
- 既不包含任何任务功能条目、也不包含任何测试要点的完全空壳文件 → 同样按"无测试要点"处理，提示后仅本地删除，放行。
- 批量删除测试大纲目录（含 3 个文件：2 个含测试要点、1 个无测试要点）→ 聚合确认弹窗仅对 2 个含测试要点的文件生成 tab 确认；第 3 个无测试要点文件直接归入"仅本地删除"处理，不占 tab、不要求逐文件确认；"谨慎操作"整体提示中标注"共 1 个测试要点文件未检测到测试要点，将仅本地删除、不同步 TMS"，让用户知悉文件总数。
- 注意：判定依据的是"文件中是否解析出测试要点节点"，而非"文件名是否带测试要点字样"。一个确实含测试要点、但因临时编辑导致某一功能条目暂空的文件，仍按含测试要点正常走同步确认，不会被误判为本地删除。

### 补充说明（已确认方案与约束）
- 方案对齐：本需求复用"删除链路里低风险文件直接本地删除"的既有语义——与案例文件删除的 `hardDeleteOnly`、测试任务未绑定的 `unbound` 同属"无需线上同步、直接物理删除"分档；区别仅在判定维度：案例文件看 `testcase_id` 是否为空 / 是否绑定任务，测试要点文件看"是否解析出测试要点节点"。
- 关键修正点：当前文件级删除流程对测试要点文件存在"含无测试要点节点的功能条目即整体拦截"的强校验，应改为"先判定是否含测试要点"——含则走同步确认、不含则降级为仅本地删除，不再以文件内的空功能条目为由整体阻断删除。
- 与"测试要点关联案例删除"（§3.4）的关系：本需求处理的是"删除测试要点文件本身"，与"在要点侧删除某测试要点、从本地案例文件移除其关联案例行"是两条不同触发路径；无测试要点的文件本就无关联案例可同步删除，因此本地删除是合理且安全的收尾。
- 验收可参考 `docs/requirements/删除案例功能需求.md` §4 第 35 条（未绑定任务仅本地删除）、第 37 条（批量整批无 TMS 交互跳过确认窗）的口径，并将其扩展为"测试要点文件无测试要点 → 仅本地删除、不进确认 tab"这一等价规则。

## F4. 通过要点删除案例文件（清空）时文件不进回收站、无法找回

### 用户场景
用户通过"测试要点"侧删除某个测试要点关联的全部案例（或若干案例）。当这些案例占满某个案例文件的全部内容、删完后该文件变空时，插件会把整个案例文件整体删除。用户关注的是：通过要点删除导致"文件被整体删掉"的那一刻，这个文件还能不能像普通删除一样从回收站找回。

（对照：用户也可能只是通过要点删掉某几个案例、文件还有剩余行——此时文件不会被整体删、只是行变少，不涉及本问题。）

### 用户反馈的问题
- 在资源管理器里直接删除案例文件时，文件会进系统回收站（废纸篓 / Recycle Bin），之后还能找回；
- 但通过要点删除、导致案例文件被整体清空删除时，文件是"直接物理删除"，不进回收站，回收站里根本找不到，一旦删掉就不可逆、无法恢复；
- 用户预期：无论用哪种方式删除，"文件被整体删掉"这件事的可恢复性应当一致——至少应该能进回收站，或提供等效的备份 / 撤销手段，而不是静默永久丢失。

### 需求
1. 通过要点删除导致案例文件整体被删除时，应与"资源管理器直接删除案例文件"在可恢复性上保持一致：文件应能进回收站（或提供等效的本地备份 / 撤销机制），用户误删后还能找回。
2. 若当前通过要点删除整体删文件走的是"直接物理删除"、不进回收站，应改造为与直接删除一致的"可恢复删除"路径（复用直接删除已有的备份 / 回收站机制），避免两条删除路径在"能否找回"上行为分裂。
3. 仅删除部分案例（文件仍有剩余行）的情形不受影响：文件不会被整体删除，仅是行减少，用户继续编辑即可，不涉及回收站问题。

### 使用预期
- 通过要点删掉某文件里最后 / 仅有的案例、导致文件被整体删除 → 该文件能进回收站 / 有等效备份，误删可从回收站找回（与资源管理器直接删除体验一致）。
- 仅通过要点删掉部分案例、文件还有剩余行 → 文件保留、仅行减少，照常编辑，不涉及回收站。
- 注意：判定"是否整体删文件"的依据是"删除后案例文件剩余行数是否为 0"，而不是"通过要点删了几个案例"。只有删到空才会触发整体删文件（从而涉及回收站 / 可恢复性）。

### 补充说明（已确认方案与约束）
- 根因（供研发参考）：通过要点删除走 `src/utils/pointCaseDeleter.ts` 的 `deleteCasesFromCaseFileMulti`，当 `remainingRecords === 0` 时调用 `fs.promises.unlink(casePath)`（pointCaseDeleter.ts:547）做裸物理删除——它不触发 VS Code 文件系统事件、也不走回收站；而资源管理器直接删除走 `src/handlers/workspaceListeners.ts` 的 `onWillDeleteFiles`（先备份到 os.tmpdir）+ VS Code 原生 Move to Trash（默认 `files.enableTrash=true`，文件先入回收站）+ `onDidDeleteFiles` 还原后再由 `finalizeHardDelete` 的 `fs.promises.unlink`（workspaceListeners.ts:1595）删除"还原副本"，因此回收站里 VS Code 最初移入的那份副本始终保留、可找回。两条路径真实删除动作都是 `unlink`，差异在于直接删除路径有"先入回收站 + tmp 备份"安全网，而要点删除路径没有。
- 方案对齐：本需求要求把"要点删除整体删文件"这一分支也接入直接删除已有的安全删除机制（回收站 / tmp 备份），使"文件被整体删掉"在两种入口下都可恢复，消除行为分裂。
- 验收：可对比"资源管理器直接删除案例文件（能否从回收站找回）"与"通过要点删除清空文件（能否从回收站找回）"两条路径，确认可恢复性一致。
- **实现说明（已落地）**：复用"资源管理器直接删除案例文件"同一条回收站路径，文件可进回收站找回，与直接删除体验完全一致：
  - 新增 `src/utils/caseFileRecoverableDelete.ts` 的 `deleteCaseFileRecoverable()`：调用 `vscode.workspace.fs.delete(uri, { useTrash: true })` 把文件**移到 OS 回收站**（原生 Move to Trash，与直接删除一致）；`pointCaseDeleter.ts` 在"案例文件被清空整体删除"分支改用该工具，`fileDeleted` / `fileDeleteError` 口径不变；trash 不可用时降级 `fs.promises.unlink`（与"直接删除 trash 失败时"行为一致，无额外 tmp 备份）。
  - 为避免该删除事件二次进入 `workspaceListeners` 的直接删除决策链路（重复备份 / 还原文件 / 弹确认框），新增中性共享模块 `src/utils/caseDeleteGuard.ts`（路径级抑制开关 Set，含 `suppressDeleteForPath` / `isDeleteSuppressed`，零业务依赖、避免循环依赖 / 依赖倒置），在删除期间抑制 `onWillDeleteFiles` / `onDidDeleteFiles` 对受抑制路径的拦截；绑定清理仍由 `pointCaseDeleter` 的 `cleanupCaseFileTraces` 负责。匹配键用 `vscode.Uri.file(p).fsPath` 归一化，与 `event.files[].fsPath` 同构，避免符号链接（如 `/var↔/private/var`）/ 大小写差异导致抑制失效。

## F5. 测试案例文件夹下的 csv / json / yaml 若不含 testcase_id 关键字段，不应使用案例编辑器打开

### 用户场景
用户把一些结构化文件（csv / json / yaml）放进了测试案例文件夹（如 `测试任务/<任务>/测试案例/`）。其中一部分确实是案例文件，字段里带有 `testcase_id`；但也常混有**并非案例**的文件——例如从别处导出的数据台账、配置快照、或其它带表头的结构化文件，它们只是恰好落在案例文件夹里，并不含 `testcase_id` 这个关键字段。

用户反馈的问题：
- 只要文件是 csv / json / yaml 且落在案例文件夹下，插件一律用**案例编辑器**打开，即便文件里根本没有 `testcase_id`；
- 用户看到的是"案例编辑器"界面、被暗示"这是一条条案例"，但其实文件根本不是案例，打开后解析出来是空的 / 错乱的，体验误导且尴尬；
- 用户预期：放在案例文件夹 ≠ 一定是案例。一个 csv / json / yaml 文件如果**不含 `testcase_id` 关键字段**，就不该被当成案例、不该用案例编辑器打开，而应像普通文件一样正常打开（文本 / 表格 / 默认编辑器）。

### 需求
1. 测试案例文件夹下的 csv / json / yaml 文件，在决定是否用案例编辑器打开前，应先检查其内容是否包含关键字段 `testcase_id`：
   - 含 `testcase_id`（首行 / 顶层字段名能识别到该关键字段）→ 视为案例文件，正常使用案例编辑器打开；
   - **不含 `testcase_id`** → **不使用案例编辑器打开**，按插件对非案例文件的默认处理方式（普通打开 / 文本编辑）打开，不把它当作案例去解析、呈现或参与案例相关操作。
2. 该"关键字段判定"应在**打开入口决策阶段**生效，即文件被识别为"是否案例"的那一刻就据此分流，而不是先用案例编辑器打开、再发现没字段才降级。
3. 判定依据是"内容里是否包含 `testcase_id` 字段"，而非"文件名 / 扩展名 / 所处目录"——一个确实含 `testcase_id` 的文件，即便文件名不带"案例"字样，仍按案例文件正常用案例编辑器打开；反之不含该字段的文件，即便在案例文件夹下，也不强用案例编辑器。

### 使用预期
- 案例文件夹下的 `案例清单.csv`（首行含 `testcase_id, 用例标题, 步骤...`）→ 正常用案例编辑器打开，照常解析呈现。
- 案例文件夹下的 `台账导出.csv` / `配置快照.json`（字段里没有 `testcase_id`）→ 不弹案例编辑器、不按案例解析，直接按普通文件（文本 / 默认程序）打开，不被误导成案例。
- 注意：本需求只改变"是否用案例编辑器打开"的决策，不改变文件在磁盘上的归属 / 目录结构；不含 `testcase_id` 的文件只是"用普通方式打开"，仍保留在案例文件夹中，不强制搬迁或改名。

### 补充说明（已确认方案与约束）
- 判定口径：以"内容是否包含关键字段 `testcase_id`"为案例识别的硬标准，与 F1 中"以 `testcase_id` 是否存在 / 是否样例占位来判断是否已推送"、F3 中"以是否含测试要点节点来判断测试要点文件"的口径一致——都是"看内容本质、不看护城河（文件名 / 目录）"。
- 与"仅样例占位"案例文件的关系：F1 处理的是"含 `testcase_id` 列、但值只是样例占位"的情形（仍按案例处理）；本需求处理的是"根本不含 `testcase_id` 字段"的情形（不是案例、不用案例编辑器）。两者互补：含字段且为样例占位 → 仍是案例、走案例逻辑；完全不含字段 → 不是案例、用普通编辑器。

## F6. 埋点增强：全链路遥测事件补充 filePath 维度

### 用户场景
现有遥测事件多以 `fileFormat`（csv / json / yaml）等维度为主，缺少"文件名"维度，线上聚合时无法区分"是哪个文件"出的问题：
- R10 已为 `parser.parseFailed` 补充了 `fileName` 维度，但编辑器打开、保存、推送、切文本、删除案例、外部变更、testcase_id 落盘等大量事件仍只有 `fileFormat`，缺文件名维度，难以定位高频出错的具体文件。
- 研发排障时只能靠用户手动反馈截图，无法在遥测后台直接按文件聚合失败分布。

用户视角的诉求：
- 线上某个文件反复出问题（解析失败 / 推送超时 / 落盘失败），希望后台能直接按文件名聚合出"哪些文件最常出错"，而不是笼统地看格式维度。
- 不希望上报绝对路径（含目录与用户名），避免 PII 泄露；仅文件名即可满足按文件定位的需要。

### 需求
1. 在所有关键遥测事件（`TelemetryService` 上报）中补充 `filePath` 字段，取值为 `path.basename(filePath)`，仅文件名、不含目录与绝对路径，符合脱敏约定。
2. 涉及事件至少包含：
   - **编辑器**：`editor.opened`、`editor.saved`、`editor.switchedToText`、`editor.reloaded`、`editor.deleteRows.error`、`editor.message.error`、`editor.save.error`、`editor.push.error`、`editor.network.error`；
   - **推送链路公共字段**（通过 `baseTelemetryProps` 统一注入）：在 `ext`、`traceId` 之外新增 `filePath: ctx.baseName`；
   - **解析器**：`parser.parseFailed`（csv / json / yaml）追加 `filePath`；
   - **编辑器提供器**：`editor.waitReady.timeout`、`editor.keepEditor.failed`、`editor.opened.tempFolder`、`editor.opened.unqualified`、`editor.visibleChange.skipped`、`editor.visibleChange.failed`、`editorPush.reparseFailed`；
   - **文件监控**：`editor.externalChange.skipped`、`editor.externalChange.fired`；
   - **webview 数据推送**：`editor.testcaseId.saveFailed`。
3. 埋点须遵循既有 `TelemetryService` 约定：受 VS Code 遥测开关控制、开发环境仅本地打印不上报、单事件 payload ≤ 8KB、不影响主流程（埋点失败静默丢弃）。
4. 脱敏约束：路径 / 文件名相关字段仅传 basename，不上报绝对路径，避免 PII（与 R10 一致）。

### 使用预期
- **线上**：遥测后台可按 `filePath` 维度聚合，定位高频出错的具体文件（如某个 csv 反复解析失败、某个 yaml 推送频繁超时），无需依赖用户手动反馈。
- **本地开发**：受 VS Code 遥测开关控制，仅本地打印，不上报。
- **业务行为零变化**：仅埋点字段扩充，不影响任何功能逻辑、不新增或改变弹窗与交互。

### 补充说明（已确认方案与约束）
- **实现位置**（均为在原有 `TelemetryService.sendTelemetryEvent/ErrorEvent` 调用处追加 `filePath: path.basename(...)`，或对推送链路公共字段函数 `baseTelemetryProps` 增加 `filePath: ctx.baseName`）：
  - `src/handlers/editorMessageHandlers.ts`：多个 `editor.*` 事件补 `filePath`；
  - `src/handlers/pushCore.stages.ts`、`src/handlers/pushCore.ts`、`src/preValidate/stepPreValidate.ts`：各自的 `baseTelemetryProps` 公共字段加 `filePath: ctx.baseName`；
  - `src/parsers/csv-parser.ts`、`src/parsers/json-parser.ts`、`src/parsers/yaml-parser.ts`：`parser.parseFailed` 补 `filePath`；
  - `src/providers/BaseEditorProvider.ts`：多个 `editor.*` 事件补 `filePath`；
  - `src/services/fileWatchService.ts`：`editor.externalChange.skipped` / `fired` 补 `filePath`；
  - `src/services/webviewDataPusher.ts`：`editor.testcaseId.saveFailed` 补 `filePath`。
- **与 R10 的关系**：R10 为 `parser.parseFailed` 新增了 `fileName` 维度；本需求在此基础上为同一事件补充 `filePath`（basename，二者取值一致，均为文件名），并横向扩展到编辑器 / 推送 / 监控等全链路事件，统一补齐按文件定位的能力。
- **与埋点契约**：事件名 / 字段遵循 `docs/specs/埋点事件清单.md`；新增的 `filePath` 维度需在该清单中登记说明（与既有 `fileName` 并列，标注取值为 basename）。
- **影响面控制**：纯字段扩充，无新增埋点事件、无逻辑分支变化，对主流程无副作用；与现有埋点脱敏、开关、上报约束完全兼容。
- **状态**：已实现（代码改动待提交）。
