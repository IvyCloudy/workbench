- **创建日期**：2026-09-09
- **状态**：已实现

## 0. 概述

本文档汇总九类用户在使用案例编辑器与推送功能时反馈的问题，以及对应的产品需求。内容从用户实际使用和感知的角度描述，不涉及技术实现细节。

| 编号 | 用户场景 / 反馈 | 需求 |
| --- | --- | --- |
| R1 | 测试案例目录里有「临时文件」文件夹，里面的草稿被误当成正式案例 | 临时文件目录内的文件应被排除在案例功能之外 |
| R2 | json 案例只有一条记录时，编辑保存后文件从"数组"变成了"对象"，形态被破坏 | 单条数组的 json 保存后应保持数组形态 |
| R3 | 想一次删掉选中的多行，但右键只能逐行删 | 选中多行时，右键支持一次性删除选中行 |
| R4 | 推送时不知道在干什么、等很久、超时不明确、后端返回失败不清晰 | 推送要给明确进度提示；最终超时定为 90 秒；超时与后端返回失败（接口返回码非 SUC0000）统一按"整文件级错误"弹窗提示，可追踪 |
| R5 | 案例路径里包含「·」（间隔点），推送后变成了「/」，路径层级错乱、与测试要点关联匹配不上 | 路径中的「·」应原样保留，不应被当作分隔符转成「/」；若为历史约定须先提示用户 |
| R6 | 测试任务目录层级错位（如嵌套 测试任务、缺少 测试案例 层级）的文件被误当合格案例打开；层级外无关文件缺少清晰区分 | 层级外的文件放行（按普通文件处理）；层级内但不满足"测试任务/单任务/测试案例"层级要求的文件拦截（不进案例编辑器，显式打开给清晰报错，右键相关菜单隐藏） |
| R7 | 案例编辑器里 steps 等单元格用 Ctrl+C / Ctrl+V 复制粘贴没反应，用右键「复制单元格 / 粘贴单元格」却可以（快捷键与右键行为不一致） | 快捷键与右键结果须一致（steps 等明细列完整写入、单值粘多格两边都摊满选区）；内部复制可原样粘回；从外部（Excel）复制仍可按 TSV 粘贴 |
| R8 | 列筛选（漏斗）弹窗选项很多、列表需要滚动时，「(全选)」行跟着选项一起滚出视野，想全选 / 取消全选还得先滚回顶部 | 列筛选列表的「(全选)」行固定在可滚动列表顶部，向下滚动时始终可见；搜索框与底部「清除筛选 / 取消 / 确定」按钮保持不变 |
| R9 | 案例里很多行共用同一个 yaml 锚点（如 `tags: *id001`），当别名引用次数超过 100 时，双击 yaml 文件案例编辑器打不开 / 打开后空白，文件被当成「无法解析」；但 yaml 语法本身没问题 | 同一锚点被大量行复用（别名引用次数远超 100）的 yaml 案例也应能正常打开并展示为表格，不受解析库的别名数量上限限制；保存时锚点复用结构保留 |
| R10 | 案例编辑器打开坏文件（JSON 括号不匹配 / YAML 缩进或锚点错误 / CSV 编码损坏等）解析失败时回退文本或空白，但解析失败缺乏统一、可检索的记录，线上难以统计哪类格式 / 哪个文件 / 哪一行常出错 | 解析失败须统一打印结构化错误日志（文件 + 报错 + 堆栈），并上报 `parser.parseFailed` 埋点（含 fileFormat / fileName / line / column / errorMessage / stackHead），便于本地排障与线上聚合统计 |

## R1. 测试案例文件夹中包含「临时文件」

### 用户场景
在测试任务目录下，常常有一个「临时文件」子文件夹，里面放的是草稿、备份或临时整理的 json/yaml/csv。

用户反馈的问题：
- 这些临时文件也被识别成了测试案例，能被打开进案例编辑器。
- 右键菜单里出现了"推送案例""绑定测试要点"等正式功能。
- 批量推送整个案例文件夹时，临时文件也被一起推送了，造成误推送。
- 双击临时文件里的 json 时，有时编辑器会卡住、界面无响应。

### 需求
1. 只要文件位于名为「临时文件」的文件夹内（不论层级多深），就不把它当作测试案例。
2. 这类文件：
   - 不能进入案例编辑器，不显示表格编辑界面；
   - 不提供推送、绑定等案例相关的右键功能；
   - 批量推送整个文件夹时自动跳过，且不计入失败。
3. 双击打开「临时文件」里的 json/yaml/csv 时，用普通文本编辑器打开即可，界面不应卡死。

### 使用预期
- 临时文件目录里的文件：右键看不到推送/绑定等菜单；批量推送时它们被静默跳过；双击以纯文本方式打开。
- 注意：判定依据的是"所在文件夹叫临时文件"，而不是"文件名里带临时文件几个字"。所以一个恰好叫 `xxx临时文件.json`、但不在临时文件文件夹里的文件，仍会被正常当作案例处理，不会误伤。

## R2. json 案例文件为单数组时，数组变为字典

### 用户场景
有些 json 案例文件，顶层是一个数组，但里面只有一条记录，例如：

```
[
  { "用例名": "...", "步骤": "..." }
]
```

用户在案例编辑器里打开、改了点内容、保存之后，发现文件变成了这样：

```
{
  "用例名": "...",
  "步骤": "..."
}
```

也就是说，原本的"数组（方括号）"被改成了"对象（花括号）"。这会导致下游读取这个文件的工具解析失败，因为形态变了。

### 需求
json 案例文件如果顶层是数组（无论里面是一条还是多条记录），编辑保存后**必须保持数组形态**，不能把单条数组自动"拍扁"成单个对象。

### 使用预期
- 原来顶层是 `[ {...} ]`（一条）的，保存后还是 `[ {...} ]`，不再是 `{...}`。
- 原来顶层是多条数组的，保存后还是数组。
- 原来顶层本来就是单个对象的，保存后仍是单个对象，不受影响（向后兼容）。

## R3. 案例编辑器选中多行时，右键支持删除选中行

### 用户场景
在案例编辑器里，用户经常需要清理一批用例：框选或整行选中了多行（比如 10 条），想一次性把它们删掉。

用户反馈的问题：
- 右键菜单里只有"删除该行"（删当前光标所在的一行），要删 10 行就得点 10 次，非常麻烦。
- 也没有"删除选中行"的入口。

### 需求
1. 当用户选中了多行（或跨多行的单元格区域）时，右键菜单应出现"删除选中行"菜单项，并标注将要删除的行数。
2. 点击后，一次性删除所有选中的行。
3. 删除行为要与现有逻辑一致：已经推送到后端的案例，走线上删除；删除失败的案例行要保留下来并给出失败原因提示，不能悄悄丢数据。

### 使用预期
- 选中多行 → 右键出现「删除选中行 (N)」→ 按提示确认 → 选中的 N 行被一次性删除。
- 如果只选中了单行（非整行），仍然显示"删除该行"；如果选的是跨多行的单元格区域，也支持一次性删除该区域覆盖的所有行。
- 已推送到后端的案例：触发线上删除；删除失败的行会保留并标灰、显示失败原因，方便后续重试。

## R4. 案例推送体验优化（进度提示 / 90 秒超时 / 兜底追踪）

### 用户场景
用户点"推送"后，经常遇到以下困惑：

1. 点了推送，界面没什么反应，不知道是正在处理还是已经卡死。
2. 等了一阵子，突然弹出一个"推送超时未响应，已解除按钮锁定"的提示，但完全不知道这个超时到底是多久、为什么触发。
3. 有些大模型生成/大批量案例，推送本身就需要比较久，10 秒～1 分钟的超时太短，动不动就失败。
4. 推送真正卡死（后端一直不返回）时，没有任何记录可以排查是哪一个文件、哪一次操作出的问题。

### 需求
1. **明确进度提示**：点击推送后，界面给出清晰的"推送中，请耐心等待"提示（按钮转圈 + 文字提示），让用户知道后台在处理。
2. **统一超时时间为 90 秒**：推送的最终超时统一设为 90 秒，前端等待兜底与后端真实等待保持一致，行为可预期。
3. **超时可追踪**：当推送真的超过 90 秒仍无任何响应、触发超时提示时，应自动记录一条使用数据（埋点），包含：触发入口（工具栏还是右键）、文件名、文件格式、本次推送行数、超时时长。便于后续定位是哪一个文件、哪一次操作卡死。
4. **后端返回失败统一为"整文件级错误"弹窗**：推送接口返回码不是 `SUC0000` 时，视为"后端返回失败"（整文件级拒绝，如任务不匹配 / 权限 / 业务拦截）。此时弹窗样式与超时场景一致（标题"推送失败：文件名" + 整段错误文案），而不是把同一条错误按行逐条塞进失败列表。错误文案统一冠以前缀「后端返回失败:」。三种推送入口（案例编辑器内、资源管理器单文件、批量推送）行为一致。
5. **批量推送按文件分别提示，不加批量级弹窗**：批量推送时每个文件独立推送；某个文件超时或后端返回失败，只在该文件对应的总结行标记为错误（✕），不额外弹批量级弹窗。用户点击该失败文件行时，才打开案例编辑器并弹出对应的（超时 / 后端返回失败）整文件错误提示。

### 使用预期
- 点击推送 → 按钮进入转圈状态，并显示"推送中，请耐心等待…"。
- 90 秒内后端返回结果 → 正常弹出结果提示，需用户手动关闭。
- 超过 90 秒仍无响应 → 界面弹出超时提示："推送案例超时（90 秒）未拿到推送结果。推送任务未终止（可能仍在 TMS 后台执行），请稍后到 TMS 平台查看案例是否推送成功；如需重试，可在案例编辑器中分批推送。"；按钮恢复正常可再次点击；同时后台记录一条该次超时的使用数据。
- 后端返回失败（接口返回码非 SUC0000）→ 界面弹出与超时场景一致的整文件级错误弹窗，标题为"推送失败：文件名"，正文以「后端返回失败: 」开头（例如："后端返回失败: 任务不匹配 / 无权限…"；若无错误详情则降级为"后端返回失败: 后端返回码=XXX，body=…，无错误详情，请联系后端排查"）。该弹窗与超时弹窗样式完全相同，不混入"失败 N 条"行级列表。
- 批量推送（多文件 / 文件夹）时：每个文件独立推送，不加批量级弹窗；哪个文件超时或后端返回失败，哪个文件的总结行标记为 ✕ 错误并展示截断后的提示；点击该文件行才打开编辑器并弹出对应的整文件错误提示。
- 重复点击推送时，提示"推送中，请耐心等待…"，不会重复发起。

### 补充说明
- 正常情况下，后端会在 90 秒时先返回超时错误，前端随之结束等待并弹出上述超时提示；因此"超过 90 秒无响应"这一提示通常只在后端彻底卡死（如连接挂起、前置处理卡住）时才会出现——而这种情况正是最需要被记录追踪的异常场景。
- 若用户所在单位另行配置了更长的推送超时时间，则以配置为准。
- 失败提示分两类，需区分：**整文件级失败**（推送接口超时 90 秒、接口返回码非 SUC0000 的后端拒绝）走统一"纯错误"弹窗；**某条案例失败**（接口 `body` 里逐行的 `type=2` 失败）仍走"失败 N 条"列表弹窗。只有顶层接口失败才是整文件级拒绝，符合"非某条案例失败"的区分。

## R5. 案例路径中的「·」被转换为「/」

### 用户场景
用户给案例所在路径（目录名或文件名）里使用了「·」（间隔点），例如 `功能模块/登录·校验`、`用例集·场景A.json`。推送之后发现，路径里的「·」全部被换成了「/」，原本是一个名称 / 一层的内容，被拆成了多级目录。

用户反馈的问题：
- 推到 TMS 后路径层级错乱，案例归类到了错误的目录，和本地对不上。
- 与测试要点做关联匹配时，路径对不上，关联失效或匹配错乱。
- 这个转换是静默发生的，推送前没有任何提示，事后才发现路径被改了。

### 需求
1. 路径中的「·」应作为名称的一部分**原样保留**，推送时不应被当作路径分隔符转换成「/」。
2. 若产品确实存在把「·」当分隔符的历史约定，至少在转换前给出**明确的提示或转换预览**，让用户知情并确认，而不是静默改写。

### 使用预期
- 路径含「·」的案例推送后，TMS 里看到的路径与本地一致，「·」仍然在，不再出现"本地一条路径、TMS 多级目录"的错位。
- 与测试要点的关联匹配基于原路径，不再因「·」被改写而失配。

### 补充说明（已确认方案与约束）
- 已确认方案：路径标准化**仅将反斜杠 \ 转换为 /**，全角 ／、间隔点 · 一律原样保留，不再当作分隔符。推送路径侧（pushDataMapper.normalizePath）与"测试要点 ⇄ 案例"关联匹配侧（pointCaseLinker.normalizePointPath）已同步修改，分隔符规则保持一致。
- 该方案直接满足需求 1：路径中的「·」原样保留，推送后 TMS 里层级不再错乱，关联匹配也基于原路径。
- 仍需关注：若历史上有团队确实用「·」或「／」当路径分隔符来组织老案例，改完后这些老案例的路径会被视为"含 ·/／ 的名称"，可能与原归类 / 关联预期不同；上线前应排查存量案例，必要时提供迁移提示或兼容处理。

## R6. 测试任务目录层级不符合要求（嵌套 / 错位）时的放行与拦截

### 用户场景
测试任务的案例文件应严格处于 `测试任务/<任务名>/测试案例/` 这一层级、测试要点处于 `测试任务/<任务名>/测试大纲/`。但实际使用中会出现两类"层级不对"的文件：

- **层级外（与测试任务结构无关）**：例如工作区里的 `src/foo.json`、或 `测试任务/C001/说明.txt` 这类根本不在"测试案例 / 测试大纲"下的文件。它们只是普通文件，本不应被当成案例。
- **层级内但错位（嵌套 / 缺层级）**：例如 `测试任务/测试任务/TT505_测试任务5/测试案例/testcases.json`——"测试任务"与"测试案例"之间多嵌了一层"测试任务"；或 `测试任务/C001/foo.csv` 少了"测试案例"这一级。这类文件**位于测试任务体系内**，但路径不满足"测试任务 / 单个任务 / 测试案例"的层级约定。

用户反馈的问题：
- 过去层级判定规则过宽，把"层级内但嵌套错位"的文件也误判为合格案例，直接打开了案例编辑器（内容形态不对、表格错乱、与测试要点关联匹配不上）。
- 显式用案例编辑器打开这类文件时，没有明确提示"为什么打不开"，用户困惑。
- 资源管理器右键里，本不该出现的"新增测试案例 / 推送 / 绑定"等菜单出现在了层级不对的文件或文件夹上。

### 需求
总体原则：**层级外的文件放行（按普通文件处理）；层级内但不满足目录层级要求的文件拦截（不进入案例编辑器，并清晰告知原因）。**

1. **层级判定以"相对工作区根"为准，严格锚定层级**：
   - 合格案例路径须形如 `测试任务 / <单个任务名> / 测试案例 / <案例文件>`，即"测试任务"与"测试案例"之间**只允许恰好一段**（任务名），不允许额外嵌套。
   - 合格测试要点路径须形如 `测试任务 / <单个任务名> / 测试大纲 / <要点文件>`。
   - 判定基于文件相对工作区根的路径，避免因工作区名动态、或路径里恰好含"测试任务"字样而误判。
2. **层级外放行**：不在上述合格结构内的文件（如 `src/foo.json`、普通说明文档），一律按普通文件处理——默认以文本编辑器打开，不进入案例编辑器，不提供推送 / 绑定等案例功能，批量推送时跳过。
3. **层级内拦截**：位于测试任务体系内、但路径层级不满足要求的文件（含嵌套 测试任务、缺少 测试案例 / 测试大纲 层级等），**不把它当作合格案例**：
   - 双击打开时，因编辑器 glob 仅匹配合格结构，由 VS Code 默认以文本打开（不进案例编辑器，不报错、不卡顿）；
   - 用户显式"用测试案例编辑器打开 / Open With > 测试案例编辑器"时，渲染**清晰的报错页**，明确指出：
     - 哪一层级不对（如"测试任务 与 测试案例 之间多嵌了一层"）；
     - 文件的完整相对路径；
     - 排查建议（应放到 `测试任务/<任务>/测试案例/` 下）。
   - 资源管理器右键中，与"测试案例 / 测试大纲"相关的菜单（新增测试案例、推送测试案例、绑定测试要点等）在层级不对的文件 / 文件夹上**不显示**。
4. 只针对"层级不对"做拦截，不误伤正常文件：恰好名字里带"测试任务""测试案例"字样、但层级正确的文件，仍正常当作案例处理。

## R7. Ctrl+C / Ctrl+V 复制粘贴与右键「复制单元格 / 粘贴单元格」结果不一致（steps 等明细列粘不上）

### 用户场景
在案例编辑器里，想把某一行的 steps（步骤）单元格内容复制到另一行（或另一个案例）。

用户反馈的问题：
- 按 Ctrl+C 复制、再按 Ctrl+V 粘贴到目标 steps 单元格后，单元格没有变化；有时只看到"明细列已跳过，请通过弹窗编辑"的提示。
- 同样的操作改用右键菜单的「复制单元格」/「粘贴单元格」却能成功。
- 同一个字段，快捷键粘不上、右键能粘上，行为不一致，容易误以为快捷键坏了。
- steps 恰好是内容最多、最需要整块复制的字段（步骤描述 / 数据 / 预期结果），快捷键失效后只能打开弹窗逐条手工重填，效率很低。

### 需求
1. steps（明细列）等单元格通过 Ctrl+C / Ctrl+V 复制粘贴，结果必须与右键「复制单元格 / 粘贴单元格」一致：内容完整写入目标单元格，步骤条数与每步的描述 / 数据 / 预期结果均对得上。
2. 复制出去的内容要保持“可再次粘回来”的能力（自己复制、自己粘贴能完整往返），不能出现“复制提示成功、却粘不回来”的情况。
3. 复制 1 个单元格后框选多格再粘贴（Ctrl+V 或右键粘贴），整个选区应被填成该内容（Excel 行为）；过滤模式下只填可见行。
4. 复制到编辑器外部（如 Excel / 文本编辑器）时看到的仍是可读文本；从编辑器外部（如 Excel）复制进来的内容仍可按 TSV 粘贴，该能力保持不变。

### 使用预期
- 选中 A 行 steps 单元格 → Ctrl+C → 选中 B 行 steps 单元格 → Ctrl+V → B 行 steps 与 A 行完全一致，并提示“已粘贴 1 个单元格”。
- 右键「复制单元格 / 粘贴单元格」与快捷键结果完全一致：明细列按对象原文写入；单值剪贴板粘到多格选区时，两边都摊满选区。
- 把 steps 复制到编辑器外部时，看到的是可读文本：各步为紧凑 JSON、以 `; ` 分隔，不因修复而变成不可读的一团。
- 粘到非 steps 的普通列时不会报错，行为与复制单个对象单元格时保持一致。

### 补充说明（已确认方案与约束）
- 根因：右键「复制选区」与 Ctrl+C 都走 `copyCell()`：既把原始对象写入内部剪贴板 `S.clip`，又把 TSV 文本写入系统剪贴板；右键「粘贴单元格」用 `S.clip` 的原始对象，因此明细列能正确写入。而旧 Ctrl+V 是完全独立的一套逻辑，只读系统剪贴板的 TSV 文本并 `JSON.parse`——对象数组转出的文本不是合法 JSON，于是被判为非对象 / 对象数组剪贴板而跳过，表现为快捷键粘贴无效。本质是快捷键没有复用右键那条已验证可用的粘贴路径。
- 已确认方案：让 Ctrl+C / Ctrl+V 与右键共用同一对函数。`copyCell()` 额外把本次写入系统剪贴板的 TSV 记到 `S._clipLastTsv`；Ctrl+V 读到的内容与之相同即判定为表内复制，先把锚点同步为选区左上角，再直接调用右键的 `pasteCell()`，二者结果完全一致（明细列按对象原文写入、单值剪贴板摊满多格选区）。外部复制（如 Excel）内容与此不一致，仍走系统剪贴板 TSV 解析，Excel 粘贴能力保留。
- 影响面控制：`pasteCell()` 新增单值剪贴板 + 多格选区时摊满选区（复用原二维铺贴分支，未新增写入路径），并对写入非明细列的对象数组做字符串化，避免 chip 渲染成 `[object Object]`（该问题对右键同样存在）。`_cellValueToTsv` 维持原样（对象数组仍用 `; ` 拼接，仅供系统剪贴板）；`copyCell` 仅多记一个 `_clipLastTsv`。
- 该项与文档 1. 通用说明中"明细列粘贴仅接受对象或对象数组、纯文本跳过并提示"的既有约定不冲突：本需求只保证"从编辑器复制出的内容本身可被粘回"。

## R8. 列筛选弹窗向下滚动时「(全选)」行滚出视野

### 用户场景
列筛选弹窗（表头漏斗）里，某一列的不同取值很多，列表很长、需要滚动查看；列表第一行是「(全选 N)」复选框（搜索后变为「(全选 搜索结果)」）。

用户反馈的问题：
- 向下滚动查找某个取值时，「(全选)」行跟着选项一起往上滚走，消失在列表顶部之外。
- 想临时"全选 / 取消全选"（或"全选搜索结果"），得先把列表滚回最顶才能点到「(全选)」，操作很麻烦。
- 「(全选)」与搜索结果的全选是高频操作，但因为会滚走而不可见，容易被忽略。

### 需求
1. 列筛选列表的「(全选)」行应固定在可滚动列表的顶部：向下滚动时始终可见，不随选项一起滚出视野。
2. 顶部的搜索框行与底部的「清除筛选 / 取消 / 确定」按钮保持不变（它们本就不在可滚动列表内，不随列表滚动）。

### 使用预期
- 列表向下滚动时，「(全选 N)」一直贴在列表顶部，下方选项从它下方滚过；勾选「(全选)」即时全选 / 取消当前可见（或全部）项。
- 搜索后「(全选 搜索结果)」同样固定在顶部，方便一键选中 / 取消全部搜索命中项。
- 主列筛选（表头漏斗）与 steps 子列筛选（步骤子表头漏斗）行为一致：二者共用同一列表渲染。

### 补充说明（已确认方案与约束）
- 实现：给「(全选)」行加 `position:sticky; top:0` + 不透明背景 + `z-index`，使其固定在 `.xs-sf-list` 滚动容器顶部；其下边线替代原分隔线（`media/common/styles/table-editor.css`）。
- 主 / 子列筛选共用 `renderColFilterList()`（04-push-find.js），一处改动两处生效；同时移除已冗余的 `.xs-sf-divider` 元素，避免出现"双线"。

## R9. yaml 案例大量复用同一锚点（别名引用超过 100）时打不开 / 空白

### 用户场景
有些 yaml 案例为了复用，会定义一个锚点（如 `tags: &id001` 列一个标签列表），然后在很多行里用 `*id001` 引用它。比如一个测试任务里几百条用例的 `tags` 列都引用同一个锚点，避免重复写。

用户反馈的问题：
- 当 `*id001` 这类别名引用次数超过 100 时，双击 yaml 文件，案例编辑器打不开，或打开后页面空白 / 不显示表格。
- 文件本身语法没问题（用 yaml 校验工具能正常解析），但编辑器就是展示不出来；用户以为是文件坏了、或自己写错了。
- 把引用减到 100 条以内又能正常打开，差别只在于别名引用的数量，而不是内容或结构。

### 需求
1. yaml 案例里同一个锚点被大量行复用（别名引用次数很多，远超 100）时，案例编辑器也应正常打开并展示为表格，不受别名数量上限限制。
2. 复用锚点的语义要正确保留：所有引用行展示出来的 `tags` 等字段值与锚点定义一致；保存后锚点复用结构不丢失（仍按引用形态写回，不展开成各自重复写死的值）。

### 使用预期
- 一个 yaml 文件里 100+ 条用例都引用同一个锚点 `*id001`，双击仍正常进案例编辑器、表格展示全部行，每行的 `tags` 列都是锚点定义的 `[界面]` 等值。
- 保存后文件仍是引用形态（`tags: *id001`），不会被强制展开成每行列重复写死的值。

### 补充说明（已确认方案与约束）
- 根因：编辑器使用的 yaml 解析库（yaml）默认 `maxAliasCount=100`，别名引用次数超过 100 即抛 `Excessive alias count indicates a resource exhaustion attack`，解析失败 → 编辑器无法把文件渲染成表格（回退到文本或无内容）。这是库为防止恶意别名炸弹设的默认安全上限，并非文件语法错误。
- 已确认方案：将 `maxAliasCount` 上限统一放宽到 10 万，且**必须挂在转换阶段（toJS 选项）而非语法组合阶段**：
  - 解析层 `src/parsers/yaml-parser.ts` 定义 `YAML_TO_JS_OPTIONS = { maxAliasCount: 100_000 }`，作用于主解析路径 `doc.toJS(YAML_TO_JS_OPTIONS)` 与 toJS 失败兜底重试的 `YAML.parse(cleanContent, YAML_TO_JS_OPTIONS)`；
  - 其余入口一致口径：`src/utils/yamlValidator.ts`（推送前校验兜底取行号）、`src/parsers/yaml-parse-check.ts`（打开时解析检查）、`src/utils/commands.ts` 均使用同一 `maxAliasCount: 100_000`，确保大别名文件在「打开 / 校验 / 推送」全链路一致可解析，不会在某环节被当成不可解析；
  - 关键根因澄清：yaml 库的 `maxAliasCount` 属于 **toJS 选项**，校验发生在「YAML → JS 转换」阶段（默认上限 100），而非 `parseAllDocuments` 的语法组合阶段；早期误传给 `parseAllDocuments` 既类型不合法也不生效（别名炸弹校验在转换时触发）。10 万阈值足以覆盖实际大规模复用、又能挡住真正的别名炸弹。该常量现已集中为 `src/utils/yamlRules.ts` 的 `YAML_TO_JS_OPTIONS`，上述四个入口统一引用同一份，避免散落硬编码漂移。
- 影响面：仅放宽解析上限，不改变文件写回逻辑，锚点复用语义在保存时保持不变。与 `skills/yaml-format-fix` 独立修复 CLI 的同类上限（如后续需要）应保持一致口径。

## R10. 文件解析异常的可观测性（统一报错打印 + 埋点）

### 用户场景 / 背景
案例编辑器在打开 csv / json / yaml 案例时，若文件存在语法问题（JSON 括号不匹配、YAML 缩进 / 锚点错误、CSV 编码损坏等），解析会失败并回退到文本或空白。此前这类解析失败在开发 / 排障时缺乏统一、可检索的记录：

- 控制台只有零散报错，难以把「某文件 + 某行 + 某错」关联到一次具体解析动作；
- 线上用户遇到打不开的坏文件时，研发无法从遥测侧统计解析失败的分布（哪种格式、哪个文件、出错在哪一行），只能靠用户手动反馈截图。

### 需求
1. **解析异常统一打印**：csv / json / yaml 三个解析器在解析失败时，统一在控制台打印结构化错误日志，包含文件路径、报错信息、错误堆栈，便于本地排障。
2. **解析异常埋点**：解析失败同时上报一条遥测错误事件 `parser.parseFailed`，维度至少包含：
   - `fileFormat`：文件格式（csv / json / yaml）；
   - `fileName`：文件名（仅 basename，按遥测规范脱敏，不上报全路径）；
   - `line` / `column`：出错所在行 / 列（从错误文案或字符位置反算，提取不到则留空）；
   - `errorMessage`：截断到 500 字符的报错原文；
   - `stackHead`：错误栈头（用于聚合，不含具体路径）；
   - `source`：触发解析的来源（editor / push / preValidate / watch / validate），由调用栈自动判定（见 `src/services/utils.ts` 的 `detectParseSource()`），调用方无需显式传参；用于区分同一文件在不同链路被解析时的失败，便于按来源聚合与去重。
3. 埋点须遵循既有 `TelemetryService` 约定：受 VS Code 遥测开关控制、开发环境仅本地打印不上报、单事件 payload ≤ 8KB、不影响主流程（埋点失败静默丢弃）。
4. csv 因无「具体行」语义（解析失败多为文件读取 / 编码错误），`line` / `column` 可留空，其余维度照常上报。

### 使用预期
- 本地开发：打开坏文件时，输出面板能看到 `CSV 解析失败: <path> | <msg> <stack>` / `JSON 解析失败: ...` / `YAML 解析失败: ...` 形式的日志。
- 线上：遥测后台可按 `parser.parseFailed` 聚合，按 `fileFormat` 看哪类格式解析失败最多，按 `fileName` / `line` 定位高频坏文件与出错位置；`errorMessage` 提供报错原文辅助判断（YAML 报错文案可能含出错行原文片段）。
- 用户关闭 VS Code 遥测后，不采集、不上报。

### 补充说明（已确认方案与约束）
- 实现位置：三处解析器 `parse()` 的 catch 统一调用 `TelemetryService.sendTelemetryErrorEvent('parser.parseFailed', buildErrorProps(e, { fileFormat, fileName, line, column, source }))`；`source` 由 `detectParseSource()`（`src/services/utils.ts`，依调用栈反推 editor / push / preValidate / watch，未命中则空串）自动判定，无需各 `parse()` 调用方显式传参。`buildErrorProps` / `stackHead` / `extractErrorLocation` 来自 `src/services/utils.ts`。行 / 列由 `extractErrorLocation(err, content?)` 从错误文案正则提取（YAML `line X, col Y` / `(X:Y)`、JSON `line X column Y` / `at position N` 反算），与 `log.error` 控制台日志并存、互补。推送校验链路 `src/utils/yamlValidator.ts` 的 `validateYamlContent` 在捕获到 YAML 解析错误时也上报同一事件（`source: 'validate'`，行 / 列取自 yaml 错误的 `linePos`），覆盖此前「打开 / 校验 / 推送」中校验环节漏报的解析失败。
- 复用既有埋点契约：事件名 / 字段与 `docs/specs/埋点事件清单.md` 保持一致；需在该清单登记 `parser.parseFailed` 事件（维度同上）。
- 脱敏约束：按 `src/utils/telemetry.ts` 约定，路径 / 文件名相关字段仅传 basename 或脱敏值，不上报绝对路径，避免 PII。
- 与 R9 的关系：R9 解决「大别名 yaml 打不开」，本需求解决「打不开 / 解析失败时能被记录与统计」；二者互补，R9 修复后正常文件不再触发 `parser.parseFailed`。

## 1. 通用说明

- **临时文件的判定看"文件夹名"**：仅当文件所在的某个文件夹名字叫「临时文件」时才排除；文件名里带这几个字不算。
- **JSON 单数组保形**：仅当原始文件顶层本来就是数组时才保持数组；原始就是单个对象的文件仍按对象保存。
- **推送 90 秒超时**：这是兜底下限；若单位配置了更长的超时，则按配置执行。
- **后端返回失败统一建窗**：接口返回码非 SUC0000 与接口超时（90 秒）均为"整文件级错误"，弹窗样式与文案前缀（"后端返回失败:"）三端（编辑器内、单文件、批量）一致；批量推送中按文件分别标记，点文件才弹对应错误，不加批量级弹窗。
- **目录层级判定锚定工作区根**：合格案例路径须为 `测试任务/<单任务>/测试案例/`、测试要点为 `测试任务/<单任务>/测试大纲/`（"测试任务"与"测试案例/测试大纲"之间恰为一段）；层级外的文件按普通文件放行，层级内但错位的文件拦截（显式打开给清晰报错、右键相关菜单隐藏）。详见 R6。
- **明细列（steps 等）的复制粘贴**：快捷键 Ctrl+C / Ctrl+V 与右键「复制单元格 / 粘贴单元格」结果须一致（共用 `copyCell` / `pasteCell`）；单值剪贴板粘到多格选区时两边都摊满选区；编辑器内部复制走 `S.clip` 的原始对象，可原样粘回；粘贴到明细列仍只接受对象 / 对象数组，纯文本（如从 Excel 复制的 TSV）依旧跳过并提示。详见 R7。
