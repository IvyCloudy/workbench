## 1. 总体架构

案例编辑器基于 VS Code `CustomEditorProvider` 构建，整体分三层，试点增强均落在这三层既有机制之上，不引入新框架：

- **扩展端（Node/ts，src/）**：文件解析、推送前校验（`src/preValidate/`）、字段映射（`src/utils/pushDataMapper.ts`）、推送主流程（`src/handlers/pushCore.ts` + `pushCore.stages.ts`）、埋点（`src/utils/telemetry.ts`）、模板创建（`src/handlers/fileCreator.ts`）、消息分发（`src/handlers/editorMessageHandlers.ts`）。
- **WebView 前端（media/pages/table-editor/editor/*.js）**：主表渲染（`02a-render.js`）、单元格编辑（`03a-cell-edit.js`）、明细弹窗（`03c-detail-modal.js` / `03d-detail-write.js` / `03h-detail-helpers.js`）、查找替换（`04-push-find.js`）、标记（`03e-mark.js`）、行操作（`03d-row-ops.js`）。
- **通信桥**：前端 `postMessage` 经 `dispatchEditorMessage`（`editorMessageHandlers.ts`）表驱动分发。

各增强落点：

| 需求模块 | 主要受影响的扩展端模块 | 主要受影响的 WebView 模块 |
|---------|----------------------|--------------------------|
| 3.1 展开步骤查找替换 | —（复用前端通用能力） | `04-push-find.js`、`03c/03d` 明细弹窗 |
| 3.2 推送字段默认值 | `pushDataMapper.ts`、`fileCreator.ts`、`pushCore.stages.ts` | — |

| 3.4 预期结果序号 | — | `03c-detail-modal.js`、`03h-detail-helpers.js` |
| 3.5 testcase_id TA 标识 | `maskUtil`（目标态，建议 `utils/`） | `02a-render.js` 单元格渲染 |

## 2. 功能详细设计

### 2.1 展开步骤支持查找替换（需求 3.1）

#### 需求要点
在 `steps` 展开的内联子表格内，复用表格编辑器通用查找替换能力，对步骤描述 / 预期结果 / 数据单元格做查找 / 替换；样例行只读跳过；筛选态仅作用于可见步骤。

#### 涉及模块与文件
- 前端：通用查找替换 `04-push-find.js`（查找 / 替换当前 / 替换全部、上下导航）；明细弹窗 `03c-detail-modal.js`（子表渲染上下文）。
- 复用既有通信通道，不新增消息类型。

#### 核心数据结构
复用 `04-push-find.js` 现有查找状态机：
```ts
interface FindState {
  keyword: string;
  caseSensitive: boolean;
  regex: boolean;
  scope: 'main' | 'subtable';  // 目标态：新增 subtable 作用域
  hits: { ri: number; ci: number; subRi?: number; subCi?: number }[];
  cursor: number;
}
```

#### 关键流程
1. **作用域切换**：子表内唤起查找替换时，将 `scope` 置为 `subtable`，查找索引仅收集当前展开子表的可编辑单元格（步骤描述 / 预期结果 / 数据）。
2. **导航与高亮**：命中项在子表内定位 / 高亮，跳过操作列、序号列。
3. **替换写回**：替换当前 / 替换全部调用既有单元格回写通道（`03a-cell-edit.js` 的 `commit`），同步 `rawRowGroups` 与折叠态合并文本；替换全部仅作用于可见步骤（与子列筛选取交集）。
4. **样例跳过**：命中单元格若处于冻结样例行，替换跳过并提示「样例数据行已冻结，不可操作」。
5. **撤销**：替换后 `pushHistory()` 纳入撤销栈，Ctrl+Z 可回退。

#### 边界与防御
- 子表查找不跨主表行：命中索引带 `ri` 隔离，避免误命中其它行子表。
- 筛选态下查找集合以过滤后可见行为准，退出筛选后重新建索引。
- 正则非法时沿用既有 `04-push-find.js` 的降级提示，不抛未捕获异常。

### 2.2 推送字段默认值（精益字段）（需求 3.2）

#### 需求要点
推送落库前，对未填写的精益字段 `keyFlag` / `planExecNum` / `projectDes`（CSV）与 `key_flag` / `plan_exec_num` / `project_des`（YAML）按系统默认值兜底；模板补充该字段；历史文件缺失字段兼容不报错。

#### 涉及模块与文件
- 扩展端：`src/utils/pushDataMapper.ts`（`mapRowToCaseItem` / `mapChineseRowToCaseItem`）、`src/handlers/fileCreator.ts`（模板）、`src/handlers/pushCore.stages.ts`（占位过滤前置阶段）。
- 配置：默认值可从系统级配置读取（与既有 `defaults` 配置结构一致）。

#### 核心数据结构
```ts
// 目标态：pushDataMapper 内新增精益字段兜底
const LEAN_FIELD_DEFAULTS = {
  keyFlag: '否',
  planExecNum: 1,          // 可由系统配置覆盖
  projectDes: '',         // 或占位说明文案
};
```

#### 关键流程
1. **占位过滤优先**：在 `pushCore.stages.ts` 既有「中文占位静默过滤 / 英文占位阻断」之后、`mapRowToCaseItem` 之前，样例行已被剔除，故兜底不会污染样例行。
2. **字段兜底**：`mapRowToCaseItem` 映射时，对上述字段读取为空（含仅空白）则填入 `LEAN_FIELD_DEFAULTS` 对应值；CSV 与 YAML 分支共用同一兜底表，行为一致。
3. **不强制回写源文件**：兜底仅在推送映射产物上生效（与现有字段默认值策略一致），是否回写源文件以系统配置为准。
4. **模板补充**：`fileCreator.ts` 在 CSV 模板增加 `keyFlag` / `planExecNum` / `projectDes` 列、YAML 模板增加 `key_flag` / `plan_exec_num` / `project_des` 字段（含默认占位），新增文件即具备完整结构。
5. **历史兼容**：解析层对缺失字段容忍，按「字段未提供」处理并走兜底；不强制回填源文件、不污染源文件。

#### 边界与防御
- 兜底层级严格位于占位过滤之后，避免样例行被写入默认值（AC-4）。
- 三字段同时缺失时统一走默认值，不重复拦截。
- 历史文件缺列不报「字段缺失」错误，仅按默认值处理并继续推送（AC-7）。

### 2.3 样例数据行冻结（需求 3.3）

#### 需求要点
`testcase_id` 为占位值的样例数据行整行只读，主表与展开子表均不可编辑 / 删除 / 复制 / 添加分组；推送前静默过滤；不参与校验修复。

#### 涉及模块与文件
- 扩展端：既有 `isSampleTsId` / `isFrozenRow`（位于 `pushCore.stages.ts` / `validators.ts` / `fileIdentifier.ts` 区域），推送过滤与校验修复入口复用。
- 前端：`02a-render.js`（只读渲染）、`03a-cell-edit.js`（拦截编辑提交）、`03d-row-ops.js`（隐藏操作入口）。

#### 核心数据结构
沿用既有 `isFrozenRow(row)` / `isSampleTsId(tsId)` 判定；新增前端只读标记 `S.frozenRowSet: Set<number>` 由 `init` 数据帧携带。

#### 关键流程
1. **只读渲染**：`init` 数据帧中样例行标记 `frozen=true`，`02a-render.js` 对其应用只读样式、`03a-cell-edit.js` 的 `commit` 直接 return。
2. **操作拦截**：`03d-row-ops.js` 对样例行不渲染编辑 / 删除 / 复制 / 添加分组按钮；触发时提示「样例数据行已冻结，不可操作」。
3. **推送过滤**：`pushCore.stages.ts` 按 `isSampleTsId` 静默剔除；全样例行时终止推送并提示行号。
4. **校验豁免**：`preValidate` / 校验修复跳过样例行（`isSampleTsId` 判定）。

#### 边界与防御
- 冻结判定以 `testcase_id` 占位值为唯一依据，不受其它字段影响。
- 冻结态跨刷新保留（来自 `init` 帧），与用户标记（`03e-mark.js`）物理隔离。

### 2.4 预期结果增加序号（需求 3.4）

#### 需求要点
步骤子表首列「步骤序号」已存在；新增「同一预期分组内多条预期按行显示连续序号」，仅展示、不写库。

#### 涉及模块与文件
- 前端：`03c-detail-modal.js`（预期分组渲染）、`03h-detail-helpers.js`（分组数据读取）。

#### 核心数据结构
```ts
// 目标态：预期分组内序号仅渲染态
interface ExpectedGroup {
  type: 'ui' | 'api' | 'db';
  items: { text: string; seq: number }[]; // seq 由渲染时按 index +1 生成
}
```

#### 关键流程
1. **步骤序号**：复用既有首列序号（增删自动重排，已有逻辑不改动）。
2. **预期序号**：`03c-detail-modal.js` 在渲染某预期分组（UI 检查 / 接口调用 / 数据检查）的多行预期时，按行内 `index` 叠加「预期 N」标签，随增删自动重排。
3. **不写库**：序号为纯展示层，不进入 `rawRowGroups` / 不回写源文件。

#### 边界与防御
- 序号与步骤序号视觉区分（前缀「预期」），避免混淆。
- 折叠态合并文本不含该序号，保持与展开态展示一致但数据层干净。

### 2.5 testcase_id TA 识别标识（需求 3.5）

#### 需求要点
`testcase_id` 命中 SDT 生成的 `testagent` / `testflow` 掩码（`TC` + 32 位掩码 uuid）时，单元格左侧显示绿色 `TA` 标签；不改原值；带悬浮提示。

#### 涉及模块与文件
- 扩展端（目标态）：`src/utils/maskUtil.ts` 新增 `detectSdtMask(testcaseId): boolean`（或复用既有掩码识别函数）。
- 前端：`02a-render.js` 单元格渲染（注入 `TA` 标签 DOM）、`init` 数据帧携带掩码判定结果。

#### 核心数据结构
```ts
// 目标态
interface TcCellMeta {
  value: string;
  isSdtMask: boolean;   // 命中 testagent/testflow 掩码
}
```

#### 关键流程
1. **判定**：`maskUtil.detectSdtMask` 校验 `testcase_id` 是否匹配 `testagent` / `testflow` 掩码规则；结果随 `init` 帧下发前端。
2. **渲染**：`02a-render.js` 对 `isSdtMask` 单元格在内容左侧渲染绿色椭圆 `TA` 标签，并加 `title="TC 掩码标识（testagent/testflow）：<原始值>"`。
3. **不改原值**：标签仅装饰层，单元格实际值不变；推送时仍按原始 `testcase_id` 路由到对应平台批次。

#### 边界与防御
- 掩码判定失败（格式异常）时降级为普通单元格，不阻断渲染。
- 标签不影响复制 / 推送取值逻辑。

### 2.6 空步骤展开自动初始化（需求 3.6）

#### 需求要点
空 `steps` 行点击展开时，内存态初始化一个空步骤结构（序号 1、空描述 / 预期 / 数据）；未实际录入不写回源文件；样例行豁免。本项为 `案例编辑器展开步骤功能需求.md` §3.1 的增强。

#### 涉及模块与文件
- 前端：`03c-detail-modal.js`（空步骤渲染）、`03h-detail-helpers.js`（空结构构造）、`03d-row-ops.js`（展开入口）。

#### 核心数据结构
```ts
// 目标态：空步骤初始化态（仅编辑会话内）
interface EmptyStepInit {
  rowIndex: number;
  inMemory: true;        // 标记尚未落盘
  touched: false;        // 用户是否实际录入
  step: { seq: 1; op: ''; data: ''; ui: ''; api: ''; db: '' };
}
```

#### 关键流程
1. **内存态初始化**：`steps` 为 `[]` / 缺失的行点击展开，`03h-detail-helpers.js` 构造单个空步骤对象并渲染子表，`touched=false`。
2. **录入写回**：用户在子表录入并失焦，`03a-cell-edit.js` 的 `commit` 写入 `rawRowGroups`，置 `touched=true` 并同步折叠态合并文本。
3. **保存落盘门槛**：保存时仅当 `touched=true` 才将 `steps` 以规范化结构落盘；若仅展开未录入，`steps` 保持原空 / 缺失，**不写回空步骤对象，避免污染源文件**。
4. **样例行豁免**：`isSampleTsId` 行展开不触发初始化，保持只读。
5. **撤销**：初始化及录入均纳入 `pushHistory()`，可回退到空步骤前。

#### 边界与防御
- 失焦无编辑时触发「还原」逻辑，确保不残留空步骤对象（AC-3）。
- 非空 `steps` 行的展开 / 收起行为维持原状，本增强仅作用于空步骤场景。

### 2.7 推送埋点任务信息（需求 3.7）

#### 需求要点
推送埋点补齐任务上下文：`testTaskNo` / `subTestTaskId` / `fileName`（仅文件名、脱敏）/ 匿名化用户标识；覆盖单文件与批量 `explorerPush.batch.*` 事件，支持跨任务批量（任务级字段按 `batch.fileResult` 逐文件携带）。

#### 涉及模块与文件
- 扩展端：`src/utils/telemetry.ts`（事件上报）、`src/handlers/pushCore.ts`（推送成功 / 失败事件触发点）、批量推送入口（资源管理器批量推送 handler）。
- 任务信息来源：`taskInfoStore`（`utils/taskInfoStore.ts`）提供 `testTaskNo` / `subTestTaskId`；用户标识取自当前会话（匿名化）。

#### 核心数据结构
```ts
// 推送事件统一携带的标准上下文字段
interface PushTaskContext {
  testTaskNo: string;
  subTestTaskId: string;
  fileName: string;          // 仅文件名，不含完整路径
  userIdHash: string;        // 匿名化用户标识，非明文 userName
}
// batch 级事件
interface BatchPushContext extends PushTaskContext {
  fileList: string[];        // 多文件名列表（batch 级汇总）
}
// batch.fileResult 逐文件携带各自任务信息
interface BatchFileResultContext extends PushTaskContext {
  filePath: string;
}
```

#### 关键流程
1. **上下文采集**：推送入口从 `taskInfoStore` 取 `testTaskNo` / `subTestTaskId`，从文件 basename 取 `fileName`，从会话取匿名化 `userIdHash`。
2. **单文件事件**：`editorPush.*` / `explorerPush.*` 的 `start` / `complete` / 失败事件统一附加 `PushTaskContext`。
3. **批量事件**：`explorerPush.batch.start` / `batch.done` 等携带 `BatchPushContext`；`batch.fileResult` 逐文件携带各自的 `BatchFileResultContext`（跨多测试任务时各文件任务信息独立）。
4. **脱敏**：`fileName` 仅取 basename；用户标识走哈希，不涉及明文个人信息。
5. **降级**：埋点上报异常不影响推送核心链路（异常在 `telemetry.ts` 内部 catch）。

#### 边界与防御
- 任务信息缺失（非任务上下文推送）时对应字段填空，不阻断上报。
- 批量跨任务场景，`batch.fileResult` 的任务字段以该文件实际归属任务为准，不与 `batch` 级汇总字段混淆。

### 2.8 适配TMS执行方式（UI自动化 / 接口自动化）（需求 3.8）

#### 需求要点
新增测试案例模板执行方式可选值含 `UI自动化` / `接口自动化`；推送前按执行方式严格白名单校验（`手工` / `UI自动化` / `接口自动化` / `自动化` / `半自动化`），合法透传、空 / 非法拦截，不回退默认值；TMS 导入归一后复用同一校验。

#### 涉及模块与文件
- 扩展端：`src/utils/pushDataMapper.ts`（`resolveTestType`）、`src/preValidate/`（推送前校验，`validators.ts` / `stepPreValidate.ts`）、`src/handlers/fileCreator.ts`（模板执行方式可选值）。
- 配置：白名单与归一表与既有 `testtype-whitelist-requirements.md` 保持一致。

#### 核心数据结构
```ts
// 沿用既有 resolveTestType 契约
const TEST_TYPE_WHITELIST = ['手工', 'UI自动化', '接口自动化', '自动化', '半自动化'];
function resolveTestType(raw: string, caseTag: string, rowIndex?: number): string {
  const v = toStr(raw).trim();
  if (!v) throw makeMapError('invalidTestType', caseTag, rowIndex, '未填写');
  if (!TEST_TYPE_WHITELIST.includes(v))
    throw makeMapError('invalidTestType', caseTag, rowIndex, `取值 "${v}" 不合法`);
  return v;
}
// TMS 归一（目标态，复用既有 normalizers.testType 规则）
const TMS_TEST_TYPE_NORMALIZE: Record<string, string> = {
  'UI': 'UI自动化', 'UI自动化': 'UI自动化', '接口': '接口自动化', '接口自动化': '接口自动化',
};
```

#### 关键流程
1. **模板含取值**：`fileCreator.ts` 在 CSV 模板「执行方式」列 / YAML `test_type` 字段的默认可选值中写入白名单五项（含 `UI自动化` / `接口自动化`），新增文件即具备完整结构。
2. **新增选择落盘**：新建时选择 `UI自动化` / `接口自动化`，文件对应字段正确写入该值（不归一、原样落盘）。
3. **推送前严格校验**：`resolveTestType` 在 `mapRowToCaseItem` / `mapChineseRowToCaseItem` 中调用，命中白名单保留并透传 `testType`；空 / 白名单外抛 `invalidTestType`，上层拼「第 N 行 案例 [xxx] 的执行方式不合法」提示，**无默认回退**。
4. **TMS 归一**：TMS 适配 / 导入阶段对执行方式做 `TMS_TEST_TYPE_NORMALIZE` 归一（如 UI 自动化类 → `UI自动化`），归一后进入同一 `resolveTestType` 校验。
5. **去空格保留**：输入先 `trim()` 再比对，带首尾空格的合法值去空格后保留、不报错。

#### 边界与防御
- 严格白名单与既有 `pushFailure` 的 `testType.enum` 分类一致，避免双重口径。
- 推送前校验与「推送字段默认值」兜底阶段顺序明确：先占位过滤 → 执行方式严格校验（拦截优先于兜底）→ 精益字段兜底，避免空执行方式被误兜底。
- 历史文件 / TMS 导入缺执行方式同样触发拦截提示，不静默入库。

---

## 3. 跨模块一致性与风险

- **校验顺序**：`pushCore.stages.ts` 各阶段顺序需固定为「占位过滤 → 执行方式严格校验（3.8）→ 精益字段兜底（3.2）→ 必填 / 长度 / 枚举校验」，保证拦截优先于兜底（3.8 AC-4/AC-5 与 3.2 不冲突）。
- **样例行豁免**：3.3 的冻结判定是 3.2 兜底不污染、3.6 不初始化的统一前置条件，判定函数（`isSampleTsId`）须全链路复用同一实现。
- **埋点降级**：3.7 的 telemetry 异常在 `telemetry.ts` 内部吞掉，绝不上抛至 `pushCore` 主链路。
- **不污染源文件原则**：3.2（历史兼容）、3.6（未录入不落盘）均强调不写回源文件，与既有「映射产物兜底、非强制回写」策略一致。
