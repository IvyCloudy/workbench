# YAML 格式检测与修复 — 需求文档

---

## 一、需求背景

用户提交的 YAML 案例文件在编写过程中常出现格式不规范的问题，例如缩进错乱、拼写型值被误判、注释截断数据等。这些格式问题会导致案例编辑器无法正常打开文件，用户看不到案例内容，更严重的是部分数据会在加载过程中丢失（比如重复字段覆盖、注释吞掉内容），存在数据安全风险。因此需要提供自动化的格式检测与修复能力，帮助用户快速修正问题，确保案例正常使用。

---

## 二、需求目的

围绕用户使用案例编辑器编辑 YAML 案例的完整流程，提供三个核心能力：

1. **编辑时自动提示**：用户编写过程中，编辑器实时检查格式问题，用红色波浪线（严重问题）和黄色波浪线（提醒问题）标注，鼠标悬停可查看问题说明；
2. **一键快速修正**：针对每个提示的问题，点击即可自动修复；也可以对整个文件一键批量修复所有问题；
3. **批量流水线处理**：将同样的检测修复能力独立打包为命令行工具，供自动化流程或 AI 助手调用，无需人工逐条处理。

---

## 三、功能清单

### 3.1 YAML 语法检测

#### 功能简述
用户在 VS Code 编辑器中打开或编辑 YAML 案例文件时，编辑器实时扫描文件内容，自动识别常见的格式错误，并在问题位置标注红色或黄色波浪线，问题详情列在下方问题面板中，点击即可跳转到对应行。

#### 功能内容

##### 3.1.1 可检测的问题类型

共 14 类格式问题，分为三个层级：

**第一层：逐行检查（8 类）**

编辑器按行逐一扫描，识别每行内的格式问题：

| 问题 | 严重程度 | 什么情况会触发 | 用户看到的例子 |
|------|---------|--------------|-------------|
| 文件头多余标记 | 提醒 | 文件最开头有一个不可见的特殊字符，可能导致解析出错 | 文件首行多了一个看不见的标记 |
| 使用了 Tab 缩进 | **严重** | 行开头用 Tab 键而不是空格键缩进，YAML 不允许 Tab 缩进 | `→→key: value`（Tab 键打出的缩进） |
| 行内有 Tab | 提醒 | 行中间（非缩进位置）出现了 Tab 字符 | 键值之间混入了 Tab |
| 行末多余空格 | 提醒 | 一行内容写完后，尾部还留有无意义的空格 | `key: value··`（末尾多打了空格） |
| 冒号后没留空格 | 提醒 | 键名后面的冒号直接跟了内容，中间没有空格分隔 | `key:value` 写成 `key:value` |
| 值的写法有歧义 | 提醒 | 值的写法恰好是 YAML 的保留词（如 yes/no/on/off/null 等），会被解析成其他含义而非普通文字 | 写了 `enabled: yes`，但系统可能把 `yes` 理解为"是/否"而非一个叫 yes 的数据 |
| 值中的 `#` 可能被截断 | 提醒 | 值的内容里出现了 `#` 号，YAML 会把 `#` 及之后的内容当作注释忽略 | 写了 `url: http://abc#section`，`#section` 会被当作注释丢掉 |
| 值的写法含特殊符号 | 提醒 | 值里用了大括号、方括号、星号、感叹号等特殊符号，会被 YAML 误解为语法标记 | 写了 `value: {a,b}` 但本意就是一段文字 |
| 列表项缺空格 | 提醒 | 列表项目符号 `-` 后面没留空格 | `-item` 写成 `-item` |

**第二层：全文检查（1 类）**

扫描整个文件，识别跨行的结构性问题：

| 问题 | 严重程度 | 什么情况会触发 | 为什么需要关注 |
|------|---------|--------------|--------------|
| 同一级别下字段名重复 | 提醒 | 同一层级中出现了两个名字完全相同的字段 | 后面写的会把前面的覆盖掉，导致数据丢失 |

**第三层：解析器兜底（5 类）**

前两层规则无法覆盖的深层问题，交给标准 YAML 解析库做最终把关：

| 问题 | 严重程度 | 什么情况会触发 |
|------|---------|--------------|
| 嵌套结构写法错误 | **严重** | 列表项里嵌套 map 层级不对，或一行里塞了多层键值对 |
| 引号忘了闭合 | **严重** | 写了前引号忘了后引号，引号不成对 |
| 缩进对不齐 | **严重** | 不同行的缩进层级混乱，子内容没对齐到父级 |
| 解析器发现重复字段 | **严重** | YAML 解析库本身报出重复 key（比第二层覆盖更广，包括花括号缩写写法里的重复） |
| 解析器非致命提醒 | 提醒 | 解析库产出的一般提醒，不做自动修复 |

> **备注**：第三层需要安装 YAML 解析库才能生效。如果没有安装，前两层仍然正常工作，第三层自动跳过，不影响使用。

##### 3.1.2 检测执行顺序

按"由浅入深"的顺序依次检查，前面的问题修正后可能会避免后面的误报：

1. 先检查文件头部是否有异常标记
2. 再逐行检查每行的格式问题（共 8 类）
3. 然后全文扫描是否有重复字段
4. 最后让解析库做一次完整的"语法编译"验证，产出第三层结果
5. 汇总所有发现的问题，在编辑器中展示

##### 3.1.3 性能优化

为保证大文件编辑体验不卡顿：

| 场景 | 处理方式 |
|------|---------|
| 普通文件（200KB 以内） | 用户停止输入半秒钟后启动检查 |
| 大文件（200KB 以上） | 延迟到 1 秒后才启动检查，减少频繁检查 |
| 刚执行完批量修复 | 短时间内不再重复检查，避免修复触发的连锁反应 |

##### 3.1.4 智能识别能力

- **准确区分"真冒号"和"假冒号"**：文件中可能出现各种冒号（引号里的冒号、花括号里的冒号、网址里的 `://`、双冒号 `::` 等），检测时能自动识别哪些冒号才是真正表示"键:值"分隔的，避免误报。
- **覆盖 17 种常见歧义关键词**：包括各种大小写形式的 yes/no、true/false、on/off、null、无穷大/NaN 等写法，确保这些词被当作普通字符串而非特殊值。

### 3.2 YAML 语法修复

#### 功能简述
针对 3.1 检测出的问题，提供"一键修复"能力。用户可以在问题处点击灯泡按钮单行修复，也可以右键或通过命令面板对全文件批量修复。修复后的文件可正常解析，且再次检查不会重复报同样的问题。

#### 功能内容

##### 3.2.1 各问题的修复方式

| 问题 | 怎么修复 | 补充说明 |
|------|---------|---------|
| 文件头多余标记 | 自动删除多余的标记 | 不影响文件其余内容 |
| Tab 缩进 | 每个 Tab 换成 2 个空格 | 符合 YAML 标准缩进要求 |
| 行内 Tab | 替换为 1 个普通空格 | 只替换不该出现 Tab 的位置 |
| 行末多余空格 | 清除行尾部所有空白 | 包括不可见的不间断空格也会清理 |
| 冒号后没留空格 | 在冒号后补上一个空格 | 如果补空格后值的写法仍有问题，会连带一起修复（比如 `enabled:yes` 会直接修复为 `enabled: "yes"`） |
| 值的写法有歧义 | 给值加上引号保护 | 智能选择用双引号还是单引号，避免和值里已有的引号冲突 |
| 值中 `#` 被截断 | 给值整体加上引号 | 只包裹"值是内容、`#` 不是注释"的那一段，不影响真正对齐写的注释 |
| 值的写法含特殊符号 | 给值加上引号保护 | 如果值本身就是合法的 YAML 语法（比如列表 `[a,b]`），则跳过不处理 |
| 列表项缺空格 | 在 `-` 后补上一个空格 | `--` 和 `---` 这种分隔线不处理 |
| 字段名重复 | 将重复出现的行改为注释 | 保留原内容在注释里，不删数据，方便审计 |
| 嵌套结构错误 | 优先尝试包裹列表项后面的值；如果不是列表项则包裹冒号后的值 | 必须从第一个冒号开始找，避免错误命中值内部的冒号 |
| 引号忘了闭合 | 检查单引号和双引号的数量，补齐缺少的闭合引号 | 单引号和双引号分别独立判断 |
| 缩进对不齐 | 将该行改为注释 | 非常复杂的缩进错乱，标记为注释，等人工检查 |
| 解析器重复字段 | 将该行改为注释 | 同字段名重复，保留原内容 |
| 无法识别的错误 | 将该行改为注释 | 兜底策略，无法自动修复的标记出来 |

##### 3.2.2 修复冲突处理

当一行同时触发多条修复规则时，按以下原则决定最终使用哪种修复：

- **一步到位优先**：如果补了空格之后还需要加引号，直接合并为加引号一次完成，不再分两步；
- **整体包裹优先**：如果值里有歧义关键字并且紧贴着 `#`，直接做整体加引号包裹，不分开处理；
- **同一条行不重复修**：如果一行已经被前几条规则修过了，不再用解析器兜底规则再改一次；
- **标记性修复后做**：凡是把行改成注释的修复（"破坏性修复"），留到最后一批统一执行，不和其他修复混在一起。

##### 3.2.3 批量修复

用户可以选择对整个文件一次性修复所有问题：

1. 收集整个文件所有检测到的问题
2. 从文件最后一行开始往前修（避免修复后行号变化导致的错位）
3. 每 100 行算一批，批间稍作停顿保持编辑器流畅
4. 所有修复合并为一个撤销操作，用户按一次撤销键就能全部回滚
5. 修复完成后重新检查文件，告知用户"共修复了多少处，还剩多少处问题"

##### 3.2.4 修复的准确性保障

部分深层问题（如嵌套结构错误）在修复过程中，可能因为修好一个错误后暴露出之前隐藏的其他错误。针对这种情况，修复会执行多轮"检查→修复→再检查"的循环，直到没有新问题出现。每轮修复前会对比内容是否变化，避免进入死循环，最多执行 5 轮。

##### 3.2.5 编辑器内的操作入口

用户可以通过以下方式触发修复：

| 操作方式 | 效果 |
|---------|------|
| 点击波浪线 → 点灯泡按钮 | 只修复当前这一行 |
| 右键菜单 → 修复全部 | 修复整个文件所有 error 和 warning |
| 命令面板 → 修复严重问题 | 只修复红色波浪线标注的问题（error 级） |
| 命令面板 → 修复提醒问题 | 只修复黄色波浪线标注的问题（warning 级） |
| 选中多行 → 右键修复 | 只修复选中范围内的行 |
| 状态栏按钮 / 命令面板 | 展示当前文件有多少个可修复的问题，用户选择执行 |

### 3.3 YAML 检测修复命令行工具（Skill）

#### 功能简述
将 3.1 和 3.2 的检测修复能力独立打包成命令行工具，提供 Node.js 和 Python 两种版本，与编辑器内的规则完全一致。AI 助手只需调用命令行即可完成修复，无需把文件内容读进对话，既节省 Token 成本，又避免 AI 直接修改内容带来的风险。

#### 功能内容

##### 3.3.1 产品定位

| 特性 | 说明 |
|------|------|
| **AI 友好** | AI 不用读文件、不用自己写修复、不用描述文件内容。只需要决定用 JS 版还是 Python 版，然后调用命令行，把返回结果告诉用户即可 |
| **双版本** | Node.js 和 Python 3.8+ 版本，检测修复规则与编辑器版完全一致 |
| **基础版开箱即用** | 不装任何额外软件就能用，覆盖前两层 10 类问题 |
| **增强版可选升级** | 安装了 YAML 解析库后自动启用第三层 5 类问题的检测与修复，共 14 类。不需要也不影响基础版 |
| **结果确定可重复** | 同样的文件每次检测修复的结果完全一致，不会有随机性 |

##### 3.3.2 运行模式

| 模式 | 用途 |
|------|------|
| 默认模式 | 检测文件并直接写入修复后的内容 |
| 预览模式 | 只看有哪些问题、会怎么修，不改文件，适合先看一眼再决定 |
| 详细模式 | 输出每条问题的详细信息，包括修复前后的行内容对比 |
| JSON 模式 | 输出机器可读的结构化数据，适合接入自动化流水线 |

##### 3.3.3 输出内容

运行后输出以下信息：

| 内容 | 说明 |
|------|------|
| 当前能力级别 | 是增强版还是基础版（有没有启用解析器兜底） |
| 问题数量 | 严重问题有多少个，提醒问题有多少个 |
| 可修复数量 | 其中有多少个是可以自动修复的 |
| 问题明细 | 每条问题列出：属于哪条规则、在第几行第几列、严重程度、问题描述、能否自动修复 |
| 修复结果 | 实际修复了多少行、多少行跳过没修、修复后还剩几个严重问题 |

##### 3.3.4 执行结果判断

| 返回码 | 含义 | 后续处理建议 |
|--------|------|------------|
| `0` | 所有严重问题已修复完成 | 流程通过 |
| `2` | 还有严重问题没修完 | 需要人工检查或再跑一次 |
| `1` | 工具运行出错（文件找不到、没权限等） | 检查环境和文件 |

部分深层问题可能需要跑 1~2 次才能完全修干净，工具会在输出中给出提示。

##### 3.3.5 处理流程

1. 解析用户传入的运行参数，确定使用哪种模式和哪个语言版本
2. 检查 YAML 解析库是否安装，决定用增强版还是基础版
3. 读取文件完整内容
4. 执行第一轮检测（基础 10 类 + 增强 4 类）
5. 如果不是预览模式，从最后一行往前逐行应用修复
6. 对修复后的内容再检测一遍，确认问题数量变化
7. 如果解析器级问题还没清完，自动多轮修复（最多 5 轮，每轮确认有变化才继续）
8. 不是预览模式的话，把修复结果写回文件
9. 输出结果，返回执行结果码

##### 3.3.6 与编辑器版的一致性

命令行版和 VS Code 编辑器版基于同一套规则定义，保证以下几点完全一致：

- 检测规则的定义、执行顺序、判断标准
- 歧义关键词、特殊符号、豁免情况的配置
- 冒号识别逻辑（区分真冒号和假冒号）
- 重复字段的检测逻辑（含列表项独立作用域）
- 引号包裹策略和智能选择逻辑

##### 3.3.7 文件说明

| 文件 | 作用 |
|------|------|
| `SKILL.md` | AI 助手调用说明，定义交互协议 |
| `README.md` | 用户手册，包含快速开始、配置和流水线对接指引 |
| `scripts/fix-yaml.js` | Node.js 版执行入口 |
| `scripts/fix_yaml.py` | Python 版执行入口（与 JS 版完全对等） |
| `references/detection-rules.md` | 检测规则详细参考 |
| `references/fix-strategies.md` | 修复策略详细参考 |

## 四、整体架构

功能在两个位置运行，共享同一套检测修复规则：

- **VS Code 编辑器内**：用户打开 YAML 文件时自动生效。实时检查 → 波浪线标注 → 灯泡菜单一键修复 → 右键批量修复。
- **命令行工具**：独立于编辑器，可被 AI 助手或自动化流水线调用。读取文件 → 检测修复 → 输出结果 → 返回执行状态。

两个位置使用完全相同的检测规则和修复策略，保证用户在不同场景下看到的检测结果和修复行为完全一致。

## 五、验收标准

| 编号 | 验收项 | 标准 |
|------|--------|------|
| AC-1 | 问题覆盖 | 覆盖全部 14 类格式问题 |
| AC-2 | 检测准确 | 正常 YAML 文件不误报，已知问题不漏报 |
| AC-3 | 修复可靠 | 同一文件连续修复两次，第二次不再有新问题产生 |
| AC-4 | 修复正确 | 修复后的文件可正常解析，原始数据含义不变 |
| AC-5 | 双版本一致 | JS 和 Python 命令行工具对同一文件的检测结果和修复内容完全相同 |
| AC-6 | 降级可用 | 没有安装 YAML 解析库时，基础版 10 类问题照常检测修复，不报错 |
| AC-7 | 大文件性能 | 一万行以内的 YAML 文件，检测加修复可在 2 秒内完成 |
| AC-8 | 结果可靠 | 无严重问题返回码为 0，有剩余问题返回码为 2，工具异常返回码为 1 |
