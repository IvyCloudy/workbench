# 推送失败度量说明

> 版本：v1.6 ｜ 更新日期：2026-08-06
> 关联文件：`src/utils/pushFailureCategory.ts`、`src/handlers/pushHandler.ts`、`src/handlers/pushCore.ts`
> 关联文档：`埋点事件清单.md`、`插件运营指标体系.md`

本文档说明「推送失败信息」如何被采集、归类、聚焦字段，以及如何在埋点/看板中完成度量分析。
核心目标：**后端每一条失败都能被稳定归类（category）+ 下钻到具体接口字段（field），不留 `undefined` 维度黑洞**。

---

## 1. 失败信息的两个正交维度

每条失败用 `PushFailureItem` 表达（定义于 `pushCore.ts`）：

```ts
export interface PushFailureItem {
    tsId: string;            // 案例唯一标识
    reason: string;          // 后端/客户端返回的中文原文（用于展示，不稳定，不做聚合）
    rowIndex?: number;       // 主表 1-based 行号
    category?: PushFailCategory;   // 稳定分类码（统计/埋点用）
    field?: PushInterfaceField;    // 命中的接口字段码（聚焦维度，字段类错误才有值）
}
```

- **reason（中文原文）**：只用于 UI 弹窗展示，措辞多变、长度大，绝不直接进聚合或埋点。
- **category（英文短码）**：失败大类，稳定可枚举，供统计聚合与埋点维度。
- **field（字段码）**：与 category 正交的第二维度，表示「命中了哪个接口必填字段」，用于埋点 `failFieldBreakdown` 与前端「按字段引导纠错」。

> 设计原则：用户仍看到完整中文 reason，统计/埋点只看稳定 `category` + `field`，既准又省 payload（避免中文长文本撑爆埋点 8KB 上限）。

## 2. 分类体系（category）

字段类错误采用**复合码 `字段.性质`**（如 `testCaseName.empty` / `testCasePath.empty` / `sourceId.dup` / `testCasePath.length`），由"命中的接口字段 + 错误性质"两段合成。`failCategoryBreakdown` 单看分类即可定位「哪个字段、出了什么问题」，不再被统一的 `fieldInvalid` 掩盖。性质固定为 `empty`/`length`/`format`/`enum`/`dup` 五种；取不到字段时落下列性质级兜底分类。

| category | 含义 | 来源 |
|---|---|---|
| `placeholder` | testcase_id 为占位值 TESTCASE_ID | 客户端预校验（结构化信号） |
| `emptyTestcaseId` | testcase_id 为空 | 客户端预校验 |
| `sample` | 样例占位数据（不可推送；"为样例数据，不允许推送…"） | 客户端预校验 |
| `emptyFile` | 文件无数据/无有效数据（前置拦截，未进 runPush） | 前端文件级拦截文本归类 |
| `fileError` | 文件级前置拦截（不在合规目录/读文件失败/CSV·JSON 解析失败，早于 runPush） | 前端文件级拦截文本归类 |
| `mapError` | 字段映射错误兜底；已知字段/性质的映射错误优先拆为 `${field}.${nature}` 复合码（如 `sourceId.empty`/`description.empty`/`expected.empty`/`testCasePath.format`/`testType.enum`） | 客户端映射（结构化信号） |
| `network` | 网络/超时 | 后端中文文本归类 |
| `auth` | 鉴权/权限/未登录 | 后端中文文本归类 |
| `yamlSyntax` | YAML 语法/解析错误（文件级前置拦截，早于 runPush，由 pushHandler 在解析前拦截） | 前端文件级拦截文本归类 |
| `${field}.dup` | 字段重复/已存在（如 `sourceId.dup` / `testCasePath.dup`）；取不到字段落 `fieldDup` | 后端中文文本归类 |
| `${field}.empty` | 必填字段为空（如 `testCaseName.empty`）；取不到字段落 `fieldEmpty` | 后端中文文本归类 |
| `${field}.length` | 字段长度超限（如 `artifactId.length`）；取不到字段落 `fieldLength` | 后端中文文本归类 |
| `${field}.format` | 字段格式非法（如 `testCasePath.format`）；取不到字段落 `fieldFormat` | 后端中文文本归类 |
| `${field}.enum` | 行内枚举值非法（如 `type.enum`/`priority.enum`/`testType.enum`）；取不到字段落 `enumInvalid` | 后端中文文本归类 |
| `fieldDup` | 重复/已存在（性质级兜底：无法定位具体字段时） | 后端中文文本归类 |
| `fieldEmpty` | 必填字段为空（性质级兜底） | 后端中文文本归类 |
| `fieldLength` | 字段长度超限（性质级兜底） | 后端中文文本归类 |
| `fieldFormat` | 字段格式非法（性质级兜底） | 后端中文文本归类 |
| `enumInvalid` | 行内枚举值非法（性质级兜底） | 后端中文文本归类 |
| `checkpointZero` | 案例检查点数为 0 | 后端中文文本归类 |
| `stepMismatch` | 步骤描述与预期结果数量不一致 | 后端中文文本归类 |
| `taskStageMissing` | 测试任务编号未匹配到有效阶段信息（早于 auth） | 后端中文文本归类 |
| `fieldInvalid` | 字段类兜底（无法定位到具体性质的字段错误） | 后端中文文本归类 |
| `paramFormat` | 接口请求参数格式/校验错误（整批失败，区别于行级字段格式错 `fieldFormat`；文本形如「参数格式不对，请检查参数」「请求参数格式不正确」「参数校验失败」） | 后端中文文本归类 |
| `notFound` | 其他不存在/未找到（兜底，具体业务已拆到下方细分类） | 后端中文文本归类 |
| `taskNotFound` | 任务不存在/未绑定/未找到（资源=测试任务） | 后端中文文本归类 |
| `testPointMissing` | 任务下未匹配到有效测试要点（资源=测试要点，field=testPoint） | 后端中文文本归类 |
| `pathNotMatchPoint` | 案例路径错误未匹配到有效测试要点（field=testCasePath） | 后端中文文本归类 |
| `serverError` | 服务端异常/5xx | 后端中文文本归类 |
| `sourceNotSupported` | 案例来源不被支持/无效（资源=案例来源平台，已从 bizReject 拆出） | 后端中文文本归类 |
| `bizReject` | 其他明确业务拒绝（不含案例来源类） | 后端中文文本归类 |
| `unknown` | 兜底（无法归类的后端文本） | 兜底 |

### 归类优先级（两段式：`BACKEND_TOP_RULES` + `BACKEND_NATURE_RULES`，先命中先生效）

**第一段 `BACKEND_TOP_RULES`（顶层稳定分类，命中即返回，不再下钻字段）：**
1. `yamlSyntax`（YAML 语法/解析错误/文件解析失败——文件级前置拦截文本，最早命中，避免被其余规则误吞）
2. `network`（超时/timeout/网络/连接失败/ECONN…）
2. `taskStageMissing`（仅精准匹配「阶段信息」——早于 auth，下钻到 testTaskNo）
3. `auth`（鉴权/权限/未登录/token/无权限/401/403…）
4. `sourceNotSupported`（不支持案例来源/无效的案例来源——精准匹配，已从 bizReject 拆出）
5. `bizReject`（不支持/不允许/拒绝——仅兜底其他明确业务拒绝，不含案例来源类）
6. `taskNotFound`（任务不存在/未绑定/未找到——早于 notFound 兜底）
7. `pathNotMatchPoint`（案例路径错误未匹配到有效测试要点——早于 testPointMissing，下钻到 testCasePath）
8. `testPointMissing`（未匹配到有效测试要点——下钻到 testPoint）
9. `notFound`（不存在/未找到/查无/404…——兜底，放在细分类之后）
10. `stepMismatch`（步骤描述与预期结果数量不一致——性质唯一，无需复合）
11. `checkpointZero`（案例检查点数为 0——性质唯一，无需复合）
12. `fieldInvalid`（字段类兜底：无法定位具体性质，极窄匹配，避免抢走下方字段级错误）
13. `serverError`（服务[器端]?/5xx(需紧跟错误语境)/系统异常…——`5\d\d` 已收窄，避免误伤「长度不能超过500个字符」）
14. `paramFormat`（接口请求参数格式/校验错误，如「参数格式不对，请检查参数」——整批失败，区别于行级字段格式错 `fieldFormat`，排在 `fieldInvalid` 之后、字段级性质规则之前）

**第二段 `BACKEND_NATURE_RULES`（字段级性质，命中后取接口字段合成 `字段.性质` 复合码；取不到字段则落性质级兜底）：**
14. `enum`（无效的案例类型/优先级/执行方式 等——合成 `type.enum`/`priority.enum`/`testType.enum`，落 `enumInvalid`）
15. `dup`（已存在/重复/冲突——合成 `sourceId.dup`/`testCasePath.dup`，落 `fieldDup`）
16. `length`（xxx 长度不能超过 N 个字符——合成 `artifactId.length` 等，落 `fieldLength`）
17. `empty`（xxx 不能为空 / 案例信息不能为空 / 缺失 / 未填写——合成 `testCaseName.empty` 等，落 `fieldEmpty`）
18. `format`（格式/不合法/必须以?结尾/关键案例格式——合成 `testCasePath.format` 等，落 `fieldFormat`）

> 结构化信号（validatorKind / mapErrorReason）优先级最高，直接映射，不走中文文本。

## 3. 字段聚焦体系（field）

`PushInterfaceField` 覆盖推送接口主要入参，分两层级别（`FIELD_LEVEL`）：

- **interface（接口级公共参数）**：一次错 = 整批失败
  `testTaskNo` / `subTestTaskId` / `artifactId` / `sourcePlatform` / `designer`
- **case（caseList[] 行级字段）**：每行独立
  `sourceId` / `testCasePath` / `testCaseName` / `testCaseDes` / `description` / `expected` / `priority` / `type` / `preCondition` / `keyFlag` / `projectDes` / `planExecNum` / `testType`
  扩展码：`caseInfo`（案例信息整行必填）/ `testPoint`（测试要点）/ `stepSeq`（步骤/预期数量一致性）
  冷门资源码（v1.6 新增，承载 `notFound`/`fieldInvalid` 类报错中常见但非主流程字段的资源维度下钻）：`caseLib`（用例库）/ `tag`（标签）/ `module`（模块）/ `env`（环境）/ `owner`（负责人/归属人，区别于 `designer` 设计人）

### 抽取规则

- 仅当 category 属于 `FIELD_RELATED_CATEGORIES`（`fieldEmpty`/`fieldLength`/`fieldFormat`/`enumInvalid`/`checkpointZero`/`stepMismatch`/`taskStageMissing`/`fieldInvalid`/`mapError`/`placeholder`/`emptyTestcaseId`/`fieldDup`/`notFound`/`taskNotFound`/`testPointMissing`/`pathNotMatchPoint`/`sourceNotSupported`/`bizReject`）时才从 reason 抽取字段码，避免 `network`/`auth` 文本偶含「名称」被误标。
  - v1.6 变更：原枚举中的 `duplicate` 为死代码（归类器实际返回 `fieldDup`/`字段.dup`），已从 `FIELD_RELATED_CATEGORIES` 与 `PushFailCategory` 联合类型中移除，避免手动传 `category:'duplicate'` 时静默丢失字段维度。
- 别名顺序敏感：把含「案例」前缀、更具体的短语排前（`sourceId` 的「案例已存在」、`stepSeq` 的「数量不一致」均需在通用别名前命中）。
- 结构化信号优先：`mapErrorReason` → 已知字段并拆为 `${field}.${nature}` 复合码（如 `missingTestcaseId` → `sourceId.empty`、`invalidTestType` → `testType.enum`）；`validatorKind` → `placeholder`/`emptyTestcaseId`/`sourceId.format`（`invalidFormat` 即 testcase_id 不符合案例唯一标识规范）。

## 4. 真实后端报错场景覆盖映射

所有场景均经 `classifyFailure` 落到 category，并经 `failureFieldOf` 抽到 field。**字段类场景无 `undefined`；纯非字段类（`network`/`auth`/`serverError`/`bizReject` 等原文不点名字段的）本就无 field，符合设计——它们不计入 `failFieldBreakdown`（`aggregateByField` 中 `if (!field) continue`）。**

## 5. 度量方式（埋点事件与聚合）

### 5.1 数据聚合函数（util 层，单文件/批量通用）

| 函数 | 作用 |
|---|---|
| `aggregateFailures(items, maxSamples)` | 按 `category` 分桶，count 降序，保留最多 maxSamples 条不重复 reason 样本 |
| `summarizeCategoryBreakdown(stats)` | 压成 `category:count` 紧凑串（如 `testCaseName.empty:12,testCasePath.length:5,sourceId.dup:3`），供埋点 |
| `aggregateByField(items, maxSamples)` | 按 `field` 分桶，自动写入 `level`（interface/case），count 降序 |
| `summarizeFieldBreakdown(stats, level?)` | 压成 `field:count` 串；可指定 `level` 输出 interface/case 子集 |
| `topFieldOfLevel(stats, level)` | 取某层级中 count 最高字段（埋点 `topInterfaceFailField` / `topCaseFailField`） |

### 5.2 埋点事件（已贯通失败维度）

失败埋点**不是只有文件推送才有**——所有推送路径（资源管理器右键、批量、案例编辑器内）最终都汇聚到核心 `runPush`，其结局事件统一携带失败分类/字段维度。区别在于**事件前缀**与**是否合并上报**：

| 入口 | 触发方 | telemetryPrefix | 结局事件 | skipCompleteTelemetry |
|---|---|---|---|---|
| 资源管理器右键（单文件） | `handleFilePush` | `explorerPush` | `explorerPush.complete` | false（正常发） |
| 资源管理器右键（多文件/文件夹） | `handleFilePush` | `explorerPush` | `explorerPush.batch.fileResult` + `batch.done` | true（跳过单文件 .complete，避免重复计数） |
| 案例编辑器内（webview 点推送） | `BaseEditorProvider` | `editorPush` | `editorPush.complete` | false（正常发） |

#### 单文件结局事件：`*.complete`（右键单文件 / 编辑器内共用一套 props）

无论前缀是 `explorerPush` 还是 `editorPush`，`runPush` 在 `onComplete` 时发出 `${telemetryPrefix}.complete`，携带维度完全一致：

- 基础：`pushResult`(allSuccess/allFail/partial) / `totalRows` / `successRows` / `failedRows` / `preValidationFailedRows` / `costMs`
- 失败分类：`failCategoryBreakdown` / `topFailCategory`（由 `aggregateFailures(mergedFailures, 3)` 算出）
- 失败字段：`failFieldBreakdown` / `topFailField` / `interfaceFailBreakdown` / `topInterfaceFailField` / `caseFailBreakdown` / `topCaseFailField`（由 `aggregateByField` 算出）
- 弱分类样本：`taskNotFoundSamples` / `testPointMissingSamples` / `pathNotMatchPointSamples` / `sourceNotSupportedSamples` / `unknownSamples`（原文样本，截断 200 字）
  - 特例：`unknownSamples` 收集**全部**未归类原文（不受 `aggregateFailures` 的 3 条样本上限约束，去重后全量拼接），便于后台完整回流、补归类规则。

> 即：**案例编辑器内的失败同样会被归类 + 字段下钻，并上报到 `editorPush.complete`**，与文件推送口径一致。做全量失败分析时，须合并 `editorPush.complete` 与 `explorerPush.complete`/`batch.done` 两个前缀。

#### 批量推送（多文件/文件夹）两条关键事件

- `explorerPush.batch.fileResult`（逐文件）
  - 基础：`ext` / `resultType`(success|error|partialFail) / `totalRows` / `successRows` / `failedRows`（与 `*.complete` 命名一致）
  - 失败分类：`failCategoryBreakdown` / `topFailCategory`
  - 失败字段：`failFieldBreakdown` / `topFailField` / `interfaceFailBreakdown` / `topInterfaceFailField` / `caseFailBreakdown` / `topCaseFailField`

- `explorerPush.batch.done`（批次汇总）
  - 基础：`fileCount` / `totalRows` / `successRows` / `failedRows` / `errorFiles` / `cancelled` / `durationMs` / `extBreakdown`（行级 `totalRows`/`successRows`/`failedRows` 与单文件 `*.complete` 命名一致；`fileCount`/`errorFiles` 为批量特有的文件维度）
  - 失败分类：`failCategoryBreakdown` / `topFailCategory`
  - 失败字段：`failFieldBreakdown` / `topFailField` / `interfaceFailBreakdown` / `topInterfaceFailField` / `caseFailBreakdown` / `topCaseFailField`
  - 样本：`taskNotFoundSamples` / `testPointMissingSamples` / `pathNotMatchPointSamples` / `sourceNotSupportedSamples` / `unknownSamples`（原文字节流，截断 200 字，便于排查未匹配/未知类；`unknownSamples` 为全量未归类原文，不受 3 条上限约束）

> 异常兜底：`batch.done` 计算若抛错，会重新基于 `results` 安全累加真实 `successRows`/`failedRows`/`errorFiles` 并带 `summaryError=1` 上报，绝不清零。

### 5.3 可开展的度量分析

| 分析目标 | 维度组合 | 示例查询 |
|---|---|---|
| 每日推送失败总量趋势 | 合并 `editorPush.complete.failedRows` + `explorerPush.complete.failedRows` + `batch.done.failedRows` + 时间 | 监控失败率是否随版本下降（须合并 editorPush/explorerPush 两前缀） |
| Top 失败类型 | `failCategoryBreakdown` / `topFailCategory` | `testCaseName.empty`/`testCasePath.empty`/`sourceId.dup` 等复合码直接定位「哪个字段 + 什么问题」最多，已无需再交叉 field 维度 |
| 哪些字段最易错 | `failFieldBreakdown` / `topFailField` | `testCasePath` 高频 → 引导用户检查路径格式；字段级复合码 `字段.性质` 已自带字段语义 |
| 接口级 vs 行级失败分布 | `interfaceFailBreakdown` vs `caseFailBreakdown` | 区分「一次错整批挂」与「零散行错」 |
| 未匹配/未知类排查 | `testPointMissingSamples` / `pathNotMatchPointSamples` / `taskNotFoundSamples` / `unknownSamples` | 定位后端新增未覆盖报错文案（testPointMissing 任务下未匹配，pathNotMatchPoint 路径错误未匹配） |
| 业务拒绝来源平台 | `sourceNotSupported` + `sourcePlatform` field | 哪个来源平台被拒最多（已从 bizReject 拆出） |

### 5.4 度量注意事项

1. **层级区分**：`interface` 级一次错 = 整批失败，count 会被放大；看板应分 `interfaceFailBreakdown`/`caseFailBreakdown` 两层，避免 `designer` 无权限导致 100 行失败在 count 上「淹没」真实的行级 `description` 分布。
2. **unknown 监控**：`unknown` 占比上升 = 后端新增未覆盖文案，应回流补充 `BACKEND_CATEGORY_RULES`。
3. **字段维度完整性**：`aggregateByField` 对 `field=undefined` 的失败直接跳过（`if (!field) continue`），故 `failFieldBreakdown` 仅含字段类报错。字段类场景（含 v1.6 新增的 caseLib/tag/module/env/owner）均已能下钻到具体字段；纯非字段类（`network`/`auth`/`serverError`/`bizReject` 及原文不点名字段的 `fieldInvalid`/`notFound`）不计入字段维度，属设计预期，不代表维度黑洞。回归测试断言覆盖所有字段类场景 `field` 非空。
