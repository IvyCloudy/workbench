- **状态**：待实现

---

## 功能简述

本功能对推送到 TMS 的案例内容做**统一的合法性校验**，在内容到达 TMS 之前提前发现问题，降低"半成品被推上去有合规风险"和"字段填错导致推送失败"两类问题。

**解决的问题**
- 案例含「待补充」等未写完内容（合规风险）；
- 枚举字段取值非法、数据类型不符（会导致 TMS 直接拒绝、推送失败）。

**提供的能力**
- **编辑期即时可见**：案例文件在编辑器中打开时，自动高亮不合法内容（黄色=待补充，红色=枚举/类型错误），悬停显示原因，修正后实时消除。
- **推送前兜底拦截**：点击推送时自动校验，命中问题弹窗提示，列出具体案例、命中字段与原因，并支持复制案例 ID 定位。
- **分层处理**：「待补充」等质量类问题为软拦截、可忽略继续；枚举非法 / 类型不符等失败类问题为强制阻断、须修正后才能推送。

**校验范围**
- 文本字段（操作步骤 / 步骤数据 / 预期结果 / 前置条件 / 名称 / 描述）做「待补充」字面量匹配；
- 枚举字段（案例类型 / 执行方式 / 优先级 / 关键标识）做取值合法性校验；
- 数据类型字段（计划执行次数）做类型校验。
- 对 csv / json / yaml 等案例文件均生效（csv 按中文列名识别字段）。

## 1. 背景与用户场景

各团队把测试案例推送到 TMS（测试用例管理系统）时，最常见、影响最大的几类内容问题，当前都缺乏前置拦截，要么"半成品被推上去有合规风险"，要么"字段填错导致推送直接失败"。归纳为以下场景：

**场景一：案例内容未写完（「待补充」占位）**
- 抽查发现仍有大量案例的**步骤（操作）**和**预期结果**里直接写着「待补充」——也就是还没写完就推上去了。
- 这类案例如果被监管或审计抽查到，属于明显的不合规、不完整的用例，存在考核与合规风险。

**场景二：枚举字段取值不合法，导致推送失败**
- 案例类型、执行方式、优先级、关键标识（key_flag）等字段有固定的允许取值（如执行方式只能是"手工/自动化"）。
- 实际编写中，用户随手填了任意文本、或留空、或填了已废弃的取值，推送时因字段值不在系统允许集合内而被 TMS 拒绝，**推送直接失败**，只能回头逐个排查是哪个字段、哪条案例填错，排错成本高。

**场景三：数据类型不符，导致推送失败**
- 部分字段对数据类型有约定（如计划执行次数 plan_exec_num 应为数值）。
- 当该字段被误填为文本、空值或负数等非数值内容时，后端/接口解析报错，**推送同样直接失败**，且报错往往指向整条案例而非具体字段，定位困难。

用户的共同痛点：
- 目前推送前没有任何提醒，大家很容易在没注意的情况下把半成品、或字段填错的案例推上去；要么有合规风险，要么直接推送失败、反复重试。
- 失败后缺乏"是哪条案例、哪个字段、什么原因"的明确指引，排查全靠人工。

**核心诉求**：在案例推送到 TMS 之前，先对内容做一次统一校验——既拦截「待补充」这类不完整内容（防合规风险），也提前发现枚举非法、类型不符这类会导致推送失败的不合法内容（防推送失败、降排错成本）——给用户一个"拦截 + 提醒 + 可定位"的缓冲。

## 2. 需求

### 2.1 总体要求
本需求对"推送到 TMS 的案例内容"建立**统一的合法性校验**，目标是在内容到达 TMS 之前，把两类问题挡在门外：
- **质量风险**：案例含「待补充」等未写完内容（合规风险）；
- **推送失败风险**：枚举取值非法、数据类型不符等导致 TMS 直接拒绝（重复重试、排错成本高）。

整体框架如下：
- **三种校验机制，互不替代**：
  1. 文本字段 → 「待补充」字面量匹配（防未写完）；
  2. 枚举字段 → 取值合法性校验（防非法取值）；
  3. 数据类型字段 → 数据类型校验（防类型错误）。
- **两个触发入口，共用同一规则**：
  1. 打开案例文件时 → 自动高亮不合法内容（编辑阶段即时可见）；
  2. 点击推送时 → 自动校验兜底（拦截 + 弹窗提醒）。
- **分层处理原则**（按问题性质区分，避免"可忽略"与"防推送失败"互相矛盾）：
  - **质量类问题**（「待补充」等未写完内容，属合规风险）：**软拦截**——列出具体案例 + 命中字段 + 原因 + 支持复制案例 ID 定位，用户可**忽略并继续推送**。
  - **失败类问题**（枚举非法 / 数据类型不符，会导致 TMS 直接拒绝、必然推送失败）：**强制阻断**——不允许忽略，提示明确告知"将导致推送失败，请修正后再推送"，用户须修正后才能推送。

以下各小节分述"触发交互 / 校验内容与规则 / 命中处理"。

---

### 2.2 校验触发与交互
#### 2.2.1 打开文件时自动高亮
案例文件（csv / json / yaml 等）在案例编辑器中打开时，系统自动扫描内容，并对不合法处做**视觉高亮**，让用户在编辑阶段就能立即发现问题，而不必等到推送才暴露。
- **「待补充」文本**：所在单元格/行高亮（**黄色**底色 + 标记），悬停提示"含『待补充』，请完善"。
- **枚举取值非法 / 数据类型不符**：对应单元格高亮（**红色**边框/底色），悬停提示具体原因（如"执行方式应为 手工/自动化""计划执行次数应为数字"）。
- **高亮粒度**：定位到具体单元格；对 json / yaml 多步骤数组，定位到对应步骤行，确保能精确指向问题位置。
- 高亮为**只读提示**，不阻止编辑；修正内容后高亮实时消除。
- **性能**：扫描为异步/增量执行，避免大文件打开时卡顿。

#### 2.2.2 推送前自动校验
每次把案例推送到 TMS 之前，系统自动检查本次要推送的案例内容，不依赖用户手动检查。
- 该入口与 2.2.1 共用同一套校验规则与字段清单，保证两处口径一致。
- 命中后的具体提示与处理见 2.4。

---

### 2.3 校验内容与规则
#### 2.3.1 检查字段
以下字段需纳入校验，字段按 yaml 模版与 csv 模版一一对应（csv 以中文列名呈现）。

**必查字段（高风险）：**
- 操作步骤：yaml `steps[].operation` ↔ csv「步骤描述」
- 步骤数据：yaml `steps[].data` ↔ csv「步骤描述」（csv 步骤与数据合一，统一在该列校验）
- 预期结果：yaml `ui_expected` / `api_expected` / `db_expected`（三条检查点均需覆盖） ↔ csv「预期结果」
- 前置条件：yaml `preconditions` ↔ csv「前置条件」
- 案例类型：yaml `type` ↔ csv「案例类型」
- 执行方式：yaml `test_type` ↔ csv「执行方式」
- 优先级：yaml `priority` ↔ csv「优先级」
- 关键标识：yaml `key_flag` ↔ csv「关键标识」
- 计划执行次数：yaml `plan_exec_num` ↔ csv「计划执行次数」

**建议补充核查字段（信息完整性，走文本「待补充」匹配）：**
- 案例名称：yaml `name` ↔ csv「名称」
- 案例描述：yaml `description` ↔ csv「案例描述」

**可选字段（按团队需要开启，默认关闭；开启后同样走文本「待补充」匹配）：**
- 案例标签：yaml `tags` ↔ csv「案例标签」

**说明：**
- 字段校验机制归属：**文本字段**（操作 / 步骤数据 / 预期 / 前置条件 / 名称 / 描述 / 标签）走 2.3.2「待补充」字面量匹配；**枚举字段**（案例类型 / 执行方式 / 优先级 / 关键标识）走 2.3.3 取值合法性校验；**数据类型字段**（计划执行次数）走 2.3.4 类型校验。
- `steps` 为数组，校验需逐条遍历每个步骤的 `operation` / `data` / 各类 `expected`。
- csv 的「步骤描述」「预期结果」为步骤级多行文本，需按步骤解析后逐段匹配。
- 枚举型字段不做「待补充」字面量匹配。

#### 2.3.2 「待补充」匹配规则（文本校验）
只要字段内容里包含字面量 **「待补充」**（含前后的「」符号）即视为命中。不做语义判断，仅做字符串匹配，避免误伤正常写法。

#### 2.3.3 枚举字段合法性校验
枚举型字段需做**取值合法性校验**：字段值必须落在系统允许的取值集合内，否则视为不合法。

- **案例类型**（`type`）：取值应为系统定义的案例类型集合，如 功能点类 / 流程类 / 界面类 等。
- **执行方式**（`test_type`）：取值应为 手工 / 自动化。
- **优先级**（`priority`）：取值应为 高 / 中 / 低。
- **关键标识**（`key_flag`）：取值应为系统定义的关键用例标识集合（如 是 / 否，或 0 / 1），具体以系统枚举为准。

校验规则：
- 字段为空、或取值不在允许集合内（含随手填写的任意文本）均判定为**不合法**。
- 具体允许取值以系统实际枚举为准（模版中以"…"表示可扩展）。

#### 2.3.4 数据类型校验
部分字段需校验**数据类型**是否与约定一致。当前纳入：

- **计划执行次数**（`plan_exec_num`）：数据类型应为**数值（建议非负整数）**；出现非数字、空值或文本均判为不合法。

校验规则：
- 若业务允许小数或限定取值范围，以系统约定为准，可在此扩展范围校验（如要求 ≥ 0）。

### 2.4 命中后的处理
#### 2.4.1 提示与定位
校验命中后弹出提示，按问题性质给出不同文案：
- **质量类（「待补充」等未写完内容）**：
  > 您的案例存在「待补充」等未写完内容，请完善后再推送。
- **失败类（枚举非法 / 数据类型不符）**：
  > 您的案例存在不合法内容（如非法枚举、类型错误），将导致推送失败，请修正后再推送。

提示应做到：
- **列出具体命中的案例与原因**：展示是哪一条（或哪几条）案例命中、命中在哪个字段、属于哪类问题，方便用户定位。
- **批量推送聚合**：多文件批量推送时，按文件聚合展示命中清单，避免信息散落。
- **支持复制案例 ID**：命中的案例应支持一键复制其案例 ID（优先取 `testcase_id`；缺失时以"文件路径 + 行号"兜底），便于直接跳转到对应案例补全或修正。

#### 2.4.2 分层处理：可忽略 vs 强制阻断
- **质量类（「待补充」）— 软拦截，可忽略**：用户确认知晓风险后，可选择"忽略提示，仍然继续推送"，系统照常推送。
- **失败类（枚举非法 / 数据类型不符）— 强制阻断，不可忽略**：此类内容会被 TMS 拒绝、必然推送失败，因此不允许忽略；用户须修正对应字段后才能推送（可关闭提示回到编辑器修正，修正后重新推送）。

## 3. 使用预期（用户视角）

**入口一：打开文件即高亮**
- 在案例编辑器打开 csv / json / yaml 等文件时，含「待补充」的单元格高亮为**黄色**、枚举非法或类型不符的单元格高亮为**红色**，悬停可见具体原因，编辑阶段即可发现并修正（多步骤数组定位到对应步骤行）。

**入口二：推送前自动校验（兜底）**
- 点击"推送" → 系统先扫描本次要推送的案例（同时做「待补充」匹配、枚举合法性、数据类型校验）。
- **全部通过** → 正常进入推送流程，无额外打扰。
- **存在「待补充」、枚举不合法或数据类型不合法** → 弹出提示，列出命中的具体案例（含案例 ID，可一键复制），告知"请完善后再推送 / 请修正不合法字段"。
- 用户有两种选择：
  - **去完善**：关闭提示，回到编辑器补全内容或修正字段后再推送；
  - **仍要推送**：点击"忽略并继续"，系统照常推送。
- 该校验对 csv / json / yaml 等各类型案例文件均生效（csv 按中文列名识别对应字段）。
- 两处入口（高亮 / 推送前）共用同一校验规则，结果口径一致。

## 4. 设计原则与边界

- **三类校验机制不同**：文本字段（操作 / 步骤数据 / 预期 / 前置条件 / 名称 / 描述）仅做「待补充」字面量匹配，不判断内容是否真的完整；枚举字段（案例类型 / 执行方式 / 优先级 / 关键标识 key_flag）做取值合法性校验；数据类型字段（计划执行次数 plan_exec_num）做类型校验。三者互不替代。
- **分层处理（软拦截 + 强制阻断）**：「待补充」等质量类问题为软拦截、可忽略，兼顾合规要求与紧急推送；枚举非法 / 数据类型不符等失败类问题为强制阻断、不可忽略，因为内容必然被 TMS 拒绝，避免"忽略后依旧失败"的无效体验。
- **字段覆盖完整**：文本目标字段（操作 / 步骤数据 / 预期 / 前置条件 / 名称 / 描述）均需覆盖，且 csv 的中文列名场景不可遗漏；枚举字段覆盖案例类型 / 执行方式 / 优先级 / 关键标识；数据类型字段覆盖计划执行次数。
- **可定位、可追溯**：通过"列出具体案例 + 复制案例 ID（优先 testcase_id，缺失以文件路径+行号兜底）"降低用户排查成本，也便于后续统计哪些团队/文件高频出现「待补充」或枚举不合法。（注：留痕/埋点机制不在本需求范围，本需求仅保证提示可定位。）

## 5. 验收要点（建议）

1. 推送含「待补充」的案例时，弹出**质量类**提示且文案正确，提供"忽略并继续"入口，点击后案例正常推送。
2. 推送含枚举非法（案例类型 / 执行方式 / 优先级 / 关键标识）或类型不符（计划执行次数非数值）的案例时，弹出**失败类**提示且文案明确"将导致推送失败"，且**不允许忽略**，必须修正后才能推送。
3. 提示中能展示命中的具体案例、命中字段与原因，并支持复制案例 ID（优先 `testcase_id`，缺失以"文件路径 + 行号"兜底）。
4. 多文件批量推送时，命中项按文件聚合展示，不散落。
5. 不含「待补充」、枚举合法且类型合法时，推送无任何额外提示。
6. csv 文件按中文列名正确识别**全部**字段（含枚举字段：案例类型 / 执行方式 / 优先级 / 关键标识，及计划执行次数）并校验。
7. 不含「」符号的"待补充"纯文本（如 `待补充` 无括号）按匹配规则不误伤（如需更宽松匹配可另行约定）。
8. 枚举字段取值合法时，不因"非待补充"的任意文本而误报（合法性以枚举集合为准，非字符串匹配）。
9. 打开案例文件（csv / json / yaml）时，含「待补充」的单元格**黄色**高亮、枚举非法 / 类型不符的单元格**红色**高亮，悬停显示原因；多步骤数组定位到对应步骤行；修正后高亮实时消除；大文件打开不卡顿。
10. 高亮 / 推送前校验两处入口共用同一校验规则与字段清单，口径一致。
11. 可选字段（案例标签）默认关闭，开启后按配置纳入「待补充」匹配校验。

> 备注：枚举字段的允许取值集合、数据类型取值范围，以系统实际定义为准（需求中以"…"标注处待确认）。
