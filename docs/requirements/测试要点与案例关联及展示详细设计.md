## 1. 总体架构

本能力处于"绑定层（声明关系）+ 匹配引擎层（自动推断）+ 展示层（结果呈现）"的三层结构之上：

- **匹配引擎层**：`src/utils/pointCaseLinker.ts`（`linkPointsToCases` / `linkPointsToCasesBatch`）。输入要点清单 + 案例文件，输出 `byPoint` / `byCase` / `stats`，并分 type 1/2/3 三档。详见 `point-case-linker-requirements.md`，本文档不再复述算法。
- **绑定层（本文档重点）**：`src/utils/pointCaseBindingStore.ts`，负责把用户的显式"要点 ↔ 案例"声明持久化为工作区内的绑定库文件，并提供双向查询、占用校验、文件重命名/删除同步。
- **展示层（本文档重点）**：基于绑定库 + 匹配引擎，在资源管理器（🔗 装饰器）、状态栏（跳转按钮）、大纲聚合 Webview（按要点聚合 + 三档 + 统计）、诊断命令（Output Channel 输出 envelope/stats）以及案例侧反向归属中呈现。

关键模块与入口：

| 职责 | 模块 |
|------|------|
| 绑定持久化、双向查询、生命周期同步、装饰器 O(1) 映射 | `src/utils/pointCaseBindingStore.ts` |
| 绑定弹窗（候选扫描、占用标记、保存落库） | `src/providers/BindDialogProvider.ts` |
| 绑定入口命令 + 方向校验 | `src/utils/commands.ts`（命令注册）、`src/handlers/bindHandler.ts`（右键菜单入口） |
| 资源管理器 🔗 装饰器 | `src/providers/TaskFolderDecorationProvider.ts`（或等价装饰器 Provider） |
| 状态栏跳转按钮 + 动态显隐 | `src/providers/BindStatusBarProvider.ts` |
| 大纲聚合 / 可视化展示公共方法 | `src/handlers/linkerDiagnosticHandler.ts`（`getLinkedCasesByMdFile` / `linkAndAggregateCases`） |
| 诊断命令入口（Output Channel 分块输出） | `src/handlers/linkerDiagnosticCommand.ts` |
| 文件重命名/删除监听 → 绑定同步 | `src/handlers/workspaceListeners.ts` |

## 2. 绑定建立与持久化

### 2.1 绑定存储结构

#### 需求要点
用户声明的"要点 ↔ 案例"关系须持久化在**工作区内**（随项目分发、不污染用户全局配置），支持双向查询、1:1 占用约束、并发写保护。

#### 涉及模块与文件
`src/utils/pointCaseBindingStore.ts`

#### 核心数据结构
存储文件位于 `<workspace-root>/.plugin/.tms/point-case-bindings.json`，顶层结构：

```ts
interface PointCaseBinding {
    point: string;        // 测试要点文件相对工作区根的 POSIX 路径，如 测试任务/xxx/测试大纲/登录.md
    cases: string[];      // 关联的测试案例文件相对路径数组
    updatedAt?: number;   // 最近更新时间戳
}
interface PointCaseBindingsFile {
    version: number;      // 当前 = 1
    bindings: PointCaseBinding[];
}
```

设计要点：
- **以要点为主键**（`point` 唯一），`cases` 为数组；当前严格 1:1 语义下 `cases` 长度最多为 1。
- 所有路径使用**相对工作区根**的 POSIX 路径，跨平台稳定；绝对/相对互转工具 `toRelPath` / `toAbsPath` / `findWorkspaceRootFor`。
- **读缓存**：`cacheByRoot: Map<root, { filePath, data, mtimeMs }>`，读前比对磁盘 mtime，未变则命中缓存避免重复 IO。
- **写乐观锁**：`saveBindings(root, data, expectedMtimeMs?)` 写前重新 `stat`，与调用方读取时的基线 mtime 对比；不一致抛 `ConcurrentWriteError`，由上层决定重试或提示。
- **装饰器聚合映射缓存**：`globalBoundFileMapCache`，5 秒 TTL 削峰，供 `provideFileDecoration` O(1) 查询；写入后 `invalidateGlobalBoundFileMap()` 失效。

#### 关键流程
1. **确保文件就绪**：`ensureStoreFile(root)` 递归创建目录并写入空结构；`ensureAllWorkspaceStores()` 在扩展激活时为所有已打开工作区初始化。
2. **读取**：`loadBindings(root)` 解析 JSON，过滤非法记录（`point` 为空 / `bindings` 非数组降级为空结构）；解析失败返回空结构不阻断。
3. **写入（覆盖式）**：`saveBindings` 先规范化（去重、去空、过滤无 point 记录），再写盘并刷新缓存。
4. **双向查询**：
   - `getBoundCasesOfPoint(pointAbs)` → 该要点绑定的案例绝对路径列表。
   - `getBoundPointsOfCase(caseAbs)` → 该案例被哪些要点绑定（1:1 下最多 1 个）。
   - `isPathBound(abs)` → 该文件是否以任一角色参与绑定。

#### 边界与防御
- 工作区根解析失败（文件不在任何已打开工作区）时查询返回空、写操作抛中文错误。
- 存储文件损坏（JSON 解析失败、非预期结构）→ 降级为空结构，仅 `ENOENT` 之外的情况 `console.warn`，不阻断编辑器。
- 跨工作区移动文件：`renamePathInBindings` 在 `oldRoot !== newRoot` 时按"先删后增"退化处理，避免跨区脏绑定。

### 2.2 绑定对话框与候选管理

#### 需求要点
从要点文件（或案例文件）发起绑定，扫描同任务目录下的候选，标记"已绑定/被占用"，用户勾选保存后覆盖式写入绑定库；1:1 占用冲突在前端即禁选、在落库时再校验。

#### 涉及模块与文件
`src/providers/BindDialogProvider.ts`（独立 Webview Panel，非单例）、`media/pages/bind-dialog/*`（前端 `index.html` / `main.js`）。

#### 核心数据结构
```ts
type BindDirection = 'point-to-cases' | 'case-to-points';
interface CandidateItem {
    absPath: string;
    relPath: string;
    name: string;
    ext: string;
    boundToSource: boolean;   // 是否已与当前源绑定
    boundToOthers: boolean;   // 是否被其它项占用（1:1 下禁选）
    boundToOwnerRel?: string; // 占用者相对路径（展示用）
}
interface InitPayload {
    direction: BindDirection;
    sourceAbsPath: string;
    sourceRelPath: string;
    scopeTaskName: string;    // 测试任务子目录名
    candidates: CandidateItem[];
    title: string;
    targetLabel: string;
    currentBoundRel?: string; // 源文件当前已绑定对端（1:1）
    targetDirAbs?: string;    // 空态"打开目录"目标
}
```

#### 关键流程
1. **入口方向校验（open）**：
   - 先 `locateTaskRoot(sourceAbsPath)` 正则匹配 `**/测试任务/<name>/`；不在该结构下 → 提示并 `bindDialog.abort(notInTaskDir)` 埋点返回，不开弹窗。
   - 校验文件在已打开工作区内。
2. **先开 Panel + loading**：避免大目录扫描阻塞；异步 `scanCandidateFilesAsync` 递归扫描目标目录（`.md/.xmind` 或 `.csv/.yaml/.yml/.json`），跳过点开头的隐藏目录，同层 `Promise.all` 并发遍历。
3. **候选人标注**：
   - `boundToSource`：由 `getBoundCasesOfPoint` / `getBoundPointsOfCase` 得到源已绑集合。
   - `boundToOthers`：`buildCaseOccupancyMap` / `buildPointOccupancyMap` 得到占用者；若占用者非当前源则禁选并展示占用者相对路径。
   - 候选人按 `relPath` 中文本地化排序。
4. **消息交互（webview.onDidReceiveMessage）**：
   - `ready`：若 payload 已就绪直接 `init`，否则下发 `loading` 文案。
   - `save`：选中 > 1 时前端直接回传 `saveError`（1:1 约束）；否则快照"旧对端"、`setPointCases` / `setCasePoints` 落库；成功后将「源 ∪ 新对端 ∪ 旧对端」URI 集合交给 `refreshDecorations` 精确刷新装饰器，并 `showToast`（"已绑定 1 个…" / "已解除绑定"），300ms 后 `panel.dispose()`。
   - `cancel`：移除弹窗，埋点 `bindDialog.cancel`。
   - `reveal` / `openTargetDir`：在资源管理器定位候选文件 / 目标目录（空态入口）。
5. **落库冲突**：`setPointCases` / `setCasePoints` 内部再次做 1:1 占用校验（`getCaseOfPoint` 已实现），占用冲突抛中文错，前端 `saveError` 展示。

#### 边界与防御
- 扫描失败：`buildPayload().catch` 埋点 `bindDialog.scanError` 并前端提示，不卡死弹窗。
- 保存写盘部分成功但抛错：兜底 `refreshDecorations()` 全量刷新，避免 UI/存储失同步。
- 1:1 约束双重防线：前端禁选 + 后端 `setPointCases`/`setCasePoints` 拒绝 >1 或占用冲突，保证存储结构不被破坏。
- 占用展示一致性：占用者相对路径取 `path.basename`，仅展示文件名，避免泄露项目绝对路径。

### 2.3 绑定生命周期同步

#### 需求要点
要点/案例文件被重命名、移动、删除时，绑定库自动更新或清理，不产生脏绑定；跨区移动按删除处理。

#### 涉及模块与文件
`src/utils/pointCaseBindingStore.ts`（`renamePathInBindings` / `removePathInBindings`）、`src/handlers/workspaceListeners.ts`（文件系统监听）。

#### 核心数据结构
同 2.1 的 `PointCaseBindingsFile`；增量维护接收绝对路径 `oldAbs/newAbs`。

#### 关键流程
1. **重命名 / 移动**：`renamePathInBindings(oldAbs, newAbs)` 把 `bindings` 中 `point === oldRel` 或 `cases` 含 `oldRel` 的项整体替换为 `newRel`；返回是否实际改动；写盘失败且为 `ConcurrentWriteError` 时重试一次。
2. **删除**：`removePathInBindings(abs)` 三步清理：① 删除 `point === rel` 整条记录；② 从所有 `cases` 中剔除该 rel；③ 清理因此变空的 point 记录；任一变动即写盘。
3. **监听触发**：`workspaceListeners` 监听 `rename`/`delete` 事件，分派到上述两函数；完成后调用 `invalidateGlobalBoundFileMap()` 让装饰器/状态栏重新拉取。

#### 边界与防御
- 跨工作区移动：`oldRoot !== newRoot` 时直接 `removePathInBindings(oldAbs)`，避免把 A 工作区绑定错误迁移到 B。
- 乐观锁冲突：删除/重命名写盘遇 `ConcurrentWriteError` 重试一次（不带 mtime 基线），保证最终一致。
- 同名文件快速替换（删除+新建同路径）：两次事件分别处理，第二次 `renamePathInBindings` 找不到旧 rel 即 no-op，最终状态由新建事件决定。

## 3. 关联展示：资源管理器与状态栏

### 3.1 资源管理器 🔗 装饰器

#### 需求要点
已参与绑定的要点/案例文件在资源管理器中显示 🔗 徽标，未绑定文件不显示；绑定变化后即时刷新。

#### 涉及模块与文件
`src/utils/pointCaseBindingStore.ts`（`buildBoundFileMap` / `getGlobalBoundFileMap`）、装饰器 Provider（如 `TaskFolderDecorationProvider`）。

#### 核心数据结构
```ts
interface BoundFileMeta {
    role: 'point' | 'case';
    boundToRel: string;    // 对端相对路径
    boundToName: string;   // 对端文件名（tooltip）
}
// 全局聚合： POSIX 绝对路径 → BoundFileMeta
getGlobalBoundFileMap(): Map<string, BoundFileMeta>
```

#### 关键流程
1. `getGlobalBoundFileMap()` 遍历所有工作区根，`buildBoundFileMap` 由 `bindings` 展开为"要点文件→元信息"与"案例文件→元信息"双映射，跨工作区合并；带 5s TTL 缓存削峰。
2. 装饰器 `provideFileDecoration(uri)` 对 uri 查表，命中则附加 🔗 徽标 + tooltip（"已绑定测试案例：xxx" / "已绑定测试要点：xxx"）。
3. `refreshDecorations(uris?)`：绑定保存后由 `BindDialogProvider` 传入"源 ∪ 新对端 ∪ 旧对端"URI 集合精确触发刷新；也可全量失效缓存后重绘。

#### 边界与防御
- 装饰器高频调用，依赖 5s TTL 缓存与 `invalidateGlobalBoundFileMap` 显式失效，避免每次 IO。
- 仅展示对端文件名（`path.basename`），不泄露绝对路径。

### 3.2 状态栏跳转按钮

#### 需求要点
打开已绑定文件时状态栏显示"跳转到已绑定对端"按钮，点击直达对端；未绑定自动隐藏；保存绑定后无需切换编辑器即出现。

#### 涉及模块与文件
`src/providers/BindStatusBarProvider.ts`；复用命令 `testcaseViewer.jumpToBoundCase` / `testcaseViewer.jumpToBoundPoint`。

#### 核心数据结构
同 3.1 的 `BoundFileMeta`；状态栏项 `vscode.StatusBarItem`（Left 对齐，优先级 100）。

#### 关键流程
1. `updateStatusBar()`：取当前活动文件（兼容 `activeTextEditor` 与 `tabGroups.activeTab.input.uri`，覆盖自定义编辑器场景），归一化后查 `getGlobalBoundFileMap()`。
2. 命中且 `role==='point'` → 文案"$(arrow-right) 跳转到已绑定的测试案例"、tooltip 含对端名、命令 `jumpToBoundCase`；`role==='case'` 对称处理。未命中则 `hide()`。
3. **监听联动**：`onDidChangeActiveTextEditor` + `tabGroups.onDidChangeTabs` 切换刷新；监听绑定库文件保存 / 文件系统变更（`**/.plugin/.tms/point-case-bindings.json`）即时刷新；`refreshBindStatusBar()` 供 `BindDialogProvider` 保存后主动调用（自现）。
4. 跳转目标缺失时由命令实现侧告警（"绑定的文件不存在"），不静默失败；未绑文件点击时命令侧提示"是否立即绑定"。

#### 边界与防御
- 取路径失败（聚焦 Output/终端等虚拟 tab）→ `hide()` 不报错。
- 多工作区：全局映射已合并所有 root，`tabGroups` 兜底路径取 `file://` scheme，跳过非 file tab。

## 4. 关联展示：大纲聚合与诊断

### 4.1 大纲/可视化聚合展示公共方法

#### 需求要点
以测试要点为节点，聚合展示其关联的全部测试案例，标注 type 1/2/3 关联强度，提示未覆盖要点，并输出统计概览；同时支撑诊断命令输出。

#### 涉及模块与文件
`src/handlers/linkerDiagnosticHandler.ts`（`getLinkedCasesByMdFile` / `linkAndAggregateCases` / `parseMdToPointListSilent` / `parseXmindToPointListSilent`）、底层 `src/utils/pointCaseLinker.ts`。

#### 核心数据结构
```ts
interface LinkedCaseItem {
    testcase_id: string;
    caseName: string;
    casePath: string;          // 案例记录中的 path 字段
    caseDetail: string;         // 【前置条件】…【预期结果】…
    type: 1 | 2 | 3;
    filePath: string;           // 案例源文件绝对路径
}
interface LinkedCasesEnvelope {
    total: number;              // 命中案例总数（== matchedRecords）
    errorMsg: string;           // 错误时非空
    data: Record<string, LinkedCaseItem[]>;  // key: `${pointId}_${pointName}`
    stats?: {
        totalRecords: number;
        typeCount: { type1: number; type2: number; type3: number };
        totalOrphan: number;
        totalStripped: number;
        duplicatePointIds?: string[];
        multiHitCases?: string[];
    };
    xmindInvalidNodes?: ...;    // 仅 xmind 源、结构错误清单
    xmindWarnings?: ...;        // 仅 xmind 源、脏数据告警
}
```

#### 关键流程
1. **一站式入口 `getLinkedCasesByMdFile(mdPath)`**：
   - 按扩展名分派 `.md`（`parseMdToPointListSilent`）/ `.xmind`（`parseXmindToPointListSilent`）；解析 0 要点 / 结构错误 → envelope 携带错误文案 + xmind 清单返回。
   - 经 `getCaseOfPoint(mdPath)` 取唯一绑定案例（1:1）；未绑 → 提示"请先绑定"；绑定文件磁盘缺失 → "已缺失"。
   - 调 `linkAndAggregateCases(pointList, casePath)` 完成匹配 + 聚合成 `data`。
2. **聚合 `linkAndAggregateCases`**：入参校验（空 pointList / 空 filePath 返回中文错误 envelope）；调用 `linkPointsToCases` 并**针对中文表头 CSV 做字段名兼容**（`detectCsvHeaderOptions` 只读首行 ≤8KB 探测 `名称/路径/前置条件/预期结果` 等别名，注入 `LinkOptions`）；将 `byPoint` 透传为 `data`，`stats` 原样收拢。
3. **md/xmind 解析**：`parseMdToPointListSilent` 提取"功能条目：xxx"前缀作为归一化的 pointPath 父级，识别 `| 序号 | 测试点 | … |` 表头弹性列名；pointId 缺失时用测试点名称兜底，使其能凭 path 参与 type=2 匹配。

#### 边界与防御
- 中文表头 CSV 无 `parent_id` → 仅能 type=2（path 兜底），为数据模型天花板，非缺陷。
- xmind 自定义编辑器打开时 `activeTextEditor` 为空，取路径逻辑在命令层兜底到 `tabGroups.activeTab`（见 4.2）。
- 缓存：底层引擎 LRU 以 `filePath+mtimeMs+size` 为键，文件保存后失效；未保存改动需先保存要点/案例文件才能被匹配到。
- 解析全程"静默"（不写 Output Channel、不弹 UI），错误统一收敛进 `envelope.errorMsg`，由展示层决定如何呈现。

### 4.2 诊断命令

#### 需求要点
提供命令面板入口，将关联匹配诊断结果以"envelope + stats"两块 JSON 输出到 Output Channel（`[TC-Linker]` 前缀），便于排查"绑定了案例但匹配为 0"等异常；并列出 xmind 结构错误清单。

#### 涉及模块与文件
`src/handlers/linkerDiagnosticCommand.ts`（命令 `testcaseViewer.diagnosticLinker`）、复用 `getLinkedCasesByMdFile`。

#### 关键流程
1. **取源路径**：优先 `activeTextEditor`（file scheme），兜底 `tabGroups.activeTab.input.uri`，再兜底遍历所有 tab 找最近的 `.md/.xmind`；均失败提示"请先打开测试要点文件"。
2. **路径校验**：必须是 `.md/.xmind` 且命中 `测试任务/<任务名>/测试大纲/`；否则告警返回。**注意**：`ch.show(true)` 必须在解析出 mdPath 之后调用，否则 Output 面板抢占 activeTab 会导致后续兜底取到非法虚拟 tab 路径。
3. **调用 + 打印**：`getLinkedCasesByMdFile` → 有错则打印 `errorMsg` + xmind 清单 + envelope JSON；无错则打印 envelope JSON + stats JSON（含 `matchedPointKeys`、三档分布、孤儿、剥离、耗时）。
4. **埋点**：成功 `linkerDiagnostic.done`、失败 `linkerDiagnostic.linkerError`（含 mdFile / elapsedMs）。

#### 边界与防御
- Output 面板激活时机严格后置，避免污染路径解析。
- xmind 结构错误清单达硬上限（200）时提示"可能还有更多未列出"，引导分批修复。

## 5. 关联展示：案例侧反向归属

### 5.1 案例归属展示

#### 需求要点
用例工程师在编辑案例时，能看"这条案例挂在哪个测试要点下"，并识别弱关联（type 2/3）与孤儿（无绑定无匹配）。

#### 涉及模块与文件
案例编辑器内嵌展示（`media/pages/table-editor` 相关脚本复用绑定库查询）、`getPointOfCase` / 匹配引擎反向索引 `byCase`。

#### 核心数据结构
- 绑定层：`getPointOfCase(caseAbs)` → 唯一绑定要点绝对路径（或 null）。
- 匹配层：`LinkResult.byCase: Record<testcase_id, { pointKey, type }>`（O(1) 反查，type 暴露关联强度）。

#### 关键流程
1. 案例编辑器加载时，先查 `getPointOfCase` 取显式绑定要点（1:1）；若为空，再用匹配引擎 `byCase` 反查（需先解析该案例的 parent_id/path，经 `linkPointsToCases` 得到）。
2. 展示归属要点名称与路径；若 `type` 为 2/3 或仅命中匹配未绑定 → 显示"弱关联"提示，建议补全 `parent_id` / `path` 或建立显式绑定；若既无绑定也无匹配（孤儿）→ 显示"未关联任何测试要点"。

#### 边界与防御
- 同一条案例可能"已绑定 A 但匹配到 B"——展示以**显式绑定**为优先口径，匹配结果仅作弱关联补充提示，避免误导。
- 多文件匹配场景下，`byCase` 以单文件为单位，跨文件聚合需在展示层合并去重（当前 1:1 单案例文件，暂不涉及）。

## 6. 跨功能交互与一致性

- **双向唯一 truth**：绑定库是唯一显式关系源；匹配引擎是推断源。展示层对"要点下案例"优先采用 `getCaseOfPoint`（绑定），未绑才走 `linkAndAggregateCases`（匹配）。
- **刷新联动**：绑定保存 / 文件重命名删除 → `invalidateGlobalBoundFileMap()` + `refreshDecorations` + `refreshBindStatusBar`，保证装饰器、状态栏、弹窗三处一致。
- **1:1 约束一致性**：前端禁选 + `setPointCases`/`setCasePoints` 后端校验双重保障；`buildBoundFileMap` 取 `cases[0]` 保证展示只取首条。
- **路径归一化统一**：md 侧 `parseMdToPointListSilent` 与案例侧匹配引擎共用 `normalizePointPath`，避免 `\` 对 `/`、尾斜杠差异导致 type 判定不一致。
- **中文表头兼容**：仅在 `.csv` 首行探测注入 `LinkOptions`，yaml/json 仍走英文字段约定，不影响其他解析路径。

## 7. 待确认 / 可演进项

- **未绑定兜底扫描**：`linkerDiagnosticHandler.ts` 内 `locateCaseDir` / `collectCaseFiles` 已设计成纯函数（当前未启用）。需求确认是否允许"要点未绑定时自动按目录约定发现案例"，以弱化"必须先绑定"的强约束。
- **多对多扩展**：当前严格 1:1（`cases` 数组最多 1 项、`setPointCases` 拒绝 >1）。若未来需求放开"一个要点绑定多个案例"，需改造 `setPointCases`、占用映射、装饰器 `cases[0]` 取首逻辑、状态栏跳转（多目标需弹列表面板）。
- **跨工作区绑定迁移**：当前跨 root 移动按删除处理，历史绑定在源工作区保留为孤儿，需在监听层决定是否级联清理。
- **案例侧反向归属 UI 形态**：当前依赖编辑器内嵌展示，是否需要在案例文件资源管理器装饰器上同时显示"归属要点名" tooltip，待 UX 确认。
