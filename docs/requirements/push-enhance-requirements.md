# 推送增强功能 — 需求文档

---

## 一、需求背景

案例推送到后端接口是一个多阶段、易出错的流程：用户可能在文件中混入样例占位行、YAML 语法错误，推送过程又会因字段非法、权限、网络等原因产生大量失败。早期推送能力在以下方面存在体验与可观测性缺口：

1. **结果统计不自洽**：含有样例占位行的文件推送后，弹窗「总计 / 成功 / 失败」三数相加对不上，用户无法判断是否有数据被静默跳过；
2. **错误前置拦截缺失**：语法非法的 YAML 文件会一路走到后端才报错，浪费请求且提示不友好；
3. **装饰刷新粗放**：绑定关系变化后，装饰图标采用全量刷新，多文件工作区下会出现不必要的重绘闪烁；
4. **失败不可归类**：后端返回的自由中文失败文案无法聚合统计，也无法区分「接口级整批失败」与「行级字段错误」，埋点与大盘口径混乱；
5. **链路不可观测**：推送失败时难以定位问题发生在预校验、样例过滤、请求还是响应阶段，排查成本高。

因此需要在「结果呈现、前置拦截、装饰刷新、失败分类、链路诊断」五个维度增强推送能力，提升正确性、可解释性与可观测性。

---

## 二、需求目的

围绕案例推送的「发起 → 校验 → 调用 → 结果 → 诊断」全链路，提供五项增强能力：

1. **跳过维度可见**：样例占位行被静默跳过时，结果弹窗新增「跳过 N」第四维度，保证 总计 = 成功 + 失败 + 跳过，统计自洽；
2. **前置语法拦截**：推送 `.yaml/.yml` 前先做语法校验，非法文件直接中止并给出可操作的修复入口与多行错误弹窗；
3. **精确装饰刷新**：绑定关系变化时仅对受影响的 URI 精确刷新装饰，避免全局重绘；
4. **失败可归类**：把自由中文失败文案稳定归类为分类码与接口字段码（区分接口级/行级），支撑分组展示与分层埋点；
5. **链路可诊断**：提供可开关的推送链路诊断日志，全程分阶段打点，默认零开销。

## 三、功能清单

### 3.1 推送结果弹窗「跳过」维度

#### 功能简述
推送结果弹窗在原有「总计 / 成功 / 失败」三维度基础上，新增第四维度「跳过 N」，专门呈现被静默跳过的样例占位行。保证四个数字严格自洽，避免「总计 13 / 成功 12 / 失败 0」与底部文案矛盾的误判。

#### 功能内容

##### 3.1.1 跳过维度的呈现规则

| 场景 | 弹窗行为 | 自洽约束 |
|------|---------|---------|
| 存在样例行被跳过（skipped > 0） | 概要栏追加「跳过 N」第四维度，底部提示「（已跳过 N 行样例数据）」 | `total = successCount + failures.length + skipped` |
| 无样例行（skipped = 0） | 不显示「跳过」维度，仅保留三维度 | `total = successCount + failures.length` |
| 全部为样例行 | 终止推送、不调后端，skipped = 选中行数 | 后端接口 0 调用，文件 testCaseNo 不变 |

##### 3.1.2 样例行的判定与终止

- 推送前由样例过滤逻辑识别占位行（`testcase_id` 为「案例唯一标识，不可修改」等样例值）；
- 若全部选中行均为样例，直接终止并汇总（skipped = 过滤行数），不进入后端调用；
- 若仅部分行为样例，仅跳过样例行，其余合法行正常推送。

##### 3.1.3 失败文案的健壮性

- 失败 reason 在序列化时对循环引用 body 做兜底降级（`String`/`returnCode` 形态），避免把「接口失败」升级为「扩展端崩溃」；
- 批量失败超过 20 个时，诊断日志 `failedTsIds` 仅列出前 20 个并附「+N」，避免超长日志。

### 3.2 推送前置 YAML 语法校验拦截与多行错误弹窗

#### 功能简述
推送 `.yaml/.yml` 文件前，先执行语法校验（`validateYamlContent`）并发布诊断。存在 error 级问题时立即中止推送，弹出带快捷修复入口的 Warning 与多行错误详情弹窗，从源头避免把非法文件发往后端。

#### 功能内容

##### 3.2.1 拦截与提示

| 触发条件 | 行为 | 遥测 |
|---------|------|------|
| 存在 error 级语法问题 | 中止推送，弹 Warning（含「YAML 修复全部」「查看问题面板」按钮），错误弹窗给出首条错误行号与摘要 | `explorerPush.aborted{reason: yamlSyntaxError}` |
| 校验器自身抛异常 | 中止推送，弹「YAML 校验器异常，已终止推送」并提示重试 | `explorerPush.aborted{reason: yamlValidatorCrash}` |
| 语法合法 | 不拦截，正常进入解析 → 映射 → 推送流程 | — |

##### 3.2.2 多行错误弹窗样式

- 通用错误弹窗内容 `<p>` 增强 `white-space: pre-line` + `text-align: left`；
- 多行错误摘要（如「首条错误（第 N 行，共 M 处错误）：\n摘要」）按 `\n` 正确换行、左对齐，不再挤成一行；
- 该多行样式在「语法错误」与「校验器异常」两类弹窗均生效。

##### 3.2.3 合法性放行

仅当校验返回 error 级问题才拦截；语法正确的 YAML 文件正常通过，校验器不误伤合法文件。

### 3.3 绑定装饰按 URI 精确刷新

#### 功能简述
绑定关系变化（保存/解除）后，仅对受影响的文件 URI 精确刷新编辑器装饰图标，避免多文件工作区下的全局重绘闪烁，同时修复历史上「空数组被当作无变更而不刷新」的缺陷。

#### 功能内容

##### 3.3.1 刷新范围策略

| 调用方式 | 刷新范围 | 说明 |
|---------|---------|------|
| `refresh(uris)`（uris 非空） | 仅对给定 URI 精确 fire | 仅受影响文件重绘，其他文件不闪 |
| `refresh([])` / `refresh(undefined)` | 退化为全量刷新（fire(undefined)） | 修复 `fire([])` 被视作「无变更」不刷新的旧 Bug |
| 绑定保存成功 | 精确刷新 源 ∪ 新对端 ∪ 旧对端（去重） | 源文件显示「已绑」，旧对端因解除显示「未绑」 |
| 绑定保存异常 | catch 中 `refreshDecorations()` 无参 = 全量刷新兜底 | 避免装饰图标与底层存储失同步 |

##### 3.3.2 边界保障

- 空数组与未传参均触发全量刷新，两条路径均可正确生效；
- 保存异常被捕获并遥测（如 `bindDialog.save.error`），不崩溃，且仍有一次全量刷新保证 UI/存储重新对齐。

### 3.4 推送失败分类（接口级 / 行级字段级）

#### 功能简述
把后端返回的自由中文失败文案，稳定归类为「分类码（category）」与「接口字段码（field）」两个正交维度，并区分「接口级公共参数错（一次错 = 整批失败）」与「行级 caseList 字段错」。用户仍看到完整中文原文，统计与埋点只看稳定短码，既不丢失信息又能聚合分析。

#### 功能内容

##### 3.4.1 分类码（category）

归类优先级：**先复用结构化信号，再走中文文本归类**。

| 来源 | 分类 | 说明 |
|------|------|------|
| 预校验结构化信号 | `placeholder` / `emptyTestcaseId` / `sample` / `mapError`（兜底）/ 已知字段映射错误拆为 `${field}.${nature}` 复合码 | 客户端已明确，直接映射 |
| 后端中文文本（关键词） | `network` / `auth` / `fieldInvalid` / `notFound` / `serverError` / `bizReject` | 按关键词优先级归类（`dup` 性质走 `fieldDup`/`字段.dup`，无独立 `duplicate` 分类） |
| 都不命中 | `unknown` | 兜底归类，不丢失败 |

> 归类顺序即优先级，先命中先生效（如 `bizReject` 早于 `fieldInvalid`，`notFound` 早于 `fieldInvalid`），保证措辞变体也能稳定归类。

##### 3.4.2 接口字段码（field）与级别

从失败文案抽取命中的接口字段，并带级别：

| 级别 | 字段 | 含义 |
|------|------|------|
| `interface`（接口级公共参数，一次错 = 整批失败） | `testTaskNo` / `subTestTaskId` / `artifactId` / `sourcePlatform` / `designer` | 请求体顶层 / header，影响整批 |
| `case`（caseList[] 行级字段，每行独立） | `sourceId` / `testCasePath` / `testCaseName` / `description` / `expected` / `priority` / `type` / `preCondition` / `keyFlag` / `projectDes` / `planExecNum` / `testType` 等 | 单条案例字段 |

分层的目的是避免「designer 无权限」这类接口级一次错误，在 count 维度淹没「description 缺失」等行级字段的真实分布。

##### 3.4.3 聚合与上报

- `aggregateFailures`：按 category 分桶，count 降序，保留少量不重复 reason 样本；`summarizeCategoryBreakdown` 压成 `cat:count` 紧凑串；
- `aggregateByField` + `splitFieldStatsByLevel`：按字段聚合并拆成 `interfaceStats` / `caseStats` 两块，支持 UI 分 section 与埋点分维度；
- 最终推送完成时（`pushCore` [汇总]），随 `.complete` 上报 `failCategoryBreakdown` / `failFieldBreakdown` / `interfaceFailBreakdown` / `caseFailBreakdown`；结果弹窗按错误类型分组展示，每条仍显示原始中文 reason。

##### 3.4.4 设计要点

- reason（中文原文）只作「展示」，category/field（英文短码）只作「统计/埋点」，二者解耦；
- 新增后端错误类型：只需在归类规则表加一条规则 + 枚举加一个值，不改持久化结构、不改埋点字段。

### 3.5 推送链路诊断日志分阶段

#### 功能简述
提供可开关的推送链路诊断日志，默认关闭且零开销；开启后同时在 Extension Host 控制台与「TestCase 推送诊断」OutputChannel 输出，全程分阶段打点，便于在失败时快速定位发生在哪一步。模块纯「观测」，不改变任何业务流程。

#### 功能内容

##### 3.5.1 开关与开销

| 配置 | 行为 | 开销 |
|------|------|------|
| `testcaseViewer.debug.push = false`（默认） | `pushDiag` 首行提前 return，不进入序列化、不写 console、不创建 OutputChannel | 零开销，正常推送完全不受影响 |
| `testcaseViewer.debug.push = true` | 双保险：Extension Host 控制台 `[推送诊断]` + OutputChannel「TestCase 推送诊断」并自动弹出 | 仅在排查时启用 |

##### 3.5.2 分阶段打点

链路各阶段均有 `pushDiag` 标记，典型阶段顺序：

```
[前端请求] 收到推送
  → [入口] runPush 开始
    → [预校验]（含类别分布 + 失败明细）
      → [样例过滤]
        → [接口] 分批 / 预映射 / 请求数据 / 返回(returnCode,errorMsg) / 解析(成功+失败明细)
          → [step5] 清洗
            → [step6] 回写 / 快照
              → [step7] 合并
                → [汇总]（失败明细按行号）
[异常] runPush catch（顶层兜底）
```

- 终态节点（短路 / 异常 / 汇总）均触发 `showPushDiag` 自动弹出对应 OutputChannel；
- 每个阶段含关键计数与类别分布，可定位失败发生在预校验还是后端返回。

##### 3.5.3 序列化健壮性

- `safeStringify` 含循环引用兜底（`getCircularReplacer`）：遇到循环引用降级为 `[Circular]`，函数降级为 `[Function]`；
- 打印含循环引用的请求/响应体时不崩溃，诊断模块始终安全可用。

## 四、整体架构

五项增强能力分布在不同层，但都围绕同一次推送流程串接：

- **结果呈现层**（前端弹窗 + `message.ts`）：聚合 onComplete 的 `successCount / failures / total / skipped`，渲染四维度概要；
- **前置校验层**（`pushHandler.ts`）：推送发起前拦截 YAML 语法非法文件；
- **编辑器交互层**（`BindTaskProvider` / `BindDialogProvider`）：绑定变化后精确刷新装饰；
- **失败建模层**（`pushFailureCategory.ts`）：在 `pushCore` 的预校验短路、样例短路、最终汇总三处落地分类与字段聚焦，并随遥测上报；
- **观测层**（`pushDiagnostics.ts`）：在 `editorMessageHandlers` 与 `pushCore` 的各阶段挂点打点。

各能力互不耦合：诊断层纯观测、分类层只产数据不影响流程、装饰刷新只在绑定域生效；仅结果呈现层消费失败分类数据做分组展示。

## 五、验收标准

| 编号 | 验收项 | 标准 |
|------|--------|------|
| AC-1 | 跳过维度自洽 | 有样例行时弹窗显示「跳过 N」，且 总计 = 成功 + 失败 + 跳过 |
| AC-2 | 全样例终止 | 全部为样例行时终止推送、不调后端，skipped = 选中行数 |
| AC-3 | 无样例行不显示跳过 | 无样例行时仅三维度，三数相加严格相等 |
| AC-4 | 失败文案不崩溃 | body 含循环引用或不可序列化时，失败 reason 降级、扩展端不抛未捕获异常 |
| AC-5 | 诊断日志截断 | 批量失败 > 20 个时 `failedTsIds` 仅列前 20 并附 +N |
| AC-6 | YAML 前置拦截 | 语法错误文件被中止、不调后端，弹 Warning 含「YAML 修复全部」「查看问题面板」，遥测 `yamlSyntaxError` |
| AC-7 | 校验器异常兜底 | `validateYamlContent` 自身抛错时弹「YAML 校验器异常」并中止，遥测 `yamlValidatorCrash`，不崩溃 |
| AC-8 | 多行弹窗样式 | 错误弹窗多行摘要按 `\n` 正确换行、左对齐 |
| AC-9 | 合法 YAML 放行 | 语法正确的 YAML 不被拦截，正常进入推送流程 |
| AC-10 | 装饰精确刷新 | 绑定保存仅刷新 源∪新对端∪旧对端，其他文件不重绘 |
| AC-11 | 空参全量刷新 | `refresh([])` / `refresh(undefined)` 均触发全量刷新，修复旧 Bug |
| AC-12 | 保存异常兜底 | 绑定保存异常时仍有一次全量刷新，装饰与存储重新对齐 |
| AC-13 | 失败分类覆盖 | 预校验信号与后端文本均归类为正确 category（含 unknown 兜底） |
| AC-14 | 归类优先级 | 同时带结构化信号与后端文本时取结构化信号，不被文本措辞干扰 |
| AC-15 | 聚合与样本 | `aggregateFailures` 分桶降序、相同 reason 去重、`cat:count` 紧凑串正确 |
| AC-16 | 接口级/行级分层 | interface 级（一次错=整批）与 case 级字段分层聚合，互不淹没 |
| AC-17 | 埋点分组上报 | `.complete` 上报 `failCategoryBreakdown` / `interfaceFailBreakdown` / `caseFailBreakdown`，弹窗按类型分组且仍显中文原文 |
| AC-18 | 诊断默认零开销 | `debug.push=false` 时不写 console、不建 channel，正常推送性能无影响 |
| AC-19 | 诊断双保险 | 开启后 console 与 OutputChannel 均有输出并自动弹出 |
| AC-20 | 分阶段可定位 | 日志含 [入口]/[预校验]/[样例过滤]/[接口]/[解析]/[step5~7]/[汇总]/[异常] 阶段标签，可定位失败环节 |
| AC-21 | 循环引用兜底 | 打印循环引用对象时不崩溃，降级为 `[Circular]` |
