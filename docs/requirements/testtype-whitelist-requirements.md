# 执行方式（testType）严格白名单校验 — 需求文档

---

## 一、需求背景

在案例推送的字段映射阶段（`pushDataMapper.ts` 的 `mapRowToCaseItem`，由 `http.ts` 的 `data.map(mapRowToCaseItem)` 对所有推送请求统一调用），数据行的「执行方式」（中文 CSV 分支）/ `test_type`（YAML 结构化分支）会被映射为后端接口字段 `testType`。该映射对所有来源平台（`testAgent` / `testAgentMA`）均生效，并非仅限某一场景。

早期实现采用「兜底默认值」策略：未在白名单中的取值（含空值）一律回退为 `'自动化'`。这种方式存在以下体验与数据质量问题：

1. **脏数据静默入库**：用户漏填、拼写错误（如 `手动`、`自动`、`xyz`）或误留空格时，系统不报错而是写入占位的 `'自动化'`，用户无从感知，后端也无法识别真实的执行方式；
2. **缺省语义失真**：「未填写」与「明确选择自动化」被混为一谈，无法区分「用户有意选自动化」与「数据缺失」，影响后续统计与筛选；
3. **白名单外扩不可控**：随着业务新增 `UI自动化` / `接口自动化` / `半自动化` 等取值，兜底策略会让非法值继续被「吞掉」，错误被掩盖而非暴露。

因此需要将「执行方式」改为**严格白名单校验**：命中白名单才保留，未填写或任意非法取值一律在映射阶段抛出结构化错误，交由上层给出友好提示，不再有默认回退。

---

## 二、需求目的

在 `pushDataMapper.ts` 的字段映射阶段，对「执行方式 / test_type」实施严格白名单校验：

1. **白名单保留**：取值命中白名单时原样保留，保证后续 `UI自动化` / `接口自动化` / `半自动化` / `自动化` / `手工` 五类取值均可正确透传；
2. **非法即报错**：未填写（空 / 仅空白）或任意白名单外取值，立即抛结构化映射错误（`reason: 'invalidTestType'`），由上层拼出「第 N 行 案例 [xxx] 的执行方式不合法」等友好文案；
3. **全链路一致**：中文 CSV 分支（`执行方式`）与 YAML 结构化分支（`test_type`）采用同一套校验逻辑，行为一致；
4. **无默认回退**：彻底移除「其它取值默认 '自动化'」的兜底分支，杜绝脏数据静默入库。

---

## 三、功能清单

### 3.1 执行方式合法取值白名单

#### 功能简述
定义「执行方式 / test_type」的合法取值白名单，作为映射阶段的唯一判定依据。

#### 功能内容

##### 3.1.1 白名单取值

| 取值 | 说明 |
|------|------|
| `手工` | 手工执行 |
| `UI自动化` | UI 自动化执行 |
| `接口自动化` | 接口自动化执行 |
| `自动化` | 通用自动化（含未细分类型） |
| `半自动化` | 半自动化执行 |

> 白名单为**封闭集合**，除上表 5 个取值外的任意输入（含空 / 仅空白 / 拼写变体 / 其它任意字符串）均视为非法。

##### 3.1.2 校验入口

- 统一封装为 `resolveTestType(raw, caseTag, rowIndex)` 函数，返回**去空格后**的合法字符串；
- 输入先 `toStr(raw).trim()` 去除首尾空白，再与白名单比对；
- 命中白名单：`TEST_TYPE_VALUES.indexOf(v) !== -1` → 直接 `return v`（即存储**去空格后**的值，如 ` 自动化 ` → `自动化`）；
- 未命中：根据 `v === ''` 区分「未填写」与「取值不合法」两种文案，抛出结构化错误。

---

### 3.2 严格校验与报错

#### 功能简述
未填写或非法取值时，抛出带结构化字段的映射错误，供上层（如 `pushCore.ts`）做友好提示与埋点归类，而不依赖正则解析 message。

#### 功能内容

##### 3.2.1 判定与报错规则

| 输入（执行方式 / test_type） | 映射结果 | 行为 |
|------|---------|------|
| `手工` / `UI自动化` / `接口自动化` / `自动化` / `半自动化`（含首尾空格，如 ` 自动化 `） | 去空格后保留 | 正常映射，不报错（存储值为去空格后的合法值） |
| 空 / 未填写 / 仅空白 | 报错 | 抛 `invalidTestType`，文案提示「未填写」 |
| 其它任意值（如 `手动`、`自动`、`xyz`、带空格的 ` 手动 ` / ` xyz `） | 报错 | 抛 `invalidTestType`，文案提示「取值 "xxx" 不合法」 |

> 注：输入会先 `toStr(raw).trim()` 去除首尾空白再比对。因此合法值带首尾空格（如 ` 自动化 `、``UI自动化 ``）会被去空格后**正常保留并使用**（`自动化` / `UI自动化`）；仅当去空格后仍未命中白名单时（如 ` 手动 ` → `手动`、` xyz ` → `xyz`）才判为非法报错。

##### 3.2.2 结构化错误字段

抛出的错误由 `makeMapError` 构造，携带以下字段，便于上层直接定位：

| 字段 | 取值 | 说明 |
|------|------|------|
| `caseTag` | 案例标识（`testcase_id` / 名称 / `(未命名案例)`） | 与 message 一致的案例定位 |
| `reason` | `'invalidTestType'` | 错误原因短标签，用于埋点归类 |
| `rowIndex` | 主表 1-based 行号 | 从 `row.__rowIndex` 读取，未预贴时为 `undefined` |

错误 message 形如：

```
案例 [<caseTag>] 的「执行方式」未填写，仅支持：手工 / UI自动化 / 接口自动化 / 自动化 / 半自动化。
案例 [<caseTag>] 的「执行方式」取值 "手动" 不合法，仅支持：手工 / UI自动化 / 接口自动化 / 自动化 / 半自动化。
```

##### 3.2.3 调用点

| 分支 | 数据源字段 | 调用 |
|------|-----------|------|
| 中文 CSV 分支（`mapChineseRowToCaseItem`） | `row['执行方式']` | `resolveTestType(row['执行方式'], caseTag, rowIndex)` |
| YAML 结构化分支（`mapRowToCaseItem`） | `row['test_type']` | `resolveTestType(row['test_type'], caseTag, rowIndex)` |

两处调用注释统一为：`// testType：执行方式 → 严格白名单校验（resolveTestType）：命中白名单保留；未填写/其它取值一律抛错，无默认值`。

---

### 3.3 配套梳理（删除无引用转换器）

#### 功能简述
原 `src/utils/yamlToCsvConverter.ts` 内含一份非严格（宽松默认）的「执行方式」转换逻辑，与 mapper 的严格策略冲突，且经全仓库检索**无任何调用方**（无 import / require / 脚本 / 测试引用），属于遗留无用代码。

#### 功能内容

- 该文件已删除，避免宽松逻辑与严格白名单语义冲突、造成维护歧义；
- 全链路「执行方式」校验语义统一收敛到 `pushDataMapper.ts` 的 `resolveTestType` 一处，无第二份实现。

## 四、整体架构

执行方式校验作为字段映射阶段的必填前置校验之一，与既有必填校验（testcase_id、步骤描述、预期结果、路径）并列。该逻辑位于 `pushDataMapper.ts`，经由 `src/services/http.ts` 对所有推送请求（`data.map(mapRowToCaseItem)`）统一生效，与具体来源平台（`testAgent` / `testAgentMA`）无关：

- **映射入口**（`mapRowToCaseItem`）：按表头风格分流中文 CSV / YAML 两分支；
- **校验函数**（`resolveTestType`）：封闭白名单比对，命中保留、未命中抛 `invalidTestType`；
- **错误构造**（`makeMapError`）：统一品牌字段 `__pushDataMapperError__`，供 `isMapError` 跨 realm 判别；
- **上层消费**（`pushCore.ts` 等）：catch 后读取 `reason === 'invalidTestType'` 与 `rowIndex`，拼出「第 N 行 案例 [xxx] 的执行方式不合法」并上报。

校验既不改变其它字段映射逻辑，也不产生默认值回退，纯「拦截 + 报错」。

## 五、验收标准

| 编号 | 验收项 | 标准 |
|------|--------|------|
| AC-1 | 白名单去空格后保留 | `手工` / `UI自动化` / `接口自动化` / `自动化` / `半自动化` 映射后 `testType` 与去空格后的输入一致 |
| AC-2 | 空值报错 | 「执行方式」为空 / 未填写 / 仅空白时抛 `invalidTestType`，文案含「未填写」 |
| AC-3 | 非法值报错 | 任意白名单外取值（如 `手动`、`自动`、`xyz`）抛 `invalidTestType`，文案含「取值 "xxx" 不合法」 |
| AC-4 | 合法值带空格去空格使用 | ` 自动化 ` / ` UI自动化 ` 经 trim 后命中白名单，存储 `testType` 为去空格后的 `自动化` / `UI自动化`，不报错 |
| AC-5 | 非法值带空格仍报错 | ` 手动 ` / ` xyz ` 经 trim 后为 `手动` / `xyz`，仍未命中，判为非法并报错 |
| AC-6 | 结构化字段完整 | 抛出错误带 `reason: 'invalidTestType'`、`caseTag`，命中行号时带 `rowIndex` |
| AC-7 | 报错文案含白名单 | 错误信息中列出全部 5 个合法取值，便于用户自查 |
| AC-8 | CSV 分支一致 | 中文 CSV `执行方式` 与 YAML `test_type` 走同一 `resolveTestType`，行为一致 |
| AC-9 | 无默认回退 | 不再存在「其它取值默认 '自动化'」的兜底分支，非法值不会静默入库 |
| AC-10 | 转换器已移除 | `yamlToCsvConverter.ts` 已删除，全仓库无残留引用，无第二份宽松实现 |
