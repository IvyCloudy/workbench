## 功能简述

本功能对推送到 TMS 的案例内容做**统一的合法性校验**，在内容到达 TMS 之前提前发现问题，降低"半成品被推上去有合规风险"和"字段填错导致推送失败"两类问题。

**解决的问题**
- 案例含「待补充」等未写完内容（合规风险）；
- 枚举字段取值非法、数据类型不符（会导致 TMS 直接拒绝、推送失败）。

**提供的能力**
- **编辑期即时可见**：案例文件在编辑器中打开时，自动高亮不合法内容（黄色=待补充，红色=枚举/类型错误），悬停显示原因，修正后实时消除。
- **推送前兜底拦截**：点击推送时自动校验，命中问题弹窗提示，列出具体案例、命中字段与原因，并支持点击行号跳转定位。
- **分层处理**：「待补充」等质量类问题为软拦截、可忽略继续；枚举非法 / 类型不符等失败类问题为强制阻断、须修正后才能推送。

**校验范围**
- 文本字段（操作步骤 / 步骤数据 / 预期结果 / 前置条件 / 描述）做「待补充」字面量匹配；
- 案例名称（`name` / CSV「名称」）做**非空校验**（error 级，独立于「待补充」匹配）；
- 枚举字段（案例类型 / 执行方式 / 优先级 / 关键案例）做取值合法性校验；
- 数据类型字段（计划执行次数）做类型校验；
- 结构完整性：必备列/字段存在性校验（缺少任一必备列/字段判定为结构性错误，强制阻断）；
- 案例唯一性：同一文件内 `name + path` 组合唯一（重复视为失败类，强制阻断）。
- 对 csv / json / yaml 等案例文件均生效（csv 按中文列名识别字段）。

## 1. 背景与用户场景

各团队把测试案例推送到 TMS（测试用例管理系统）时，最常见、影响最大的几类内容问题，当前都缺乏前置拦截，要么"半成品被推上去有合规风险"，要么"字段填错导致推送直接失败"。归纳为以下场景：

**场景一：案例内容未写完（「待补充」占位）**
- 抽查发现仍有大量案例的**步骤（操作）**和**预期结果**里直接写着「待补充」——也就是还没写完就推上去了。
- 这类案例如果被监管或审计抽查到，属于明显的不合规、不完整的用例，存在考核与合规风险。

**场景二：枚举字段取值不合法，导致推送失败**
- 案例类型、执行方式、优先级、关键案例（key_flag）等字段有固定的允许取值（如执行方式只能是"手工/自动化"）。
- 实际编写中，用户随手填了任意文本、或留空、或填了已废弃的取值，推送时因字段值不在系统允许集合内而被 TMS 拒绝，**推送直接失败**，只能回头逐个排查是哪个字段、哪条案例填错，排错成本高。

**场景三：数据类型不符，导致推送失败**
- 部分字段对数据类型有约定（如计划执行次数 plan_exec_num 应为数值）。
- 当该字段被误填为文本、空值或负数等非数值内容时，后端/接口解析报错，**推送同样直接失败**，且报错往往指向整条案例而非具体字段，定位困难。

用户的共同痛点：
- 目前推送前没有任何提醒，大家很容易在没注意的情况下把半成品、或字段填错的案例推上去；要么有合规风险，要么直接推送失败、反复重试。
- 失败后缺乏"是哪条案例、哪个字段、什么原因"的明确指引，排查全靠人工。

**核心诉求**：在案例推送到 TMS 之前，先对内容做一次统一校验——既拦截「待补充」这类不完整内容（防合规风险），也提前发现枚举非法、类型不符这类会导致推送失败的不合法内容（防推送失败、降排错成本）——给用户一个"拦截 + 提醒 + 可定位"的缓冲。

## 2. 需求

### 2.1 总体要求
本需求对"推送到 TMS 的案例内容"建立**统一的合法性校验**，目标是在内容到达 TMS 之前，把两类问题挡在门外：
- **质量风险**：案例含「待补充」等未写完内容（合规风险）；
- **推送失败风险**：枚举取值非法、数据类型不符等导致 TMS 直接拒绝（重复重试、排错成本高）。

整体框架如下：
- **六种校验机制，互不替代**：
  1. 文本字段 → 「待补充」字面量匹配（防未写完）；
  2. 案例名称 → 非空校验（防案例无法被识别定位，error 级独立硬拦截）；
  3. 枚举字段 → 取值合法性校验（防非法取值）；
  4. 数据类型字段 → 数据类型校验（防类型错误）；
  5. 结构完整性 → 必备列/字段存在性校验（防必备列/字段缺失导致的推送失败）；
  6. 案例唯一性 → 同一文件内 `name + path` 组合不得重复（防同名案例互相覆盖导致的推送失败）。
- **两个触发入口，共用同一规则**：
  1. 打开案例文件时 → 自动高亮不合法内容（编辑阶段即时可见）；
  2. 点击推送时 → 自动校验兜底（拦截 + 弹窗提醒）。
- **分层处理原则**（按问题性质区分，避免"可忽略"与"防推送失败"互相矛盾）：
  - **质量类问题**（「待补充」等未写完内容，属合规风险）：**软拦截**——列出具体案例 + 命中字段 + 原因 + 支持点击行号跳转定位，用户可**忽略并继续推送**。
  - **失败类问题**（枚举非法 / 数据类型不符，会导致 TMS 直接拒绝、必然推送失败）：**强制阻断**——不允许忽略，提示明确告知"将导致推送失败，请修正后再推送"，用户须修正后才能推送。
  - **结构类问题**（必备列/字段缺失，会导致本文件所有案例都无法被正确解析或推送）：**强制阻断**——不允许忽略，且在打开文件时即弹窗告知具体缺失项，须补齐后才能继续使用。
  - **唯一性问题**（同一文件内 `name + path` 组合重复）：**强制阻断**——不允许忽略。重复案例会在 TMS 侧互相覆盖或被拒绝，用户须修改重复案例的名称或路径后才能推送。

以下各小节分述"触发交互 / 校验内容与规则 / 命中处理"。

### 2.2 校验触发与交互
#### 2.2.1 打开文件时自动高亮
案例文件（csv / json / yaml 等）在案例编辑器中打开时，系统自动扫描内容，并对不合法处做**视觉高亮**，让用户在编辑阶段就能立即发现问题，而不必等到推送才暴露。
- **「待补充」文本**：所在单元格高亮（**黄色**底色 + 左侧竖条 + 右上角 ⚠ 小角标），悬停提示 `⚠️ 格式校验失败：含「待补充」，请完善`。
- **枚举取值非法 / 数据类型不符 / 案例名称为空 / 案例名称重复**：对应单元格高亮（**红色**底色 + 左侧竖条 + 右上角 ⚠ 小角标），悬停提示具体字段级原因（如 `⚠️ 格式校验失败：执行方式=xxx（应为 手工/自动化）`、`⚠️ 格式校验失败：计划执行次数=xxx（应为非负整数）`、`⚠️ 格式校验失败：案例名称未填写`、`⚠️ 格式校验失败：重复案例名称`）。
- **必备列/字段缺失**：打开文件时先做一次**结构性检查**（详见 2.3.7），若缺少任一必备列/字段，**弹窗**列出缺失项并提示"缺列会导致推送失败，请补齐后再使用"；此为文件级问题，不做单元格高亮。
- **高亮粒度**：**字段级精确高亮**——只对命中问题的字段所在单元格上色，不做整行铺红；对 json / yaml 多步骤数组，定位到对应步骤行的具体子字段（如 `steps[2].operation`）。
- **hover 交互**：悬停单元格显示的是**该单元格自身命中的字段级原因**（而非整行聚合），首行统一带 `⚠️ 格式校验失败：` 前缀便于用户与正常内容区分。
- 高亮为**只读提示**，不阻止编辑；修正内容后高亮实时消除（保存文件即触发重扫）。
- **性能**：扫描为异步/增量执行，避免大文件打开时卡顿。

#### 2.2.2 推送前自动校验
每次把案例推送到 TMS 之前，系统自动检查本次要推送的案例内容，不依赖用户手动检查。
- 该入口与 2.2.1 共用同一套校验规则与字段清单，保证两处口径一致。
- **单文件推送**：webview 内直接弹出"案例格式校验"面板，展示命中清单；含 error 级问题时隐藏"忽略并继续"按钮，仅可关闭；仅含 warn 级问题时提供"忽略并继续"选项。
- **批量推送**：先按文件顺序逐个执行 `validateFileForPush`（纯校验，无落盘、无埋点），完成后按文件聚合展示。文件名可点击进入对应文件；点击后若目标文件尚未在编辑器打开，则打开并弹出该文件的校验详情弹窗（复用 2.2.1 的弹窗组件），若已打开则直接聚焦不重复弹窗。
- 命中后的具体提示与处理见 2.4。

### 2.3 校验内容与规则
#### 2.3.1 检查字段
以下字段需纳入校验，字段按 yaml 模版与 csv 模版一一对应（csv 以中文列名呈现）。

**必查字段（高风险）：**
- 操作步骤：yaml `steps[].operation` ↔ csv「步骤描述」
- 步骤数据：yaml `steps[].data` ↔ **CSV 无独立列**（CSV 模板未拆分数据列，步骤级内容全部写入「步骤描述」；因此 CSV 端仅通过「步骤描述」承载步骤内容，`steps[].data` 的独立字段级校验仅在 YAML/JSON 生效）
- 预期结果：yaml `ui_expected` / `api_expected` / `db_expected`（三条检查点均需覆盖） ↔ csv「预期结果」
- 前置条件：yaml `preconditions` ↔ csv「前置条件」
- 案例类型：yaml `type` ↔ csv「案例类型」
- 执行方式：yaml `test_type` ↔ csv「执行方式」
- 优先级：yaml `priority` ↔ csv「优先级」
- 关键案例：yaml `key_flag` ↔ csv「关键案例」
- 计划执行次数：yaml `plan_exec_num` ↔ csv「计划执行次数」

**独立硬拦截字段（error 级，非空校验，详见 2.3.5）：**
- 案例名称：yaml `name` ↔ csv「名称」

**建议补充核查字段（信息完整性，走文本「待补充」匹配）：**
- 案例描述：yaml `description` ↔ csv「案例描述」

**唯一性判定键（跨行判定，详见 2.3.6）：**
- 案例名称 `name` + 路径 `path` 组合在同一文件内不得重复（name 还同时受 2.3.5 非空校验约束）。

**说明：**
- 字段校验机制归属：**文本字段**（操作 / 步骤数据 / 预期 / 前置条件 / 描述）走 2.3.2「待补充」字面量匹配；**案例名称**走 2.3.5 非空校验（error 级独立硬拦截）；**枚举字段**（案例类型 / 执行方式 / 优先级 / 关键案例）走 2.3.3 取值合法性校验；**数据类型字段**（计划执行次数）走 2.3.4 类型校验。
- `steps` 为数组，校验需逐条遍历每个步骤的 `operation` / `data` / 各类 `expected`。
- csv 的「步骤描述」「预期结果」为步骤级多行文本，需按步骤解析后逐段匹配。
- 枚举型字段不做「待补充」字面量匹配。

#### 2.3.2 「待补充」匹配规则（文本校验）
采用**极简子串命中**策略：字段内容里只要出现**待补充**三字（无需前后带「」或其它括号）即视为命中。不做语义判断，仅做字符串包含判定；命中样本包括但不限于：`「待补充」`、`【待补充】`、`[待补充]`、裸文本 `待补充`、多行文本中独立一行的 `待补充` 等。

#### 2.3.3 枚举字段合法性校验
枚举型字段需做**取值合法性校验**：字段值必须落在系统允许的取值集合内，否则视为不合法。

- **案例类型**（`type`）：取值应为系统定义的案例类型集合，如 功能点类 / 流程类 / 界面类 等。
- **执行方式**（`test_type`）：取值应为 手工 / 自动化。
- **优先级**（`priority`）：取值应为 高 / 中 / 低。
- **关键案例**（`key_flag`）：取值应为系统定义的关键用例集合，仅支持「是 / 否」，具体以系统枚举为准。

校验规则：
- 字段为空、或取值不在允许集合内（含随手填写的任意文本）均判定为**不合法**。
- 具体允许取值以系统实际枚举为准（模版中以"…"表示可扩展）。

#### 2.3.4 数据类型校验
部分字段需校验**数据类型**是否与约定一致。当前纳入：

- **计划执行次数**（`plan_exec_num`）：数据类型应为**数值（建议非负整数）**；出现非数字、空值或文本均判为不合法。

校验规则：
- 若业务允许小数或限定取值范围，以系统约定为准，可在此扩展范围校验（如要求 ≥ 0）。

#### 2.3.5 案例名称非空校验（`name` / CSV「名称」不得为空）

对每条案例的**案例名称**做**独立非空校验**：当 `name` 缺失、为空串或仅含空白字符时，视为**失败类**问题，**强制阻断**。

**背景**：案例名称是 TMS 上的核心可读标识，一旦为空会导致该条案例无法被识别与定位；且案例名称字段不参与「待补充」字面量匹配（不能因为空字符串代替内容而绕过质量校验），因此单独立一条硬拦截规则。

**判定规则**：
- 归一化后判空：先对 `name` 值做 `trim()`，若结果为空字符串则命中。
- 覆盖场景：YAML/JSON 中 `name` 键缺失、值为 `""` 或 `"   "` / `"\t"` 等仅空白字符；CSV 中「名称」列单元格为空或仅空白。
- 命中范围：逐行判定，每条命中案例的「名称」单元格红色高亮，hover 显示 `⚠️ 格式校验失败：案例名称未填写`。
- 与其它校验的关系：**该行不再参与 2.3.6 `name+path` 唯一性判定**（避免"空名称互相视为重复"的语义冲突）；其它字段仍照常校验。

**命中处理**：
- 严重级别：`error`（category=`testCaseName.empty`），与枚举/类型错误同层，`hasError=true` 时不允许忽略。
- 用户须在 `name` / 「名称」列填写非空且非纯空白的内容后才能推送。

#### 2.3.6 案例唯一性校验（`name + path` 同文件内不得重复）

对同一文件内的案例做**跨行唯一性**校验：以案例的 `name`（案例名称） + `path`（路径）作为联合唯一键，若出现两条或以上完全相同的组合，视为**失败类**问题，**强制阻断**。

**判定规则**：
- 归一化后比较：两侧字段先做 `trim()`；`name` 或 `path` 任一为空的行**不参与**重复判定（空 `name` 由 2.3.5 独立处理，避免语义冲突）。
- 命中范围：同一文件内所有非样例行；跨文件不做判定。
- 高亮策略：**只标红命中重复的 `name` 单元格**（`path` 单元格不上色，避免误导用户以为路径出错），hover 显示 `⚠️ 格式校验失败：重复案例名称`。

**设计说明（与 §4「字段级精确高亮」原则的关系）**：
- 本规则的判定键虽为 `name + path` 组合，但高亮策略**有意仅高亮 `name` 单元格**。原因：
  1. 用户在 TMS 侧感知的重复实体是"案例名称"，双色会误导为"路径也有问题"；
  2. 修复动作首选为修改 `name`，高亮位置与修复鿰头对齐可降低理解成本；
  3. 本机制为 **§4 字段级高亮原则的一个特殊变例**（判定键 ≠ 高亮字段），需在实现中保持一致。如后续用户反馈 `path` 也需直观提示，可升级为双单元格高亮 + hover 展示"归属重复组合"。

**命中处理**：
- 严重级别：`error`，与枚举/类型错误同层；`hasError=true` 时不允许忽略。
- 用户需修改重复案例的 `name` 或 `path` 使组合唯一后才能推送。

#### 2.3.7 必备列/字段存在性校验（结构完整性）

对文件级结构做兜底校验：若缺少下列任一**必备列（CSV）**或**必备字段（YAML / JSON）**，视为**结构性错误**，属**失败类**问题，**强制阻断**。

**必备列/字段清单**（YAML 键 ↔ CSV 中文列名）：

| YAML 键 | CSV 中文列名 |
|---|---|
| `name` | 名称 |
| `path` | 路径 |
| `description` | 案例描述 |
| `preconditions` | 前置条件 |
| `type` | 案例类型 |
| `test_type` | 执行方式 |
| `priority` | 优先级 |
| `steps[].operation` | 步骤描述 |
| `steps[].ui_expected` / `api_expected` / `db_expected`（三者至少出现其一） | 预期结果 |

**判定规则**：
- **CSV**：以表头行为准，检查上述中文列名是否全部存在；缺任一即命中。对"预期结果"，CSV 只有一列合并列，存在即通过；具体单元格是否为空由行级校验负责，与本条无关。
- **YAML / JSON**：以整个文件所有案例为整体判定——若**全文件所有案例**均未出现某必备键，则该键命中缺失（即：只要文件中至少有一条案例包含该键，则视为该键存在，不命中）。这样做是为了避免误伤单条案例暂缺某键的中间态。
- **`steps.*_expected` 至少一个`：YAML/JSON 只要文件中出现过 `ui_expected` / `api_expected` / `db_expected` **任一键**即算通过；三者全部缺失才命中。CSV 只要有「预期结果」列即通过。
- **触发范围**：打开文件时 + 推送前，两处共用同一清单与判定规则。

**关于 YAML/JSON"整文件聚合判定"的设计权衡与盲区提醒**：
- 本规则采用"**文件内至少有一条案例包含该键即视为存在**"的宽容策略，目的是避免单条案例处于编辑中间态时被误拦。但它存在**已知的盲区**：当大部分案例均缺某键、仅少数案例包含时，本规则会判定为结构完整，但缺键行仍会在 TMS 侧失败。
- **补偿层**：行级必填字段如果为空，已由其它行级校验处理——如 `name` 由 2.3.5 非空硬拦截、`type` / `test_type` / `priority` / `key_flag` 由 2.3.3 枚举校验（空值属不合法取值）、`plan_exec_num` 由 2.3.4 类型校验拦截。因此行级空值在大多数情形下仍能被拦住，不会真正“漏”到 TMS。
- **仅写入 `path` / `description` / `preconditions` / `steps` 等未接入行级硬拦截的字段**，存在“部分案例未写则本次不拦，推送后对应条次失败”的小概率遗漏。后续如回收到真实漏接案例，可考虑升级为"每行都检查必填键存在"的严格模式（作为可配项）。

**命中处理**：
- 打开文件时：**弹窗**列出全部缺失列/字段（一次性汇总，不逐条弹），文案示例：`当前文件缺少必备列/字段：路径、案例描述、前置条件……缺列会导致推送失败，请补齐后再使用。`
- 推送时：**强制阻断**，不允许忽略；错误级别与枚举/类型错误同层（error），提示文案统一走"失败类"提示。
- **优先级**：结构性错误优先于行级校验展示——若本文件已命中必备列/字段缺失，其它行级校验结果可延后或折叠展示，避免噪音。

### 2.4 命中后的处理
#### 2.4.1 提示与定位
校验命中后弹出提示，按问题性质给出不同文案：
- **质量类（「待补充」等未写完内容）**：
  > 您的案例存在「待补充」等未写完内容，请完善后再推送。
- **失败类（案例名称为空 / 枚举非法 / 数据类型不符 / 案例名称重复）**：
  > 您的案例存在不合法内容（如案例名称为空、非法枚举、类型错误、重复案例名称），将导致推送失败，请修正后再推送。
- **结构类（必备列/字段缺失）**：
  > 当前文件缺少必备列/字段（如：路径、案例描述、前置条件……），将导致推送失败，请补齐后再使用。

提示应做到：
- **列出具体命中的案例与原因**：展示是哪一条（或哪几条）案例命中、命中在哪个字段、属于哪类问题，方便用户定位。
- **批量推送聚合**：多文件批量推送时，按文件聚合展示命中清单，避免信息散落。
- **支持点击行号跳转定位**：清单每一组的组头以 `第 N 行` 展示，可点击直接跳转至编辑器对应行；文件级问题（缺必备列/字段）展示为 `📁 文件级问题`；无行号且带 `testcase_id` 的场景（罕见），以 `testcase_id 前8位…` 显示，方便识别但不承担跳转职责。

> 注：早期设计曾提供"一键复制案例 ID"入口（并规约 `testcase_id` 缺失时以"文件路径 + 行号"兜底的中间省略展示形态），现按用户反馈已移除该图标——多数用户不需要复制 `testcase_id`，且额外按钮反而挤占卡片可读区域；如需定位改由行号点击跳转承担。

#### 2.4.2 分层处理：可忽略 vs 强制阻断
- **质量类（「待补充」）— 软拦截，可忽略**：用户确认知晓风险后，可选择"忽略提示，仍然继续推送"，系统照常推送。
- **失败类（案例名称为空 / 枚举非法 / 数据类型不符 / 案例名称重复）— 强制阻断，不可忽略**：此类内容会被 TMS 拒绝、必然推送失败或导致互相覆盖，因此不允许忽略；用户须修正对应字段后才能推送（可关闭提示回到编辑器修正，修正后重新推送）。
- **结构类（必备列/字段缺失）— 强制阻断，不可忽略**：此类问题会导致本文件所有案例都无法被正确解析或推送，因此不允许忽略；用户须补齐缺失的列/字段后才能推送。打开文件时即弹窗告知，无需等到推送。

### 2.5 校验结果面板 UI（对应 2.2 两入口共用弹窗）

本节描述编辑期高亮弹窗与推送前 gate 弹窗共用的"案例格式校验"面板结构，两处入口 UI 一致：

- **标题**：`案例格式校验（阻断）` 或 `案例格式校验（提醒）` —— 依据本次命中是否包含 error 级切换。
- **主按钮**：`忽略并继续`（仅 warn 级独立命中时可见）/ `关闭` / `重新校验`。含 error 级时隐藏"忽略并继续"按钮。
- **命中清单**：按"案例"聚合，每行展示：
  - 组头行标识：优先 `第 N 行`（可点击跳转至编辑器对应行）；文件级问题显示 `📁 文件级问题（缺必备列/字段）`；无行号且带 `testcase_id` 时显示 `testcase_id 前8位…`（罕见分支）；
  - 命中字段名（如"执行方式"、"步骤描述"、"计划执行次数"、"案例名称"、"关键案例"）；
  - 具体原因（如 `执行方式=xxx（应为 手工/自动化）`）；
  - 严重级别标签（error/warn 分色）+ 组头右侧「阻断 X · 提醒 Y」分类计数。
- **分类汇总**：清单顶部按类别小计（如 `重复案例名称 × 2 / 执行方式非法 × 1 / 待补充 × 3`）。
- **批量推送场景**：先按文件汇总展示（只有"文件名 + 该文件汇总结果"两列，不展开每案例明细），点击文件名进入对应文件并弹出该文件的详情面板（已打开的文件直接聚焦，不重复弹窗）。

## 3. 使用预期（用户视角）

**入口一：打开文件即高亮**
- 在案例编辑器打开 csv / json / yaml 等文件时，含「待补充」的单元格高亮为**黄色**、枚举非法或类型不符的单元格高亮为**红色**，悬停可见具体原因，编辑阶段即可发现并修正（多步骤数组定位到对应步骤行）。

**入口二：推送前自动校验（兜底）**
- 点击"推送" → 系统先扫描本次要推送的案例（同时做「待补充」匹配、枚举合法性、数据类型校验）。
- **全部通过** → 正常进入推送流程，无额外打扰。
- **存在「待补充」、枚举不合法或数据类型不合法** → 弹出提示，列出命中的具体案例（含行号可点击跳转），告知"请完善后再推送 / 请修正不合法字段"。
- 用户有两种选择：
  - **去完善**：关闭提示，回到编辑器补全内容或修正字段后再推送；
  - **仍要推送**：点击"忽略并继续"，系统照常推送。
- 该校验对 csv / json / yaml 等各类型案例文件均生效（csv 按中文列名识别对应字段）。
- 两处入口（高亮 / 推送前）共用同一校验规则，结果口径一致。

## 4. 设计原则与边界

- **六类校验机制不同**：文本字段（操作 / 步骤数据 / 预期 / 前置条件 / 描述）仅做「待补充」字面量匹配，不判断内容是否真的完整；案例名称（`name` / CSV「名称」）做独立非空校验（error 级）；枚举字段（案例类型 / 执行方式 / 优先级 / 关键案例 key_flag）做取值合法性校验；数据类型字段（计划执行次数 plan_exec_num）做类型校验；结构完整性做必备列/字段存在性校验；案例唯一性做同一文件内 `name + path` 重复判定。六者互不替代。
- **分层处理（软拦截 + 强制阻断）**：「待补充」等质量类问题为软拦截、可忽略，兼顾合规要求与紧急推送；案例名称为空 / 枚举非法 / 数据类型不符 / 结构性缺列 / `name+path` 重复等失败类问题为强制阻断、不可忽略，因为内容必然被 TMS 拒绝或导致互相覆盖，避免"忽略后依旧失败"的无效体验。
- **字段覆盖完整**：文本目标字段（操作 / 步骤数据 / 预期 / 前置条件 / 描述）均需覆盖，且 csv 的中文列名场景不可遗漏；案例名称走独立非空硬拦截；枚举字段覆盖案例类型 / 执行方式 / 优先级 / 关键案例；数据类型字段覆盖计划执行次数。
- **字段级精确高亮与 hover**：高亮粒度降到单元格字段级，不做整行铺红；hover 只展示该单元格自身的命中原因（不叠加同行其它字段），保证位置与原因一一对应；右上角 ⚠ 小角标用于快速视觉识别，不影响内容可读性。
- **跨入口口径一致**：编辑期高亮与推送前 gate 走同一套 `runValidators + DEFAULT_VALIDATORS`（包含 `scanDuplicateNameRows` batch 扫描），保证字段清单、判定规则、严重级别一致。
- **可定位、可追溯**：通过"列出具体案例 + 行号点击跳转 + 单元格级高亮"降低用户排查成本，也便于后续统计哪些团队/文件高频出现问题。（注：留痕/埋点机制不在本需求范围，本需求仅保证提示可定位。）

## 5. 验收要点（建议）

1. 推送含「待补充」的案例时，弹出**质量类**提示且文案正确，提供"忽略并继续"入口，点击后案例正常推送。
2. 推送含枚举非法（案例类型 / 执行方式 / 优先级 / 关键案例）或类型不符（计划执行次数非数值）的案例时，弹出**失败类**提示且文案明确"将导致推送失败"，且**不允许忽略**，必须修正后才能推送。
3. 提示中能展示命中的具体案例、命中字段与原因，并支持通过行号点击跳转到编辑器对应行；文件级问题以 `📁 文件级问题` 呈现，不承担跳转。
4. 多文件批量推送时，命中项按文件聚合展示，不散落。
5. 不含「待补充」、枚举合法且类型合法时，推送无任何额外提示。
6. csv 文件按中文列名正确识别**全部**字段（含枚举字段：案例类型 / 执行方式 / 优先级 / 关键案例，及计划执行次数）并校验。
7. 命中规则为"子串包含"：裸文本 `待补充`（无括号）、`[待补充]`、`【待补充】` 等变体均命中。若业务从严收敛（仅全角「」才命中），可在后续版本另行约定。
8. 枚举字段取值合法时，不因"非待补充"的任意文本而误报（合法性以枚举集合为准，非字符串匹配）。
9. 打开案例文件（csv / json / yaml）时，含「待补充」的单元格**黄色**高亮、枚举非法 / 类型不符的单元格**红色**高亮，悬停显示原因；多步骤数组定位到对应步骤行；修正后高亮实时消除；大文件打开不卡顿。
10. 高亮 / 推送前校验两处入口共用同一校验规则与字段清单，口径一致。
11. 单元格 hover 提示为**字段级 reason**（仅显示该单元格自身命中的原因，不叠加整行其它字段的原因），首行带 `⚠️ 格式校验失败：` 前缀；命中单元格右上角有 ⚠ 小角标便于视觉辨识。
12. 打开案例文件时，若缺少任一必备列/字段（`name` / `path` / `description` / `preconditions` / `type` / `test_type` / `priority` / `steps.operation` / `steps.*_expected` 至少一个，或对应 CSV 中文列名），弹窗一次性列出全部缺失项，文案明确"将导致推送失败"。
13. 推送含必备列/字段缺失的文件时，弹出**结构类**提示且**不允许忽略**，必须补齐后才能推送；结构性错误在展示上优先于行级校验结果。
14. 同一文件内出现两条以上 `name + path` 完全相同的案例时，弹出**失败类**提示且**不允许忽略**；只标红命中重复的 `name` 单元格，hover 提示 `⚠️ 格式校验失败：重复案例名称`；`name` 或 `path` 为空的行不参与重复判定。
16. YAML `name` 键缺失、值为空串、或仅含空白字符（`" "`、`"\t"` 等），以及 CSV「名称」列为空时，弹出**失败类**提示且**不允许忽略**（category=`testCaseName.empty`，error 级）；该单元格红色高亮，hover 显示 `⚠️ 格式校验失败：案例名称未填写`；命中行不参与 `name+path` 唯一性判定。
15. 批量推送场景下，弹窗按"文件名 + 该文件汇总结果"两列展示，点击文件名进入对应文件；若目标文件尚未打开则打开并弹出该文件详情面板，已打开的文件直接聚焦，不重复弹窗。

> 备注：枚举字段的允许取值集合、数据类型取值范围，以系统实际定义为准（需求中以"…"标注处待确认）。
