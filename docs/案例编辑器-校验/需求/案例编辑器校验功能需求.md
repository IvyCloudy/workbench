## 1. 背景与目标

当前案例推送失败率较高，而现有度量体系（`pushFailureCategory` + `*.complete` 埋点）均为**推送之后**才生效——一次失败意味着：一次失败的接口调用、一次失败的回写、一次用户等待。

从推送链路（`pushCore.stages.ts`）看，推送前的本地拦截仅有 4 道（任务绑定、`testcase_id` 占位/空/格式、模板样例行、YAML 语法）。而真实后端报错场景（`推送失败度量说明.md` §4 的 43 类）中，**绝大多数行级字段错误（empty / length / enum / format）和全部接口级字段错误（designer / artifactId / sourcePlatform）都未在前置阶段拦截**，直接打到后端才返回失败。

**本功能目标**：在案例编辑器（表格 webview）内提供「校验」能力，把"哪一行、哪一格、什么问题"精确呈现；支持两种触发：**编辑期自动校验**（打开 / 编辑防抖时自动跑一遍）与**手动触发校验**（工具栏「校验」按钮）。对于其中**确定性可修复**的问题（必填空值、格式可归一化项），由独立的修复功能承接，本文档只做**定位与展示**，不自动改值。

**与现有 YAML 修复的关系（重要）**

| 维度 | 现有 YAML 修复（YamlFixProvider） | 本功能（编辑器字段校验） |
|------|-----------------------------------|---------------------------|
| 作用对象 | YAML **文本行**（语法层：缩进 / 重复键 / 解析错误） | **字段 / 单元格**（语义层：空值 / 枚举 / 格式） |
| 触发位置 | 文本编辑器灯泡菜单 / 命令面板 | 案例编辑器（表格 webview）自动 + 工具栏按钮 |
| 修复落点 | 整行文本替换 | 具体 `[row, col]` 单元格值（修复见独立文档） |
| 复用关系 | 独立 | 复用其"批量修复"心智 + 同一落盘通道 |

两者互补：YAML 修复解决"文件打不开 / 解析错"；本功能解决"能打开但推不过"。

## 2. 术语与前提

| 术语 | 含义 |
|------|------|
| 单元格 `[row, col]` | 主表中具体一格，`row` 为数据行下标（0-based），`col` 为列下标（0-based），与既有 `highlightedCells.cells` 坐标体系一致 |
| 字段码 `field` | 底层英文 key（如 `testCaseName` / `testCasePath` / `description` / `expected`），经 `headerLabels` 映射为中文列名展示。**后端只回传 `field`，`col` 由前端用 `headerLabels` 反查得到**（避免后端依赖前端列序） |
| `CellIssue` | 一条校验问题，携带 `row / field / category / reason`（修复相关字段 `fixable / fixValue / suggestion` 由修复功能定义）。**同一 `[row, col]` 可能命中多条规则（如空值 + 超长 + 非法字符），前端按格聚合为一条展示** |
| 行级校验能力 | 校验与推送预校验共用的行级字段校验能力，非抛错式收集一行内全部问题，复用既有的必填 / 长度 / 枚举 / 格式约束；具体函数形态属技术实现（见配套技术设计文档），不在需求范围 |
| `highlightedCells.cells` | 既有单元格高亮机制，结构为 `[row, col]` 数组；本功能前端将 `CellIssue` 映射为该项以触发红底 |
| 冻结行 / 冻结列 | 样例数据行（`testcase_id` 占位值）整行只读；`testcase_id` 列系统列不可编辑（既有冻结行 / 冻结列约束） |

## 3. 功能需求

### 3.1 工具栏「校验」按钮

#### 需求背景与目标
用户编辑案例后、推送前，缺少一个"先自查"的入口。目标是：在编辑器工具栏提供常驻「校验」按钮，点击后跑一遍行级校验，给出"可推送性"结论，而非等到推送才报错。

#### 交互与功能规则
- **入口位置**：工具栏新增「校验」按钮，与现有「推送」「查找」按钮并列。
- **校验范围**：
  - **默认校验全表**：对所有非样例行执行行级校验。
  - **过滤视图（如"仅看失败行"）下的可见性**：校验基于全量数据行（不受前端过滤影响），但结果面板可与过滤视图叠加显示；"隐藏行误伤"风险见 §5.2。
- **触发行为**：点击后触发一次行级校验（基于当前已加载的表格数据，无需重新解析文件），略过样例行，对每行收集校验问题并回推结果。
- **结果呈现**：以「校验结果面板」（复用编辑器现有的结果弹窗样式，代号 05g）列出每条问题；无问题时提示"校验通过，可推送"。
- **与推送预校验一致性**：校验规则应与推送前的本地预校验规则共用同一份字段约束（以推送预校验为唯一权威源），确保"校验通过"即代表"推送时不会因行级字段错失败"；任一侧新增 / 修改字段约束须同步另一侧。


### 3.2 单元格级问题定位

#### 需求背景与目标
推送失败弹窗只能给"行号 + 文案"，用户还要自己找列。目标是：校验发现的每个问题都能**精确高亮到具体单元格**，用户一眼看到"哪一格"有问题。

#### 交互与功能规则
- **列映射**：后端回传 `field`（英文 key），前端经表头映射关系反查 `col`（列下标）；若某 `field` 在当前表头中**找不到对应列**（如新增字段未纳入映射、或中文表头列名漂移），则降级为**高亮整行**并在面板标注"列缺失，请检查表头映射"，不静默丢弃该问题。
- **红底高亮**：每条 `CellIssue` 经单元格高亮机制精确渲染到具体单元格，复用现有单元格级红底样式。同一格的多条问题聚合为一条展示，高亮与定位均作用于该 `[row, col]` 单格。
- **点击定位**：结果面板每条问题带「定位」按钮，点击滚动到该格并临时聚焦高亮；与现有"推送失败行定位"体验一致。
- **字段名可读**：面板显示「行 N · 中文列名（field）· 原因」，中文列名经 `headerLabels` 映射得到，便于非技术用户理解。

### 3.3 不可修复项的引导

#### 需求背景与目标
C 类问题（语义不符、需业务判断）系统不应擅自改写，否则可能破坏案例真实性。目标是：对这类问题只做"定位 + 建议值文案"，由用户手改。确定性可修复项由独立的修复功能承接，本文档只定位不修复。

#### 交互与功能规则
- **C 类处理**：不显示「修复」按钮，仅显示「定位」+ 原因说明 + **建议值文案**，但建议值**不自动写入**，由用户手改。建议值仅在结果面板以文案展示，不触发任何写盘。
- **建议值文案来源（明确）**：
  - 若为"枚举非法但非别名"（如 `testType` 拼错）：建议值 = 枚举白名单列表（如"建议改为：手工 / UI自动化 / 接口自动化 / 自动化"）——**静态话术，由系统枚举白名单生成**。
  - 若为"步骤 / 预期缺失"：建议值 = 通用补全提示（如"建议至少补充一个步骤"）——**静态话术**。
  - 若为"语义数量不一致"（预期数 ≠ 步骤数）：当前**仅给提示文案，不计算具体建议值**。
- C 类保持原样并在面板中标注"需手动处理"，其建议值仅作展示。

### 3.4 编辑期自动校验

#### 需求背景与目标
除手动点击「校验」外，文件**打开**与**编辑过程**也应主动校验，做到"问题早发现"：打开文件即检查结构性缺列与行级失败并弹窗；编辑防抖后自动重跑，刷新高亮与弹窗。

#### 交互与功能规则
- **触发时机**：
  - **打开文件**：文件在编辑器打开时自动跑一次校验（文件级缺列 + 行级失败），命中即弹窗（05g）展示，不阻断打开。
  - **编辑防抖**：用户在表格内编辑（单元格写回 / 增删行）后防抖触发重跑，刷新校验结果面板与单元格高亮。
- **展示与落盘**：校验结果写入编辑器侧的失败盘（`push-failures.json`），供前端渲染红 / 黄底高亮；打开弹窗通过 `postFileLevelPreValidateGate` 呈现，编辑后刷新通过 `postEditValidationRefresh`。
- **降级与抑制**：解析失败 / 竞态场景不阻断；同一文件重复打开有抑制 / 序列保护，避免重复弹窗。

### 3.5 推送前预校验与门控

#### 需求背景与目标
点击「推送」进入 `runPush` 前，先做一遍本地预校验，能拦截的（必填列缺失、testcase_id 占位/空/格式、枚举、计划执行次数、名称空、重名、待补充等）在前端拦截掉，避免打到后端才失败。

#### 交互与功能规则
- **预校验类型（按 kind 分别上报，详见埋点文档 §4.11）**：缺失必填列、占位 `TESTCASE_ID`、空 `testcase_id`、格式非法、枚举取值非法、计划执行次数非法、名称为空、同文件重名、内容含「待补充」软拦截。
- **拦截语义**：
  - error 级（占位 / 空 / 格式 / 枚举 / 计划执行次数 / 名称空 / 重名）→ 对应行从 payload 剔除、不参与后端推送；
  - warn 级（「待补充」等）→ 不剔除，行仍参与推送，仅高亮提示。
  - 结构性缺列（必填列缺失）→ 所有行剔除、推送短路。
- **推送门控（preValidateGate）**：预校验存在 error 级失败 → 门控**阻断**推送（用户无法继续，reason=`preValidateGateBlocked`）；仅有 warn 级 → 弹确认，用户点「取消」放弃推送（reason=`preValidateGateCancelled`），点「继续」才放行。

#### 字段级校验要求（不同字段要求不一致）
> 各字段校验严格度并不一致，明确如下（字段码以 `headerLabels` 为准），供实现与验收核对：
> - **硬约束（error，推送必失败，须修）**：`testcase_id`（标识，必填 + 格式 + 唯一，冻结列只读、样例行占位跳过）、`testCaseName`（名称，必填）、`type`（案例类型，枚举 13 项白名单）、`test_type`（执行方式，枚举白名单，且支持简写 `接口`→接口自动化、`界面`→UI自动化 大小写不敏感归一）、`priority`（优先级，高/中/低）、`key_flag`（关键案例，是/否）、`planExecCount`（计划执行次数，非负整数）。
> - **软约束（warn，可忽略继续）**：`description` / `expected` / `testCaseDes` 等内容字段，含 `待补充` / `TODO` 等占位仅黄底提示；步骤 / 预期缺失属 C 类仅提示不修。
> - **接口级（本地不可校验，仅提示边界）**：`designer` / `artifactId` / `sourcePlatform` 等仅后端可判定，须在面板提示「校验通过 ≠ 一定推送成功」。
> 说明：硬约束由行级校验统一收集；软约束不阻断推送但参与高亮；接口级字段缺失 / 错误只能推送后置发现（见 §5.1）。

### 3.6 单元格高亮持久化

#### 需求背景与目标
校验发现的"有问题单元格"需以红 / 黄底在表格内持续高亮，且关闭 / 重开 / 重启 VSCode 后不丢失，便于用户边改边看。

#### 交互与功能规则
- **着色规则**：error 级（占位 / 格式非法 / 枚举 / 计划执行次数 / 名称空 / 重名）→ 红底；warn 级（「待补充」）→ 黄底；前端按 `field` / `[row, col]` 精确染色。
- **持久化**：校验结果写入 `globalStorageUri/push-failures.json`，以文件绝对路径为 key；编辑 / 推送 / 重开时重新加载，覆盖旧标记。

### 3.7 埋点

校验全流程的埋点事件与维度（含 `columns` 列名维度）见 `测试案例用户行为埋点需求.md` §4.11（实现状态以该文档为准），核心事件：
- 编辑期：`editValidation.missingColumnsDetected` / `editValidation.openPromptFailures` / `editValidation.failuresDetected`；
- 推送前：`${telemetryPrefix}.missingColumnsDetected` 及 8 个 `.xxxSkipped`（`telemetryPrefix` 为 `explorerPush` / `editorPush`）；
- 门控：`${telemetryPrefix}.aborted`（reason=`preValidateGateBlocked` / `preValidateGateCancelled`）。

### 3.8 批量推送多文件预校验

#### 需求背景与目标
实际使用中常需一次性推送多个案例文件。目标是：批量推送时对每个目标文件逐一执行与单文件一致的本地预校验，且单文件失败**不阻断**其他无错文件，最终聚合成清晰的「成功 / 失败」结果，避免「一个坏文件拖垮整批」。

#### 交互与功能规则
- **逐文件预校验**：批量推送（多选文件 / 多案例推送）时，对每个目标文件分别执行 §3.5 的 `stepPreValidate`；单文件内 error 级行剔除、结构性缺列短路的逻辑与单文件推送一致。
- **文件级隔离**：某文件存在 error 级失败 → 该文件整体不参与推送（门控阻断），但**不自动阻断其他无错文件**；最终聚合成「成功文件 / 失败文件」清单。
- **缺列文件短路**：结构性缺列文件直接整文件剔除，不发出后端请求。
- **部分失败呈现**：结果清单标注失败文件原因（缺列 / error 级行数）；仅含 warn 级的文件弹确认可整体「忽略并继续」。
- **埋点**：批量场景 `${telemetryPrefix}.missingColumnsDetected` 及 `.xxxSkipped` 按文件聚合上报（telemetryPrefix 为 `explorerPush` / `editorPush`）。

## 4. 用户操作流程

### 4.1 校验并定位
1. 在案例编辑器编辑案例，点击工具栏「校验」（或文件打开 / 编辑防抖自动触发）。
2. 系统跑行级校验（默认全表），弹出校验结果面板。
3. 面板按**单元格**列出每条问题（同格多问题聚合为一条）：「行 N · 中文列名 · 原因（可含多条）」+「定位」按钮（C 类仅有「定位」，本需求不提供修复操作）。
4. 点击「定位」，表格滚动到该格并红底高亮；若列缺失则高亮整行。

### 4.2 校验后推送
1. 确认无 error 级阻塞（问题已处理）后点击「推送」。
2. 推送前预校验（`stepPreValidate`）再次校验一遍；若存在 error 级失败，门控阻断（或 warn 级弹确认）。
3. **注意**：接口级字段（designer / artifactId / sourcePlatform）无法本地校验，仍需推送后才发现（见 §5.1）。

## 5. 边界、风险与对策

### 5.1 必须明确的边界
- **接口级错误无法本地修复**：`designer` / `artifactId` / `sourcePlatform` 等只有调后端才知道对错，纯本地校验无法发现，也不能自动修复（属已知边界）。"校验通过"≠"一定推送成功"，需在面板提示此边界，避免用户误解。
- **C 类只定位不修（仅给建议值）**：语义类问题（预期与步骤数不一致、枚举选错具体值）系统不擅自改写，防止破坏案例真实性（见 §3.3）。
- **空表 / 仅样例行边界**：文件为空或所有数据行均为样例行时，点「校验」应提示"无可校验的数据行（均为样例行或文件为空）"，而非空面板或报错。
- **过滤视图叠加**：校验基于全量数据行，结果面板可与"仅看失败行"等过滤视图共存；若用户处于过滤视图，定位 / 高亮仍作用于全量中命中的单元格，不限于可见行。

### 5.2 风险与对策
| 风险 | 对策 |
|------|------|
| 列映射失败导致问题丢失 | 前端字段→列反查失败时降级为整行高亮 + 面板标注"列缺失"，不静默丢弃 |
| 校验规则与推送不一致 | 校验与推送预校验共用同一份字段约束（以推送预校验为唯一权威源），单方改动需同步维护 |
| 隐藏行 / 过滤视图下误判 | 基于全量数据行校验与高亮，不区分可见性 |
| 冻结行 / 列被误标 | 校验定位沿用既有冻结行 / 列约束，冻结列（如 `testcase_id`）不参与编辑校验写回 |
| 编辑防抖重复弹窗 | 打开弹窗有序列 / 抑制保护，编辑后刷新通过 `postEditValidationRefresh` 重绘而非重复弹窗 |

## 6. 验收标准

1. **校验入口**：工具栏出现「校验」按钮；点击后对**全表**跑校验，弹出结果面板，无问题时提示"校验通过，可推送"；空表 / 仅样例行时提示"无可校验数据行"。编辑期自动校验（打开 / 编辑防抖）亦能触发弹窗与高亮。
2. **单元格定位**：每条问题精确红底高亮到 `[row,col]`（列由 `field` 映射；映射失败时高亮整行并标注）；点「定位」滚动并聚焦该格；面板显示中文列名 + 原因。
3. **推送前预校验与门控**：点击推送时 `stepPreValidate` 复校一遍；error 级失败门控阻断（`preValidateGateBlocked`），warn 级弹确认可取消（`preValidateGateCancelled`）；缺列短路全部行。
4. **高亮持久化**：红 / 黄底高亮写入 `push-failures.json`，关闭 / 重开 / 重启后不丢失。
5. **一致性**：校验与推送预校验共用同一份字段约束（以推送预校验为唯一权威源）。
6. **边界**：面板提示"校验通过≠一定推送成功（接口级错误需推送才发现）"；列缺失不导致问题丢失；冻结列不被误标。
7. **埋点**：校验全流程事件（编辑期 `editValidation.*`、推送前 `${prefix}.*`、门控 `.aborted`）按埋点需求文档 §4.11 上报，且含 `columns`（有问题的列名）维度。
