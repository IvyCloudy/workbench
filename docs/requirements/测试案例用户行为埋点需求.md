# 测试案例用户行为埋点需求文档

> 文档视角：业务 / 用户行为分析（运营、产品、研发回溯）
> 适用范围：用户对「测试案例文件」从创建到销毁全生命周期的一切可观测操作行为
> 说明：本文档描述**需要被埋点追踪的用户行为**、业务规则与验收标准，不涉及具体实现方式。
> 现状基线：`src/utils/telemetry.ts` 已提供统一埋点通道（`TelemetryService.sendTelemetryEvent` / `sendTelemetryErrorEvent`），`docs/specs/埋点事件清单.md` 为事件契约总表。

---

## 1. 总体背景与目标

测试案例以 CSV / YAML / JSON 文件维护于「测试任务」目录体系下。当前埋点已覆盖**保存落盘、推送、在线查看、绑定/解绑弹窗、删除案例行**等核心链路，但从「用户行为分析 / 操作旅程还原」视角看，仍存在大量空白：

- **文件级生命周期不全**：有创建（仅成功）、有绑定库同步（改名/删除的副作用），但缺「用户删除案例文件」「用户给案例文件改名」这一**行为本体**事件；
- **编辑中行为空白**：仅埋了"保存"这一落盘点，用户在编辑器内的单元格编辑、增删行、撤销重做等**过程行为**完全不可见；
- **复制 / 另存 / 导入 / 导出**等高频操作无任何追踪；
- **旅程无法串联**：创建 → 改名 → 多次编辑 → 推送 → 删除 是一条完整用户旅程，但缺乏 `journeyId` 等稳定关联标识，后台只能孤立看单点事件；
- **旅程边界缺失**：无「关闭文件」「切换文件」「外部工具改了案例」等界定旅程起止与冲突的事件。

本需求目标：让**每一个用户可感知的案例操作行为都可被埋点追踪**，从而支撑用户行为分析、操作旅程还原、功能使用热度与流失点定位。

---

## 2. 术语与前提

| 术语 | 业务含义 |
|------|----------|
| 测试案例文件 | 位于「测试任务 / <任务> / 测试案例」目录体系下、被插件识别为案例的 `.csv` / `.yaml` / `.yml` / `.json` 文件 |
| 测试要点文件 | 与之关联的 `.md` / `.xmind` 等测试大纲文件（本文档聚焦案例侧，要点侧仅在「绑定同步」副作用中涉及） |
| 用户行为事件 | 由用户主动操作触发、可观测的埋点事件（区别于系统/绑定库自动同步的副作用事件） |
| 旅程（journey） | 一次用户任务会话：从创建或打开案例文件起，到关闭 / 推送完 / 删除止；用 `journeyId` 串联 |
| 会话（session） | 插件启动级标识，已在 `telemetry.ts` 自动注入（`sessionId`） |
| 稳定文件标识（fileId） | 跨改名仍可关联同一文件的标识，建议取 `testcase_id`（若有）或文件内容 hash；改名后旧事件据此关联 |
| 命令创建 | 通过插件「新增测试案例」入口创建的文件，区别于用户手动 `touch` / 资源管理器新建 |

## 3. 用户行为全景（按生命周期阶段）

```
[创建] → [打开/进入编辑] → [改名] → [编辑内容(多次)] → [复制/导入/导出]
   │            │              │            │                  │
   └────────────┴──────────────┴────────────┴──────────────────┘
        （全程可触发：校验 / 推送 / 配置修改）
                          │
                   [关闭文件] → [删除文件]
```

| 阶段 | 用户行为 | 是否已有埋点 | 备注 |
|------|----------|--------------|------|
| 创建 | 新增测试案例文件 | ⚠️ 部分（`createNewTestCase.success`） | 缺失败/取消、缺模板与旅程维度 |
| 打开 | 打开案例编辑器 | ✅（`editor.opened` / `editor.opened.unqualified`） | 可补 `journeyId` |
| 改名 | 重命名案例文件 | ⚠️ 仅副作用（`pointCaseBindings.rename.synced`） | 缺用户行为本体 |
| 编辑 | 单元格编辑 / 增删行 / 撤销重做 | ❌ 空白 | 仅 `editor.saved` 落盘点 |
| 复制 | 复制 / 另存为案例文件 | ❌ 空白 | 会生成新 testcase_id，需追踪 |
| 导入 | 从表格浏览器等导入数据到案例 | ❌ 空白 | |
| 导出 | 导出案例 | ❌ 空白 | |
| 校验 | 手动触发 YAML / 格式校验 | ❌ 空白 | 诊断已有，主动校验无 |
| 推送 | 推送案例 | ✅（`editorPush.*` / `explorerPush.*`） | 可补 `journeyId` 关联 |
| 关闭 | 关闭 / 失活案例文件 | ❌ 空白 | 旅程结束边界 |
| 删除 | 删除案例文件 | ⚠️ 仅副作用（`pointCaseBindings.delete.synced`） | 缺用户行为本体 |
| 冲突 | 外部工具 / 他人修改案例 | ❌ 空白 | 协作可感知结果 |

## 4. 功能需求（按行为逐一描述）

### 4.1 文件创建行为

#### 需求背景与目标
创建是用户旅程起点。需完整追踪「用户意图 → 校验 → 成功/失败」全过程，并打上 `journeyId` 作为旅程锚点。

#### 交互与功能规则
- **成功创建**：`createNewTestCase.success` 需补充维度 `template`（模板类型：csv/yaml 标准模板）、`journeyId`（本次旅程唯一标识，随文件打开传入 webview）。
- **前置校验失败**：新增 `createNewTestCase.aborted`，`reason` 取值：`noTarget`（无目标目录）/ `notTestCaseDir`（非测试案例目录）/ `noExt`（未指定扩展名）。
- **创建异常**：新增 `createNewTestCase.failed`，携带 `errorMessage` / `stackHead` / `ext`。

### 4.2 文件改名行为（用户行为本体）

#### 需求背景与目标
用户给案例文件改名是高频操作，但当前仅有「绑定库同步」副作用事件，无法区分"用户主动改名"与"系统同步"。需独立的用户行为事件。

#### 交互与功能规则
- **改名成功**：新增 `testCaseFile.renamed`，维度：`oldName` / `newName` / `ext` / `journeyId` / `via`（改名途径：`inline` 内联重命名 / `explorer` 资源管理器 / `command` 命令）。
- **改名同步异常**：新增 `testCaseFile.rename.failed`，区别于现有 `pointCaseBindings.rename.error`（后者为绑定库副作用，保留共存）。
- **判定范围**：通过 `fileIdentifier` 判定 old/new 是否为案例文件，仅案例文件触发；非案例文件不报。

### 4.3 文件删除行为（用户行为本体）

#### 需求背景与目标
删除是旅程终点之一。当前仅有 `pointCaseBindings.delete.synced`（绑定库引用清理），无法感知"用户删除了案例文件"这一行为本身，也无法统计删除频率与误删率。

#### 交互与功能规则
- **删除成功**：新增 `testCaseFile.deleted`，维度：`fileName` / `ext` / `journeyId` / `isTestCase`（`true` 插件识别为案例 / `false` 仅按扩展名命中）/ `hasBoundCase`（删除时是否仍绑定要点）。
- **删除同步异常**：新增 `testCaseFile.delete.failed`（区别于 `pointCaseBindings.delete.error`，保留共存）。
- **触发来源**：`vscode.workspace.onDidDeleteFiles` 监听器内，对案例文件补报本行为事件（与现有绑定库同步并列，不替换）。

### 4.3.1 编辑器内删除案例（同步 TMS 平台）

#### 需求背景与目标
用户在表格编辑器内右键删除已推送案例行，会触发"同步删除 TMS 平台案例及执行/缺陷关联"。当前仅有 `syncDeletedRows.*`（底层同步副作用），无法感知"用户在编辑器内主动删除了案例"这一行为本体，也无法统计编辑器内删除频率、同步成功率与失败原因分布。

#### 交互与功能规则
- **删除发起**：新增 `editor.deleteRows.init`，维度：`fileFormat` / `requestRows`（本次删除的案例行数，含纯本地行）。无论最终是否同步、是否成功都上报，记录"用户触发了删除动作"这一行为本体。
- **删除结果**：新增 `editor.deleteRows.synced`，维度：`syncedTotal`（线上同步成功数）/ `failedRows`（失败数）。与 `init` 形成"发起→结果"闭环，可计算编辑器内删除同步成功率。
- **删除异常**：新增 `editor.deleteRows.error`，维度：`fileFormat` / `errorMessage` / `stackHead`。
- **与底层同步事件关系**：`editor.deleteRows.*` 是用户行为本体（在 `editorMessageHandlers` 删除入口上报），`syncDeletedRows.*` 是底层同步副作用（在命令面板"同步已删除行"与编辑器删除共用的同步方法内上报）；两者共存，后台以前者统计"用户删除行为"、以后者统计"同步动作本身"。

### 4.3.2 文件删除拦截（资源管理器删文件）

#### 需求背景与目标
资源管理器删除案例文件时，插件在"文件即将删除"阶段拦截并按行同步、在"文件已删除"阶段重建/重开。当前仅 `pointCaseBindings.delete.synced`（绑定库引用清理副作用），无法感知整个拦截旅程——包括"是否需要线上删除""用户是否取消""重建是否成功"。需补充本行为本体事件。

#### 交互与功能规则
- **拦截发起**：新增 `caseFileDelete.intercept.init`，维度：`filePath`（仅文件名）/ `totalRows` / `hasTsId` / `nonEmptyIds`（非空案例标识数，区分"需线上删"与"纯本地删"）。即便无案例标识也上报，记录"用户触发了文件级删除"。
- **拦截结果**：新增 `caseFileDelete.intercept.done`，维度：`total` / `success` / `failed`。
- **拦截异常**：新增 `caseFileDelete.intercept.error`，维度：`filePath` / `errorMessage` / `stackHead`（waitUntil 阶段未捕获异常）。
- **用户取消重建**：新增 `caseFileDelete.restore.done`，维度：`failedRows` / `filePath`（用户取消后把原文件重建回盘，保留失败行版本）。
- **自动重开**：新增 `caseFileDelete.reopen`，维度：`filePath`（删除前文件已打开，处理完成后自动重开并渲染删除高亮）。
- **did 阶段异常**：新增 `caseFileDelete.didHandler.error`，维度：`filePath` / `errorMessage` / `stackHead`。
- **与文件删除行为本体的关系**：`caseFileDelete.*` 聚焦"删除拦截旅程"（含取消/重建/重开），`testCaseFile.deleted`（§4.3）聚焦"文件最终被删除"这一结果；两者正交、可叠加，后台用文件名关联。

### 4.3.3 要点删除关联案例（本地清理）

#### 需求背景与目标
在测试大纲侧删除某测试要点时，会顺带把该要点关联的案例行从本地案例文件移除。这是删除案例功能中"纯本地清理"的一条路径，需有独立行为事件支撑"要点删除频率""清理量""异常率"分析。

#### 交互与功能规则
- **逐要点完成**：`pointCaseDeleter.done`（已在清单 §12 登记），维度含 `pointId` / `pointName` / `pointPath` / `deletedCount` / `type1` / `type2` / `type3` 等，逐要点各 1 条。
- **聚合**：`pointCaseDeleter.done.aggregate`，多要点删除时额外 1 条，去重口径。
- **异常**：`pointCaseDeleter.error`，删除流程任一环节抛错（互斥仅 1 条）。
- **与绑定库副作用关系**：`pointCaseDeleter.*` 是要点删除案例行为本体；若被删案例文件同时被绑定库监听，还会触发 `pointCaseBindings.*` 同步副作用，二者共存。

### 4.4 文件复制 / 另存为行为

#### 需求背景与目标
用户复制一份案例（Ctrl+C/V 或另存为）是常见复用手段，且会生成新的 `testcase_id`，需追踪复制来源与去向，避免"幽灵案例"无溯源。

#### 交互与功能规则
- **复制成功**：新增 `testCaseFile.duplicated`，维度：`srcName` / `dstName` / `ext` / `journeyId`（继承源文件旅程或新开）。
- **判定**：文件创建且内容/命名与既有案例高度相似、或捕获到「复制」命令触发的连续 create+rename 模式时上报。

### 4.5 案例内容编辑行为（编辑中过程）

#### 需求背景与目标
仅埋"保存"丢失了用户在编辑器内的真实操作密度与习惯。需追踪编辑过程行为，支撑"哪些字段最常改""用户是否频繁撤销"等分析。

> 前置条件：webview → 插件 的 `telemetry` 消息通道需先行落地（`BaseEditorProvider` 接收 `postMessage({type:'telemetry', name, props})` 并上报；前端在对应交互处补 `postMessage`）。当前该通道在清单中为「展望」，尚未实现。

#### 交互与功能规则
- **单元格编辑**：`caseContent.cellEdited`，维度：`fileFormat` / `journeyId` / `col` / `row`。
- **新增行**：`caseContent.rowAdded`，维度：`fileFormat` / `journeyId`。
- **删除行**：`caseContent.rowRemoved`，维度：`fileFormat` / `journeyId`。
- **撤销 / 重做**：`caseContent.undo` / `caseContent.redo`，维度：`fileFormat` / `journeyId`。
- **保存（补维度）**：现有 `editor.saved` 补充 `journeyId`，新增 `caseContent.save.failed`（落盘失败，`fileFormat` / `errorMessage` / `stackHead` / `journeyId`）。
- **频率控制**：单元格编辑为高频事件，建议前端节流（如 1s 内同 cell 合并为 1 条）或仅上报聚合计数，避免埋点队列压垮网关。

### 4.6 导入 / 导出行为

#### 需求背景与目标
从表格浏览器发送数据到案例、或将案例导出，是数据进出案例的边界操作，需追踪流向。

#### 交互与功能规则
- **导入到案例**：`caseContent.imported`，维度：`source`（`tableBrowser` / `clipboard` / `file`）/ `totalRows` / `journeyId`。
- **导出案例**：`caseContent.exported`，维度：`target`（`csv` / `xlsx` / `clipboard`）/ `totalRows` / `journeyId`。

### 4.7 校验 / 诊断主动行为

#### 需求背景与目标
用户主动触发 YAML / 格式校验是质量自纠动作，需与"系统自动 diagnostic"区分。

#### 交互与功能规则
- **主动校验**：`caseContent.validate`，维度：`fileFormat` / `trigger`（`command` / `saveAuto`）/ `issueCount` / `journeyId`。
- **Xmind 解析为要点**：`xmind.parsed`（如适用），维度：`pointCount` / `costMs` / `journeyId`。

### 4.8 文件关闭 / 切换行为（旅程边界）

#### 需求背景与目标
需明确旅程起止，才能计算"一次编辑会话时长""编辑后是否推送""编辑后是否误删"。

#### 交互与功能规则
- **关闭文件**：`editor.closed`（新增），维度：`fileFormat` / `journeyId` / `dirty`（`true` 有关未保存改动被丢弃或保留）。
- **切换文件 / Tab**：`editor.switched`（新增，可选），维度：`from` / `to` / `journeyId`。

### 4.9 冲突 / 外部变更行为

#### 需求背景与目标
协作场景下他人或外部工具改了同一案例，需可感知冲突。

#### 交互与功能规则
- **内容冲突**：`caseContent.conflict`（新增，可选），维度：`fileFormat` / `journeyId` / `origin`（`fsWatcher` / `onDidSaveTextDocument`）。

### 4.10 配置 / 元行为（影响埋点的上下文）

#### 需求背景与目标
推送环境切换、designer 修改等配置变化会显著影响后续行为解读，需记录上下文。

#### 交互与功能规则
- **配置变更**：`config.changed`（新增，可选），维度：`key`（如 `pushEnv` / `designer` / `telemetryEnabled`）/ `scope`（`user` / `workspace`）。

## 5. 旅程串联设计（核心能力）

### 5.1 journeyId（旅程串联核心机制）

#### 5.1.1 为什么需要专门机制
一次用户旅程会跨越**两个进程世界**，journeyId 必须在它们之间"夹带"存活，否则串不起来：
- **插件主进程（Node.js）**：文件创建、改名、删除、保存落盘、推送——由 `vscode` API 与 `BaseEditorProvider` 处理。
- **webview 渲染进程（浏览器）**：用户在表格内的单元格编辑、增删行、撤销——发生在前端 JS 里。

现有代码已印证该边界：
- `BaseEditorProvider` 用 `panelMap: Map<filePath, panel>` 维护「文件 → webview」映射（`BaseEditorProvider.ts:292`）；
- `webviewPanel.webview.postMessage(...)` 是**插件→前端**通道，`onDidReceiveMessage` 是**前端→插件**通道（`editorMessageHandlers.ts` 的 `buildHandlers` 表）；
- 前端目前**没有**回传 telemetry 的通道（`caseContent.cellEdited` 等仍停留在清单「展望」区，尚未实现）。

因此 journeyId 的串联本质 = **在插件↔webview 双向消息里稳定夹带一个 ID**。

#### 5.1.2 journeyId 全生命周期（5 步串联）

```
① 生成（锚点）
   触发点：文件创建成功 或 首次打开编辑器（editor.opened）
   生成：journeyId = crypto.randomBytes(8).toString('hex')   // 复用 sessionId 同款机制
   存储：存入该文件在插件侧的 EditorSession（与现有 session 对象同生命周期，
        见 editorMessageHandlers.ts:35 的 EditorMsgCtx.session）

② 下发前端（插件 → webview）
   pushDataToWebview 组装数据帧时，把 journeyId 塞进消息体：
     webviewPanel.webview.postMessage({ type:'data', journeyId, ... })

③ 前端持有（webview 内部）
   前端把 journeyId 存在自身状态里；
   每次用户操作（cellEdited / rowAdded / undo）postMessage 回插件时原样带回：
     webview.postMessage({ type:'telemetry', name:'caseContent.cellEdited', journeyId, props })

④ 插件接收并上报（前端 → 插件）
   editorMessageHandlers 新增 'telemetry' handler，直接转发：
     TelemetryService.sendTelemetryEvent(name, { ...props, journeyId })

⑤ 改名时的"接力"（关键）
   改名后 filePath 变了，但 journeyId 不变——
   - BaseEditorProvider 已有 updatePanelMapKey(old, new)（BaseEditorProvider.ts:300）；
   - journeyId 不绑 filePath 字符串，而是绑 EditorSession；
     改名时只更新 filePath 引用（现有 renameSub 已做，BaseEditorProvider.ts:583），
     journeyId 留在 session 里继续用 → 改名前/后的事件自动同旅程。
```

#### 5.1.3 保证"串得起来"的 4 个关键机制

| 机制 | 如何保证串联 | 代码落点 |
|------|------------|---------|
| **单一生成点** | journeyId 只在「创建成功」或「首次打开」生成一次，后续绝不重新生成 | `fileCreator.ts` 创建处 / `editorMessageHandlers.handleInit` |
| **session 持有** | journeyId 存在 `EditorSession` 上（与现有 `session` 同生命周期），不依赖 filePath 字符串 | `editorMessageHandlers.ts:35` 的 `EditorMsgCtx.session` |
| **改名不丢** | 改名只改 `filePath` 引用，不动 session / journeyId | 现有 `renameSub` + `updatePanelMapKey` 机制直接复用 |
| **双向夹带** | 插件↔webview 每次消息都带 journeyId，前端无状态也无所谓 | `postMessage` 数据帧 + 新增 `telemetry` handler |

#### 5.1.4 必须处理的边界情况（否则串断）

- **① 用户用外部编辑器改案例（不走插件）**：无 journeyId 生成点 → 后台会看到「孤立的 `editor.saved` 无 journeyId」。处理：journeyId 允许为空；后台把「有 journeyId」算完整旅程，「无」算游离操作（仍可单独统计），不强行串。
- **② 同一文件被两个 tab 打开（多次 open）**：现有 `panelMap` 是 `Map<filePath, panel>`（单值），第二次 open 会覆盖第一次。journeyId 也面临「第二次 open 是否新开旅程」：建议**复用同一 journeyId**（同一文件 = 同一旅程），实现时在 session 里判重。
- **③ 跨会话（关闭插件再开）**：journeyId 是内存态、不持久化，重启后新旅程 = 新 journeyId。这**符合预期**（旅程本按「一次使用会话」界定）。跨重启关联需用 `fileId`（见 §5.2）做二级关联键。

#### 5.1.5 后台还原旅程
```sql
SELECT * FROM events WHERE journeyId = 'ab12cd34' ORDER BY ts;
-- 得到有序事件流：
-- createNewTestCase.success → editor.opened → caseContent.cellEdited ×3
-- → caseContent.rowAdded → editor.saved → editorPush.start → editorPush.complete
-- → testCaseFile.renamed → editor.closed
```
据此可算：**停留时长**（首末事件差）、**编辑密度**（cellEdited 次数）、**行为顺序异常**（如推送后才改名）等。

#### 5.1.6 关联维度约定
- 所有 §4 新增事件均带 `journeyId`；
- 已有事件在可行处补带：`editor.opened` / `editor.saved` / `editorPush.start` / `editorPush.complete` / `explorerPush.start` / `explorerPush.complete`（从编辑器发起时携带当前 session 的 journeyId）。

### 5.2 fileId（稳定文件标识，跨改名/跨会话关联）

- **用途**：journeyId 仅覆盖「一次使用会话」，fileId 用于跨改名、跨重启把同一物理文件的历史事件归并。
- **取值**：优先取文件内 `testcase_id`（若存在且稳定），否则取文件内容 hash。
- **携带**：改名事件同时带 `oldFileId` / `newFileId` 便于后台归并；删除事件带 `fileId` 便于回溯「该文件一生」的操作。
- **与 journeyId 关系**：journeyId 是「会话内有序链」，fileId 是「文件级归并键」，二者正交、可叠加使用。

### 5.3 优先级
| 优先级 | 范围 | 说明 |
|--------|------|------|
| **P0** | `testCaseFile.created(补)` / `renamed` / `deleted` + `journeyId` 串联 + `editor.closed` | 旅程骨架，缺失最严重 |
| **P1** | webview `cellEdited` / `rowAdded` / `rowRemoved` / `undo` / `redo` + 通道落地 | 编辑过程可见 |
| **P2** | `duplicated` / `imported` / `exported` / `validate` | 数据进出与质量自纠 |
| **P3** | `editor.switched` / `caseContent.conflict` / `config.changed` / `xmind.parsed` | 边界与元行为 |

## 6. 验收标准

1. **文件级行为全埋点**：在一个测试案例文件上执行「创建 → 改名 → 删除」三步，后台能收到对应的 `createNewTestCase.success` / `testCaseFile.renamed` / `testCaseFile.deleted` 各 1 条，且三者 `journeyId` 一致（创建与删除同旅程，改名在同旅程内）。
2. **删除行为本体可追溯**：删除一个案例文件，除现有 `pointCaseBindings.delete.synced` 外，额外收到 `testCaseFile.deleted`；删除非案例文件（如 `.txt`）不触发 `testCaseFile.deleted`。
3. **编辑过程可见**：在编辑器内编辑单元格、增删行、撤销，webview 通道能上报对应 `caseContent.*` 事件，且携带 `journeyId`。
4. **旅程可还原**：后台按 `journeyId` 分组，能完整还原用户一次从创建到推送/删除的操作序列，无断点。
5. **埋点不影响主流程**：所有埋点失败（网络/网关异常）不影响用户创建、保存、推送等核心操作，且不向上抛错。
6. **脱敏合规**：所有事件不含明文文件路径全称（仅文件名 / 扩展名 / `fileId`），遵循 `telemetry.ts` 既有脱敏约定。

## 7. 与现有埋点体系的关系

- **不破坏现有事件**：本文档新增事件均为追加，现有 `editor.*` / `editorPush.*` / `explorerPush.*` / `pointCaseDeleter.*` / `pointCaseBindings.*` 保持不变。
- **删除案例三类行为本体已补齐**：本文档 §4.3.1（编辑器内删除 `editor.deleteRows.*`）、§4.3.2（文件删除拦截 `caseFileDelete.*`）、§4.3.3（要点删除 `pointCaseDeleter.*`）分别覆盖删除案例功能的三条入口；与底层同步副作用 `syncDeletedRows.*`、绑定库副作用 `pointCaseBindings.*` 解耦共存。
- **副作用事件与行为事件解耦**：`syncDeletedRows.*` 是底层行同步副作用、`pointCaseBindings.*` 是绑定库自动同步副作用，而 `editor.deleteRows.*` / `caseFileDelete.*` / `pointCaseDeleter.*` / `testCaseFile.deleted` 是用户行为本体；两者共存，后台用文件名 / 案例标识关联，互不替代。
