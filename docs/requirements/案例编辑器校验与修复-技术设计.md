## 2. 核心数据结构

```ts
// 后端校验产出（handleValidate 回推给前端）
interface CellIssue {
  row: number;          // 0-based 数据行下标
  field: string;        // 英文 key，如 'testCaseName'（前端据此映射 col，后端不持有列序）
  category: string;     // 错误分类，对齐 pushFailureCategory 的 category
  reason: string;       // 短标签，如 'empty' / 'invalidEnum' / 'format' / 'missing'
  message: string;      // 用户友好文案
  fixable: 'A' | 'B' | false;  // A=可填默认值, B=可归一化, false=需手改(C类)
  fixValue?: string;    // A/B 类给出的建议修复值（见需求 §3.3 系统级配置）；同格多问题时由修复步骤按优先级合并为单值
  fixSteps?: FixStep[]; // 同格多 A/B 类动作的**有序修复步骤**（优先级来自系统级配置，见 §4），前端按序执行后一次写回
  suggestion?: string;  // C 类给出的建议值文案（不自动写入，见需求 §3.4）
}
// 注：col 不在结构中；前端用 headerLabels 将 field 映射为 col 后再构造 highlightedCells.cells。

// 同格多 A/B 类动作的修复步骤（由系统级配置驱动，见 §4）
interface FixStep {
  action: 'fillDefault' | 'normalize' | 'caseNormalize'; // 动作类型
  field: string;        // 作用字段
  priority: number;     // 执行次序，取自配置
  value?: string;       // 目标值（fillDefault / normalize 用）
}
```

## 3. 关键实现骨架

### 3.1 后端 handler

```ts
// editorMessageHandlers.ts —— buildHandlers() 新增一项
validate: handleValidate,

async function handleValidate(_msg, ctx) {
  // 1. 取缓存的当前文件表格数据（无需重新解析）
  const rows = ctx.session.cachedTableData?.rows ?? [];
  // 2. 复用 collectRowIssues 跑全量校验（跳过样例行）
  const issues: CellIssue[] = [];
  rows.forEach((row, i) => {
    const tsId = row[TS_ID_COLUMN];
    if (tsId && isSampleTsId(tsId)) return;   // 样例行跳过
    issues.push(...collectRowIssues(row, i));
  });
  // 3. 下发结果：问题清单（col 由前端映射）
  ctx.webviewPanel.webview.postMessage({
    type: 'validateResult',
    issues,
    fixableCount: issues.filter(x => x.fixable).length,
  });
}
```

### 3.2 前端改动点

1. **`index.html` 工具栏**：新增「校验」按钮 `id="validateBtn"`（置于「推送」旁）。
2. **`02b-bind.js` `bindToolbar()`**：绑定 `validateBtn` 点击事件 → `postMessage({ type: 'validate' })`（当前不带 range；后续增强选中范围校验时补 `range` 透传）。
3. **结果面板**：复用编辑器现有结果弹窗结构，新增「一键修复全部可修复项」按钮 + 每条问题的「定位 / 修复」按钮 + 「重新校验」入口（「重新校验」复用同一 `validate` 消息通道，即全表校验）。
4. **监听 `validateResult` 消息**（`01-core.js` 的 `onMessage` 分支）：
   - 将每条 `CellIssue.field` 经 `getHeaderLabels()` 映射为 `col`；找不到列时降级高亮整行并标注"列缺失"。
   - 同 `[row, col]` 多条问题按格聚合为一条展示（见需求 §3.3）；聚合条内若同时含 A/B 类与 C 类，A/B 类「修复」区与 C 类「定位 + 建议」区分两行排布（A/B 在上、C 类在下），避免操作混淆。
   - 构造 `highlightedCells.cells:[row,col]` 触发红底。
   - 渲染问题清单（中文列名 + 原因 + 按钮）。
5. **「修复」执行**：调用 §1 的回写三连（`row[ci]=fixValue; S.mods.add; saveFile(); patchCell`），批量模式最后一次 `renderTable()`；修复前 `pushHistory()` 以支持 `Ctrl+Z`。修复值 / 步骤严格取自系统级配置（见 §4）。

## 4. 系统级配置结构草案

> 需求文档 §3.3 已明确：修复步骤优先级与兜底值 / 归一目标值均为**系统级配置**（随扩展分发，对所有用户 / 项目生效，本期不引入项目级 / 用户级覆盖层）。本节给出该配置的具体结构草案，供实现参考。

```yaml
# 系统级配置文件（随扩展分发，对所有用户/项目生效；具体文件名由实现确定）
fixSteps:
  # 同格多 A/B 类动作的执行次序；priority 越小越先执行
  - action: fillDefault      # 填空值兜底
    priority: 10
  - action: normalize        # 去非法字符 / 枚举归一
    priority: 20
  - action: caseNormalize    # 大小写 / 同义词归一
    priority: 30

defaults:                    # A 类空值兜底（field -> 默认值）
  testCaseName: "未命名"
  type: "功能点类"
  description: "待补充描述"
  testCaseDes: "待补充描述"
  expected: "待补充预期"
  keyFlag: "否"

normalizers:                 # B 类归一（field -> 目标值映射 / 规则）
  testType:
    "接口": "接口自动化"
    "界面": "UI自动化"
    "手工": "手工"
    "自动化": "自动化"
  keyFlag:
    "是": "是"
    "否": "否"
  # 其余枚举：大小写 / 同义词归一，按 yamlConstants 枚举表执行
```

**一致性约束**：校验时给出的建议值与修复时写入的值，均须读取**同一份生效配置**（默认或覆盖后），禁止两侧各自硬编码，避免建议与写回不一致。
