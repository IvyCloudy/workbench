## 0. 概述

本文档汇总五类用户在使用案例编辑器与推送功能时反馈的问题，以及对应的产品需求。内容从用户实际使用和感知的角度描述，不涉及技术实现细节。

| 编号 | 用户场景 / 反馈 | 需求 |
| --- | --- | --- |
| R1 | 测试案例目录里有「临时文件」文件夹，里面的草稿被误当成正式案例 | 临时文件目录内的文件应被排除在案例功能之外 |
| R2 | json 案例只有一条记录时，编辑保存后文件从"数组"变成了"对象"，形态被破坏 | 单条数组的 json 保存后应保持数组形态 |
| R3 | 想一次删掉选中的多行，但右键只能逐行删 | 选中多行时，右键支持一次性删除选中行 |
| R4 | 推送时不知道在干什么、等很久、超时不明确 | 推送要给明确进度提示；最终超时定为 5 分钟；超时无响应时要可追踪 |
| R5 | 案例路径里包含「·」（间隔点），推送后变成了「/」，路径层级错乱、与测试要点关联匹配不上 | 路径中的「·」应原样保留，不应被当作分隔符转成「/」；若为历史约定须先提示用户 |

## R1. 测试案例文件夹中包含「临时文件」

### 用户场景
在测试任务目录下，常常有一个「临时文件」子文件夹，里面放的是草稿、备份或临时整理的 json/yaml/csv。

用户反馈的问题：
- 这些临时文件也被识别成了测试案例，能被打开进案例编辑器。
- 右键菜单里出现了"推送案例""绑定测试要点"等正式功能。
- 批量推送整个案例文件夹时，临时文件也被一起推送了，造成误推送。
- 双击临时文件里的 json 时，有时编辑器会卡住、界面无响应。

### 需求
1. 只要文件位于名为「临时文件」的文件夹内（不论层级多深），就不把它当作测试案例。
2. 这类文件：
   - 不能进入案例编辑器，不显示表格编辑界面；
   - 不提供推送、绑定等案例相关的右键功能；
   - 批量推送整个文件夹时自动跳过，且不计入失败。
3. 双击打开「临时文件」里的 json/yaml/csv 时，用普通文本编辑器打开即可，界面不应卡死。

### 使用预期
- 临时文件目录里的文件：右键看不到推送/绑定等菜单；批量推送时它们被静默跳过；双击以纯文本方式打开。
- 注意：判定依据的是"所在文件夹叫临时文件"，而不是"文件名里带临时文件几个字"。所以一个恰好叫 `xxx临时文件.json`、但不在临时文件文件夹里的文件，仍会被正常当作案例处理，不会误伤。

## R2. json 案例文件为单数组时，数组变为字典

### 用户场景
有些 json 案例文件，顶层是一个数组，但里面只有一条记录，例如：

```
[
  { "用例名": "...", "步骤": "..." }
]
```

用户在案例编辑器里打开、改了点内容、保存之后，发现文件变成了这样：

```
{
  "用例名": "...",
  "步骤": "..."
}
```

也就是说，原本的"数组（方括号）"被改成了"对象（花括号）"。这会导致下游读取这个文件的工具解析失败，因为形态变了。

### 需求
json 案例文件如果顶层是数组（无论里面是一条还是多条记录），编辑保存后**必须保持数组形态**，不能把单条数组自动"拍扁"成单个对象。

### 使用预期
- 原来顶层是 `[ {...} ]`（一条）的，保存后还是 `[ {...} ]`，不再是 `{...}`。
- 原来顶层是多条数组的，保存后还是数组。
- 原来顶层本来就是单个对象的，保存后仍是单个对象，不受影响（向后兼容）。

## R3. 案例编辑器选中多行时，右键支持删除选中行

### 用户场景
在案例编辑器里，用户经常需要清理一批用例：框选或整行选中了多行（比如 10 条），想一次性把它们删掉。

用户反馈的问题：
- 右键菜单里只有"删除该行"（删当前光标所在的一行），要删 10 行就得点 10 次，非常麻烦。
- 也没有"删除选中行"的入口。

### 需求
1. 当用户选中了多行（或跨多行的单元格区域）时，右键菜单应出现"删除选中行"菜单项，并标注将要删除的行数。
2. 点击后，一次性删除所有选中的行。
3. 删除行为要与现有逻辑一致：已经推送到后端的案例，走线上删除；删除失败的案例行要保留下来并给出失败原因提示，不能悄悄丢数据。

### 使用预期
- 选中多行 → 右键出现「删除选中行 (N)」→ 按提示确认 → 选中的 N 行被一次性删除。
- 如果只选中了单行（非整行），仍然显示"删除该行"；如果选的是跨多行的单元格区域，也支持一次性删除该区域覆盖的所有行。
- 已推送到后端的案例：触发线上删除；删除失败的行会保留并标灰、显示失败原因，方便后续重试。

## R4. 案例推送体验优化（进度提示 / 5 分钟超时 / 兜底追踪）

### 用户场景
用户点"推送"后，经常遇到以下困惑：

1. 点了推送，界面没什么反应，不知道是正在处理还是已经卡死。
2. 等了一阵子，突然弹出一个"推送超时未响应，已解除按钮锁定"的提示，但完全不知道这个超时到底是多久、为什么触发。
3. 有些大模型生成/大批量案例，推送本身就需要比较久，10 秒～1 分钟的超时太短，动不动就失败。
4. 推送真正卡死（后端一直不返回）时，没有任何记录可以排查是哪一个文件、哪一次操作出的问题。

### 需求
1. **明确进度提示**：点击推送后，界面给出清晰的"推送中，请耐心等待"提示（按钮转圈 + 文字提示），让用户知道后台在处理。
2. **统一超时时间为 5 分钟**：推送的最终超时统一设为 5 分钟，前端等待兜底与后端真实等待保持一致，行为可预期。
3. **超时可追踪**：当推送真的超过 5 分钟仍无任何响应、触发"已解除按钮锁定"时，应自动记录一条使用数据（埋点），包含：触发入口（工具栏还是右键）、文件名、文件格式、本次推送行数、超时时长。便于后续定位是哪一个文件、哪一次操作卡死。

### 使用预期
- 点击推送 → 按钮进入转圈状态，并显示"推送中，请耐心等待…"。
- 5 分钟内后端返回结果 → 正常弹出结果提示，需用户手动关闭。
- 超过 5 分钟仍无响应 → 界面提示"推送超过 5 分钟未响应，已解除按钮锁定"，按钮恢复正常可再次点击；同时后台记录一条该次超时的使用数据。
- 重复点击推送时，提示"推送中，请耐心等待…"，不会重复发起。

### 补充说明
- 正常情况下，后端会在 5 分钟时先返回超时错误，前端随之结束等待；因此"超过 5 分钟无响应"这一提示通常只在后端彻底卡死（如连接挂起、前置处理卡住）时才会出现——而这种情况正是最需要被记录追踪的异常场景。
- 若用户所在单位另行配置了更长的推送超时时间，则以配置为准。

## R5. 案例路径中的「·」被转换为「/」

### 用户场景
用户给案例所在路径（目录名或文件名）里使用了「·」（间隔点），例如 `功能模块/登录·校验`、`用例集·场景A.json`。推送之后发现，路径里的「·」全部被换成了「/」，原本是一个名称 / 一层的内容，被拆成了多级目录。

用户反馈的问题：
- 推到 TMS 后路径层级错乱，案例归类到了错误的目录，和本地对不上。
- 与测试要点做关联匹配时，路径对不上，关联失效或匹配错乱。
- 这个转换是静默发生的，推送前没有任何提示，事后才发现路径被改了。

### 需求
1. 路径中的「·」应作为名称的一部分**原样保留**，推送时不应被当作路径分隔符转换成「/」。
2. 若产品确实存在把「·」当分隔符的历史约定，至少在转换前给出**明确的提示或转换预览**，让用户知情并确认，而不是静默改写。

### 使用预期
- 路径含「·」的案例推送后，TMS 里看到的路径与本地一致，「·」仍然在，不再出现"本地一条路径、TMS 多级目录"的错位。
- 与测试要点的关联匹配基于原路径，不再因「·」被改写而失配。

### 补充说明（已确认方案与约束）
- 已确认方案：路径标准化**仅将反斜杠 \ 转换为 /**，全角 ／、间隔点 · 一律原样保留，不再当作分隔符。推送路径侧（pushDataMapper.normalizePath）与"测试要点 ⇄ 案例"关联匹配侧（pointCaseLinker.normalizePointPath）已同步修改，分隔符规则保持一致。
- 该方案直接满足需求 1：路径中的「·」原样保留，推送后 TMS 里层级不再错乱，关联匹配也基于原路径。
- 仍需关注：若历史上有团队确实用「·」或「／」当路径分隔符来组织老案例，改完后这些老案例的路径会被视为"含 ·/／ 的名称"，可能与原归类 / 关联预期不同；上线前应排查存量案例，必要时提供迁移提示或兼容处理。

## 1. 通用说明

- **临时文件的判定看"文件夹名"**：仅当文件所在的某个文件夹名字叫「临时文件」时才排除；文件名里带这几个字不算。
- **JSON 单数组保形**：仅当原始文件顶层本来就是数组时才保持数组；原始就是单个对象的文件仍按对象保存。
- **推送 5 分钟超时**：这是兜底下限；若单位配置了更长的超时，则按配置执行。
- 本批次新增的可追踪使用数据（推送 5 分钟无响应、编辑器内删除案例）目前暂无自动化测试覆盖，将在后续按需补充。
