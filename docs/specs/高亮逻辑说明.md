## 1. 高亮种类总览

| # | 名称 | CSS 类 | 触发来源 | 状态字段 | 清理路径 |
|---|---|---|---|---|---|
| 1 | 修改小三角 | `.modified` | 用户直接编辑单元格 | `S.mods` / `S._detailModCellKeys` | 编辑器内推送后 05a 精确清；数据整体重载清；**右键推送后由 full-data 帧的 `clearAllMods` 标志清** |
| 2 | 单元格黄底（推送更新） | `xs-td-push-updated` | changedRows 中的具体单元格 | `S._highlightedCells.cells` | 快照更新后 diff 无差异即消失 |
| 3 | 行级橙底（推送更新） | `xs-td-push-updated-row` | changedRows 的整行 | `S._highlightedCells.rowSet` | 同上 |
| 4 | 新增行绿底 | `xs-td-push-added` | 快照中不存在该 tsId 且非样例、无 tcNo、无失败记录 | `S._addedRowSet`（扩展端 addedInfos） | 推送成功、快照包含后消失 |
| 5 | 用户手动标记 | `xs-td-user-marked` + inline `bgColor/fontColor` | 右键手动上色 | `S._userMarks` + `markStore.json` | 用户主动清除；不受任何推送/保存影响 |
| 6 | 推送失败红底 | 行 `xs-tr-push-failed`；单元格 `xs-td-push-failed` | 后端返回失败 / 前置校验失败 | `S._pushFailedTsIds` + `S._pushFailedReasons` + `S._pushFailedTime` + `pushFailureStore.json` | 该 tsId 推送成功后由 05a 清 |
| 7 | 失败叠加保护 | `xs-td-overrides-fail` | 失败时间早于其他高亮时间时保留原色 | 渲染时基于时间戳计算 | 每次渲染重新计算 |
| 8 | 样例灰底 | 首行灰色，禁止参与除标记外的高亮 | testcase_id 为占位符（`TESTCASE_ID` 等） | `isPlaceholderTsId` 判定 | 常驻，不参与失败/新增/修改高亮 |
| 9 | 删除幽灵行 | `xs-td-ghost` | deletedInfos | `S._deletedInfos` | 用户操作后清；数据整体重载清 |

## 2. 优先级与叠加规则（渲染时决策）

**决策文件**：`02a-render.js`。所有高亮共用一个"最新时间戳胜出"机制：

```
bestTime = 0
bestClass = ''

if 有黄/橙 push-updated: 用 _highlightedTime
if 有 push-added:        用 _addedRowTime
if 有 user-marked:       用 mkInfo.time
if 有 push-failed:
    if 失败时间 >= bestTime → bestClass = xs-td-push-failed（红色覆盖）
    else                    → bestClass 不变，附加 xs-td-overrides-fail（红底不吞其他色）
```

- 样例行永远只允许 `xs-td-user-marked`，其余类别不参与判定。
- 修改小三角 `.modified` 独立于以上机制，只要 `S.mods` 中包含该单元格坐标就渲染，与颜色叠加无冲突。

## 3. 数据流

### 3.1 编辑 → 保存 → 高亮下发

```
用户编辑
  │
  ▼
S.mods.add("r,c") ────────────── 修改小三角 #1 立即渲染（前端本地）
  │
  ▼ Ctrl+S / 焦点丢失
save 消息
  │
  ▼
BaseEditorProvider.save
  │
  ├─ diffPushSnapshot(oldSnap, newRows)
  │     ├─ changedRows → cells / rowIndices        （高亮 #2 / #3）
  │     ├─ addedInfos  → _addedRowSet + expandCells（高亮 #4，同时黄底 #2）
  │     └─ pushFailures 保持                          （高亮 #6）
  │
  ├─ session.highlightedCells = { cells, rowIndices }
  ├─ setHighlight(filePath, highlightedCells)
  │
  ▼ pushDataToWebview('saveHighlight')
前端 01-core.js 收到消息：
  · saveHighlight 是"自反弹"通道 → 不清 S.mods
  · 更新 S._highlightedCells / S._addedRowSet / S._pushFailedTsIds
  · renderTable()
```

### 3.2 编辑器内推送 → 精确清理

```
前端 04-push-find pushChanges
  · 缓存 S._lastPushBatchRowIndices / _lastPushBatchTsIds
  │
  ▼ postMessage('pushTestCase', ...)
BaseEditorProvider push handler
  │
  ▼ 后端 http 推送
  │
  ▼ postMessage('pushResult', { successCount, failures, ... })
前端 05a-push-result:
  1. 计算本批成功 tsId → 从 _pushFailedTsIds 移除
  2. 累加本次失败 → _pushFailedTsIds.add
  3. 精确清 S.mods / _detailModCellKeys / _addedRowSet 中"本批 rowIndices"的条目
  4. renderTable()
  │
  ▼ 后端 refresh('pushSuccess')
再走一遍 diff → highlightedCells 更新
  · 前端 01-core：pushSuccess 是"自反弹"通道 → 不清 S.mods（这里已被 05a 精确清完）
```

### 3.3 资源管理器右键推送 → 全量清理

右键推送**不经过 webview**，前端 05a 无从触发，需要扩展端主动清理。为避免"pushSuccess 帧默认保留 mods"策略与"整文件一次性提交"语义冲突，将清理指令**内嵌到 full-data 帧本身**，单帧原子完成：

```
右键 → pushHandler.handleFilePush → runPush（pushCore）
  │
  ▼ 成功回写 testCaseNo
  │
  ▼ hooks.afterWriteBack / onAllFailedSnapshot
BaseEditorProvider.postExplorerPushRefresh(filePath):
  entry.refresh('pushSuccess', true, true)
     └─ pushDataToWebview(forceReparse=true, reason='pushSuccess',
                          force=true, clearAllMods=true)
            · 重新 parse + diffPushSnapshot 得到最新 highlightedCells
            · session.highlightedCells / highlightStore.json 同步覆盖
            · full-data 消息附带 clearAllMods=true
  │
  ▼
前端 01-core 收到 full-data:
  · 覆写 S.data 前判断 m.clearAllMods === true：
      - S.mods.clear()
      - S._detailModCellKeys.clear()
      - S._history.length = 0 / S._future.length = 0
      - S._lastPushBatchTsIds.clear() / _lastPushBatchRowIndices = null
      - S._addedRowSet.clear() / _addedInfos = []
  · 走原 pushSuccess 分支更新 _highlightedCells / _pushFailedTsIds
  · renderTable()
  · 保留 _pushFailedTsIds / _userMarks 等其他状态
```

**关键点**：
- 右键推送语义 = 整文件一次性提交，因此 `S.mods` 直接**全量清空**是合理的。
- 不能复用 `clearAllHighlights` 消息，那是"重置一切"，会把用户手动标记 / 失败标记 / 新增行等一并清掉。
- `clearAllMods` 与数据帧同帧到达，无需 pre/post 两次 `clearMods` 兜底夹住中间帧的写法，也不再依赖多消息顺序保证。
- session.highlightedCells / highlightStore.json 由 pushSuccess 分支自身重设（无差异时置 null 并 clearHighlight），无需外部再显式清。

### 3.4 快照基线全量刷新（右键推送 & 编辑器推送统一）

`writeBackTestCaseNos` 中调用 `savePushSnapshot(filePath, tableData)` **不再传 `pushedTsIds` 增量参数**，两种推送路径统一走全量更新：

```
- await savePushSnapshot(filePath, parsed.tableData, pushedTsIds)   // ❌ 增量（旧行为）
+ await savePushSnapshot(filePath, parsed.tableData)                 // ✅ 全量
```

**为什么必须全量**：
- 用户在推送前编辑过的**失败行**（本次未成功回写）不在 `pushedTsIds` 中
- 增量更新只会覆盖成功行，失败行的快照仍是旧值
- 磁盘保存的是最新内存态（含失败行的编辑）→ 下次 diff 命中"旧快照 vs 新磁盘"→ 黄色修改高亮**假阳性**
- 全量刷新后：一次推送操作 = "用户认可当前磁盘状态为新基线"，失败行的红色高亮由 `pushFailures` 独立管理，与快照无关

## 4. 状态字段一览

| 字段 | 位置 | 生命周期 | 说明 |
|---|---|---|---|
| `S.mods: Set<"r,c">` | 前端 01-core | 单元格编辑 → 推送清理 | 修改小三角坐标集合 |
| `S._detailModCellKeys: Set<"r,c">` | 前端 01-core | 明细弹窗编辑 → 推送清理 | 明细弹窗改的格子（不受一般 mods.clear 影响，独立清理） |
| `S._highlightedCells: { colIdx, rowSet, cells }` | 前端 01-core | 每次 saveHighlight/pushSuccess 覆盖 | 黄/橙格集合 |
| `S._highlightedTime` | 前端 01-core | 更新时打点 | 与失败时间比较优先级 |
| `S._addedRowSet: Set<rowIndex>` | 前端 01-core | 每次刷新覆盖 | 新增行索引 |
| `S._addedRowTime` | 前端 01-core | 更新时打点 | 优先级用 |
| `S._pushFailedTsIds: Set<tsId>` | 前端 01-core / 后端 pushFailureStore.json | 失败入 / 成功出 | 失败标记 |
| `S._pushFailedReasons: Map<tsId, reason>` | 同上 | 同上 | 失败原因（tooltip） |
| `S._pushFailedTime: Map<tsId, ts>` | 同上 | 同上 | 失败时间戳（叠加优先级） |
| `S._lastPushBatchTsIds: Set<tsId>` | 前端 04-push-find | 一次推送生命周期 | 本批参与推送的 tsId |
| `S._lastPushBatchRowIndices: number[]` | 前端 04-push-find | 一次推送生命周期 | 本批行索引，用于精确清 mods |
| `S._userMarks` | 前端 01-core / 后端 markStore.json | 用户主动清除 | 手动上色数据 |
| `S._deletedInfos` | 前端 01-core | 每次刷新覆盖 | 幽灵删除行 |
| `session.highlightedCells` | 后端 BaseEditorProvider（每 panel 独享） | 保存/推送时更新 | 下发到 webview 的高亮基线 |
| `pushSnapshotStore.json` | 后端持久化 | 每次推送成功后覆盖 | 与磁盘 diff 的基线 |
| `pushFailureStore.json` | 后端持久化 | 与 `_pushFailedTsIds` 双向同步 | 失败标记持久化 |
| `highlightStore.json` | 后端持久化 | saveHighlight 时更新 | 高亮基线持久化，webview 关闭再打开可复原 |

## 5. 常见排错清单

| 现象 | 根因 | 修复位置 |
|---|---|---|
| 右键推送后修改小三角残留 | pushSuccess 帧默认保留 S.mods，右键推送不经过 05a | `postExplorerPushRefresh` 让 full-data 帧携带 `clearAllMods=true` 由前端在覆写 S.data 前无条件清全量本地状态（已修复） |
| 编辑器推送后修改小三角残留 | S.mods 清理未匹配到本批 rowIndices | 05a 兜底路径：从 tsId 反查 rowIndex |
| 失败行修改后仍红色 | `diffPushSnapshot` 曾对失败行 `return`，导致 mod 判定跳过 | 已移除防御 4，让失败行也参与修改判定 |
| 新增行推送失败后绿底残留 | `_addedRowSet` 没清 | 05a：pushRowIndices 中的项从 addedRowSet 中删除 |
| 修改状态与推送失败叠加 | 时间戳竞争异常 | 02a-render：比对 `_pushFailedTime` 与 `_highlightedTime`，早的加 `xs-td-overrides-fail` |
| 样例行被高亮 | 未先判 `isPlaceholderTsId` | 02a-render 内部先跳过样例行的高亮判定 |
| **改了 src 后没生效** | **未编译 TypeScript** | **执行 `npm run compile` 或 `npm run watch`** |

## 6. 修改后重启验证步骤

由于扩展主入口是 `./out/extension.js`，**改动 `src/*.ts` 必须编译**：

```bash
# 一次编译
npm run compile

# 或开发时持续监听
npm run watch
```

前端 JS（`media/pages/**/*.js`）修改**无需编译**，但 webview 需要重新加载：
- 关闭并重新打开对应文件的 tab；或
- 命令面板 `Developer: Reload Webviews`。

修改扩展逻辑后建议：`Developer: Restart Extension Host` 或重启 VSCode。
